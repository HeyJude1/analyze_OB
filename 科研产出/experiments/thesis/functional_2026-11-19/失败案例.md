# 失败案例与修复行为

下表由候选源码与编译／执行报告对照得到。用例数量是测试输入数，失败断言数量是输出元素、保护区和输入保留检查的失败次数。一个用例可触发多个断言。

| 单元 | 首轮与修复 | 从源码和日志能定位的问题 |
| --- | --- | --- |
| x86 DDOT，文本 RAG | 编译失败 → 编译失败 | 候选用了 `__m256d` 和 `_mm256_*`，文件缺少 `<immintrin.h>`，尾部循环还引用了作用域外的下标。两轮候选哈希相同。[记录](ollama/ddot/x86_avx2/text_rag/rep-1/result.json) |
| RISC-V DAXPY，约束规划 | 数值错误 → 编译失败 | 快速路径只要求 `incx==1`，对 `y` 连续载入和存储，违反合法的非单位 `incy`。修复切成了 x86 头文件及 AVX，RISC-V 编译器报缺头文件。[记录](ollama/daxpy/k1_rvv256/constraint_plan/rep-1/result.json) |
| RISC-V DAXPY，独立策略卡 | 编译失败 → 数值错误 | 首轮尾部变量超出作用域。修复调整了变量声明，快路径仍缺少对输出跨步的约束。[记录](ollama/daxpy/k1_rvv256/strategy_cards/rep-1/result.json) |
| x86 DGEMV，无外部知识 | 数值错误 → 数值错误 | `n==0 && alpha==0` 时直接返回，遗漏接口约定的 `beta*y`。两轮候选哈希相同。[记录](ollama/dgemv/x86_avx2/no_knowledge/rep-1/result.json) |
| RISC-V DGEMV，约束规划 | 数值错误 → 数值错误 | 无条件读出 `y` 并乘以 `beta`。测试在 `beta=0` 时让旧 `y` 含 NaN 来检查应有的覆盖语义。候选两轮哈希相同。[记录](ollama/dgemv/k1_rvv256/constraint_plan/rep-1/result.json) |
| x86 DSCAL，无外部知识，独立留出 | 数值错误 → 数值错误 | 候选将负步长路径写成 `x[(-i - 1) * incx]`。契约中 `x` 已指向逻辑起点，应使用从起点开始的有符号偏移。验证同时报输出错误和保护区写入。[记录](ollama/dscal/x86_avx2/no_knowledge/rep-1/result.json) |
| RISC-V DSCAL，无外部知识，独立留出 | 编译失败 → 编译失败 | 首轮对 RISC-V 目标输出了 `__m256d` 和 `_mm256_loadu_pd` 等 x86 接口。编译日志明确指出类型和 intrinsic 不可用。[记录](ollama/dscal/k1_rvv256/no_knowledge/rep-1/result.json) |
| x86 DASUM，文本 RAG，独立留出 | 运行超时 → 运行超时 | 模型用 `size_t n`，首轮循环条件为 `i <= n - BLOCK_SIZE`。当 `n < BLOCK_SIZE` 时无符号减法下溢，短输入可能进入大规模越界循环。验证器按 20 秒预算记录超时。[记录](ollama/dasum/x86_avx2/text_rag/rep-1/result.json) |
| RISC-V DASUM，文本 RAG，独立留出 | 编译失败 → 通过 | 修复移除了错误的头文件及相关实现，改为按有符号步长遍历和调用 `fabs`。这是标量回退通过功能检查的实例。[记录](ollama/dasum/k1_rvv256/text_rag/rep-1/result.json) |
| x86 DSYMV，独立策略卡，独立留出 | 编译失败 → 数值错误 | 修复后的展开主循环条件是 `i<n`，但每轮都计算并写出四项，尾部循环随后又覆盖部分元素。在非四倍数长度上，主循环未守住输出边界。[记录](ollama/dsymv/x86_avx2/strategy_cards/rep-1/result.json) |
| x86 DSYMM，约束规划，近迁移 | 编译失败 → 数值错误 | 修复后的列展开按 `j<n` 进入，每轮写四个 `c[i*ldc+j+k]`，没有处理末尾不足四列的情况。保护区检查确认越界写入。[记录](ollama/dsymm/x86_avx2/constraint_plan/rep-1/result.json) |

这些样本给出三个可单独验证的改动方向。对于架构提示，模板字段应显式绑定头文件和编译器版本。对于跨步或数值契约，验证前先检查生成代码有没有守住双步长、零系数和尾部条件。对于文本修复，次轮生成前可检查响应与候选代码指纹，用于识别无变化的修复。后续比较要给每组同样的执行和反馈预算。
