## 一句话结论

**不要推倒重来，但必须换掉"知识"的载体**：现有 7 实体 / 12 关系的原型骨架（Milvus + DashScope）和对齐流程可复用约 40%，缺的不是"更多实体类型"，而是 4 样让知识**可用、可查、可信**的东西——**硬件实例与参数值、可核查的性能证据、行级来源溯源、可执行实施模板**；12 周内只做一条闭环（RISC-V 双版本语料 → 差分抽取 → 结构化检索 → Morph 生成 → 现成 QEMU/bench 验证），存储以文件/SQLite 为真源、向量检索可插拔，**不引入 Neo4j**。

### 1.3 现有 Schema 的七个缺口（每一条都有证据）

> 判定标准：一条知识要能支撑"检索→生成→验证"，必须同时回答 **何时用（条件）、对什么硬件用（参数）、用了有什么收益（证据）、从哪来（溯源）、怎么写（模板）**。现有 Schema 只回答了其中"是什么"。

**G1 硬件知识是"教科书名词"，不是"硬件实例与参数值"。**
- `architecture_capability` 实体的 `TARGETS` 邻居名是 `寄存器` / `寄存器文件` / `浮点运算单元` / `内存子系统` / `分支预测器` / `SIMD` / `Cache`（`relation_refine_3.txt` 前 20 行可见）。
- 没有 VLEN/LMUL/SEW、向量寄存器个数、L1d/L2/L3 容量、cacheline、流水线深度等**任何数值**；`params` 字段在抽取器里被写成空串（`extractor.py:388`）。
- 后果：无法做"硬件约束过滤"；论文卖点"优化策略与硬件信息的关联"在数据层面**不可验证**。

**G2 性能收益是 LLM 形容词，不是可核查证据。**
- 典型值："整体加速可达 20%-50%"（`gemm_analysis.json:396`）、"显著提升缓存命中率"（`:55`）。
- 没有任何 baseline / 矩阵尺寸 / 平台 / 测量协议；`evidence_strength=0.5`、`source_count=1` 是**硬编码常量**（`extractor.py:368`、`:297`）。
- 后果：策略之间无法比较收益；审稿人一句"这是幻觉"即可否定排序的合法性。

**G3 来源溯源只到文件名。**
- 实体只存 `source_file = "cgemm3m_incopyb.clean.c"`，无仓库、commit、行号、抽取版本、prompt 版本。
- 关系描述是模板串："矩阵乘法微内核可使用指针算术优化优化"（`merger.py:214-221` 生成）。
- 后果：知识不可核查、不可增量更新、不可复现。

**G4 适用条件不可执行。**
- `applicability_conditions` 是自由文本："输入矩阵A为按列主序存储的单精度复数矩阵..."（`gemm_analysis.json:58`）。
- 本应承担条件判断的 `APPLIES_WHEN` 在**现有数据里 0 条**（只有 4 类关系）。
- 后果：检索无法做硬过滤，也无法解释"为什么推荐/不推荐"。

**G5 没有实施模板，参数覆盖率极低。**
- `implementation` 是自然语言段落；`tunable_parameter` 只有 38 条 `HAS_PARAMETER`，对 274 条 `OPTIMIZES_PATTERN` 覆盖率 ≈14%；参数值只有 `value_in_code`（如 2）和 `typical_range`，没有"该值由什么硬件参数决定"。
- 后果：生成端只能"参考描述"，无法按槽位注入参数——所谓"结构化 Prompt 模板"缺了最重要的结构化对象。

**G6 只有成功知识，没有失败与边界。**
- 全部语料来自 OpenBLAS 已高度优化的代码 → 典型生存者偏差；`CONFLICTS_WITH`、`ANALOGOUS_TO` 在数据里 **0 条**。
- 而 C 语料里就有负例：`41_idamax_op` 迁移版相对参考实现 geomean **0.187×**（尺寸≥64），`22_dnrm2_op` 0.589×（本文实测统计，见 §3.5）。
- 后果：无法回答"何时不该用"；"策略冲突消解"在数据上是空壳。

**G7 关系语义与实现不一致，一半关系是死代码。**
- 声明 12 种关系，实际产生过实例的只有 4 种；**8 种从未产生**：`INSTANCE_OF`、`GENERALIZES`、`COMPOSES_WITH`、`REQUIRES`、`APPLIES_WHEN`、`CONFLICTS_WITH`、`ANALOGOUS_TO`、`HAS_CHARACTERISTIC`。
- 更严重：`extractor.py` 的 v2 代码**根本不发 `OPTIMIZES_PATTERN`**（`grep` 结果只有第 34 行声明 + `merger.py:214` 的字符串比较），即用当前代码无法重建现有图谱；现有数据是旧版本抽取器的产物。
- `retrieval.py:349` 用 `INSTANCE_OF` 从相似 pattern 找 strategy（该关系 0 条），而数据里是 `OPTIMIZES_PATTERN` 且方向为 pattern→strategy → **现有检索链路对现有数据返回空**。

## 2. Schema v2（完整实体表 / 关系表 / 约束 / 真实 JSON）

### 2.1 设计原则（6 条，后面所有字段都由它们推出）

1. **证据优先（evidence-first）**：任何"收益"数值只能来自 `PerformanceEvidence`；策略本身**不存** speedup 数字。LLM 只能写解释，不能写数字（性能、硬件参数）。
2. **可执行（actionable）**：一条策略必须能落到 `ImplementationTemplate`（槽位 + 骨架 + 校验提示），否则只是"知识点"不是"知识"。
3. **可溯源（provenance）**：每个节点至少 1 个 `SourceArtifact`（仓库 + commit + 文件 + 行号），每条边有 `source`（artifact / evidence / manual）。
4. **闭集词表（controlled vocabulary）**：策略家族、计算阶段、代码特征类型、ISA、微架构必须先定义枚举；LLM 只能在闭集内填值，开放词只允许出现在 `description`。
5. **软合并（soft merge）**：对齐只写 `canonical_id + alias_ids`，永不物理删除；ID 一旦发布不可变（避免现有 `merger.py` 删了再插导致的 ID 漂移）。
6. **图-向量分离（split storage）**：结构化事实（节点/边/条件/参数）用 JSONL/SQLite；语义相似只在检索时用向量；两者通过 `id` 关联，可分别替换。

### 2.5 约束与不变量（可写成 `schema/validate.py`，CI 必须全过）

1. **ID 稳定**：`id = "{type}:{slug}"`，slug 由 `canonical_name` 经词表规范化得到；**禁止** v1 的 `md5(json.dumps(整个实体))`（`extractor.py:121`）——改一个标点就换 ID。
2. 每个节点 `provenance_ids` ≥1，且每个 artifact 的 `path/commit` 可解析。
3. **数值不变量**：`speedup/throughput/latency` 只能出现在 `PerformanceEvidence.value`；`OptimizationStrategy` 任何字段不得存收益数字；硬件数值只能来自 E8/E9。违反即校验失败（这是对 §1.4 B 的强制约束）。
4. 条件谓词必须引用 `char_type` 闭集；`value` 的类型必须与 `char_type` 匹配（数值型 vs 枚举型）。
5. 每条边必须有 `source`（`artifact_id` / `evidence_id` / `manual`）；`support < 2` 的边标 `status=candidate`，检索时降权。
6. 关系端点必须存在（外键校验）；`STRATEGY_CONFLICTS_WITH` 必须双向存在或查询时对称化。
7. 软合并：`status=merged` 的节点必须有 `canonical_id` 指向存活节点，`alias_ids` 保留全部历史 ID；**任何节点不得物理删除**。
8. 每个 `Strategy` 至少有 1 个 `STRATEGY_APPLIES_WHEN` 或显式 `applies_to_all=true`；每个 `Template` 至少有 1 个 slot 或显式 `slots=[]`。
9. 同一 `(head, rel, tail)` 唯一（幂等 upsert），避免重复抽取导致边翻倍（v1 merger 用"已存在则跳过"临时处理，见 `merger.py:253-256`）。
10. 版本四元组 `{schema_version, extractor_version, prompt_version, model_version}` 必须写入每次构建的 `manifest.json`。
11. 文本上限：`description ≤ 2000` 字、`skeleton ≤ 6000` 字符、代码证据走 artifact 行号不内联。
12. 每条 `PerformanceEvidence` 必须带 `protocol` 与 `measure_env`；QEMU 证据标 `confidence ≤ 0.4` 且 `rerun_needed=true`。

### 2.7 v1 → v2 迁移映射表（老数据怎么处理）

| v1 字段/实体 | v2 落点 | 迁移动作 |
|---|---|---|

### 3.2 一个算子目录里，哪些文件是知识（字段映射）

以 `openblas_newtest1/16_dgemm_op1/` 为例：

| 文件 | 内容 | 抽取为 | 生成方式 |
|---|---|---|---|
| `_command.txt` | 完整的 `gcc -march=... -D...` 提取/编译命令链 | **架构与 ISA 标签的唯一确定性来源**（`-march=rv64gcv_zvl256b` → RVV 1.0 + VLEN≥256；`-DCOMPLEX/-UDOUBLE` → dtype） | 正则解析，**不用 LLM** |
| `zzz_*_template.c` | 从 OpenBLAS 仓库复制的模板源 | `SourceArtifact.path` | 从 `cp` 命令提取路径 |
| `zzz_*.i` | 预处理后的完整翻译单元（500KB+） | `SourceArtifact` 的行号来源（`# 行号 "文件名"` 标记） | `# <n> "<file>"` 正则 → 近似行号 |
| `<op>.c` / `<op>_U.c` | 接口层（参数校验/prep/post） | `ComputationPattern`（`prep.*`/`post.*`） | LLM + 静态 |
| `<op>_k.c` | generic kernel | 策略实例（标量实现） | 差分 + LLM |
| `<op>_k_rvv.c` | RVV kernel | 策略实例（向量实现） | 差分 + LLM |

| `_file/benchmark/_<op>_dgc.c` | 测量协议（尺寸范围、参数、比较方式） | `PerformanceEvidence.protocol` | 人工读一次，固化为枚举 |

> **实测警示**：`01_chbmv_op/chbmv_k.c` 的内容其实是 `caxpy_k`（`01_chbmv_op/_command.txt` 的 `---next kernel---` 段显示脚本把 `caxpy_k.o` 当成了下一轮 kernel，覆盖了 `zzz_chbmv_k_template.c`）。这不是个例，W1 必须加**配对校验**：`grep -o '^int [a-z0-9_]*(' <op>_k.c` 得到的函数名必须包含 `<op>`（RVV 版还须以 `_rvv` 结尾，除非原始库就无 `_rvv`）。校验不通过的文件进 `quarantine/`，不进图谱。

### 3.3 架构归属怎么确定（解决"全部通用"的根因）

**不要问 LLM**。三个确定性来源，优先级从高到低：
1. `_command.txt` 里的 `-march=` / `-mabi=`（RVV 构建里可见 `rv64gcv_zvl256b`；x86 构建里可见 `-mavx2`/`-mavx512f`）。
2. `_file/lib/makelog.txt` / `rvv_makelog.txt` 里该 `.o` 的编译命令（`grep -E "\b<op>_k\.o\b"`）。
3. 源文件路径：`kernel/riscv64/` → RISC-V；`kernel/x86_64/` → x86；`kernel/generic/` → 架构无关。
这三条在现有语料里**都已存在**（`skill.md` 明确记录这套提取流程），所以 v2 的 `architecture` 字段准确率可以做到 100%，不需要概率模型。

### 3.5 性能证据语料（现成的，10,627 条）

- 解析目标：`<op>_log.txt`（格式 `SIZE:Ref: x MFlops y ms | Migration: ... | Speedup:z x => pass`），字段直接映射为 evidence。
- 聚合口径（写死在 `evidence.py`，不随实验改）：只取 `size ≥ 64`（排除启动噪声）、`=> pass` 记录、几何平均；同时存 `median/min/max/n_points`。
- 实测样例（本次统计，尺寸 64–200）：

| 算子 | n_points | geomean | median | min | max | 解读 |
|---|---|---|---|---|---|---|
| dgemm（16_dgemm_op5） | 137 | **2.044** | 2.07 | 1.55 | 3.39 | 向量化收益明显 |
| dtrmm（37_dtrmm_op1） | 137 | 1.392 | 1.35 | 1.16 | 2.05 | 中等收益 |
| daxpy（13_daxpy_op） | 137 | 1.211 | 1.21 | 1.01 | 1.49 | 访存受限，收益有限 |
| dnrm2（22_dnrm2_op） | 137 | **0.589** | 0.60 | 0.48 | 0.81 | **负例**：迁移后更慢 |
| idamax（41_idamax_op） | 137 | **0.187** | 0.18 | 0.15 | 2.20 | **强负例**：约 5× 变慢 |

- 这些数字的三个用途：① 作为 `PerformanceEvidence` 的初始内容（`confidence≈0.35`，标 `rerun_needed`）；② 负例直接支撑 G6（"失败案例"有真实来源）；③ 在论文里作为"知识库已有 operator 级证据"的说明，但**不能**当作"策略级消融"的结论（§6.4 会重新做受控实验）。

> **解读必须谨慎（否则就是另一种幻觉）**：这些日志的 `Ref` 是链接进来的 OpenBLAS 库实现（`_command.txt` 可见链接 `libopenblas_riscv64_zvl256bp_rvv-*.a`），`Migration` 是抽取/改造后的实现；两者差异**不是单策略消融**，因此 2.04× 只能读作"这条实现路径在该环境下的整体表现"，不能归因给某一条策略；负例（idamax 0.187×）同理只能读作"这条迁移路径变慢了"。它足以证明"失败/负例真实存在"（G6 所需），但不足以证明"某策略无效"。真正的策略级证据要靠 W7–W9 的受控生成实验。

- 噪声处理：QEMU 单次运行、无重复、小尺寸受计时器分辨率影响 → **W7 起所有进入论文的数字必须用统一 harness 重跑 3 次取中位数**，旧日志只作线索。

### 3.6 要不要加 GPU 源？——不加（明确回答）

| 维度 | 加 GPU 的收益 | 加 GPU 的成本 |
|---|---|---|
| 新颖性 | 能说"跨 CPU/GPU" | 需要新 schema（occupancy/shared memory/tensor core/warp）、新验证环境、新生成提示 |
| 工作量 | — | ≥6 周（约占剩余工期 1/3），且 GPU 资源未知 |
| 论文必要性 | 低：用 **RVV ↔ x86 两个 CPU 架构**已足够支撑"跨架构"论点 | — |

**结论**：MVP 与论文主体都用 RISC-V + x86 两个架构；GPU 只在 future work 一句带过。若导师坚持，最早在 W10 用 Triton 教程里的 matmul/softmax 做**只读**对照（不建图），不进入主实验。

| S2 | 同一算子的 `_k.c` 与 `_k_rvv.c`（以及接口层 C/RVV 对） | `diffs.jsonl`（变换三元组） | `build/s2_diff.py`（§4.3） | 0 | 15 min |
| S3 | 每个算子的全部 diff + 算子上下文 | `strategies_raw.jsonl`（策略/参数/条件/模板草案） | `build/s3_llm.py` + `prompts/s3_extract.yaml` | **45 次** | 20–40 min |
| S4 | 原始策略 + 词表 | 规范化后的策略/别名/合并关系 | `build/s4_normalize.py` + 词表映射 + 簇内 LLM 判定 | ≤45 次（只在候选簇内） | 20 min |
| S5 | `*_log.txt` + `_<op>_dgc.c` | `evidence.jsonl`（含负例） | `build/s5_evidence.py` | 0 | 5 min |
| S6 | 全部 JSONL | 通过校验的 `nodes.jsonl` / `edges.jsonl` / `manifest.json` | `build/s6_validate.py` + `schema/validate.py` | 0 | 5 min |

**设计要点**：LLM 只在 S3/S4 出现，且**只负责语义命名与解释**；所有结构事实（架构、dtype、循环深度、参数值、性能数字、行号）都由规则或日志产生。这是与 v1（三层 LLM 全包、数字靠硬编码）最本质的区别。

**关于"分几层 Agent"（任务原问题，这里直接回答）**：本方案**不做多层 Agent**，只保留 1 个 LLM 调用点（S3）+ 1 个可选判别点（S4）。理由有三：
1. 现有 `workflow.py` 的 algorithm/code/instruction 三层是**串行三次调用**（`workflow.py:61-65`），三层之间没有信息增量——同一段代码让 LLM 分三次看，产出的策略高度重叠（数据里 206 条策略按 `related_patterns` 去重后只剩 45 个策略簇，说明重复率极高）；
2. 每多一层 Agent 就多一次格式失败风险与成本，而对硕士工期来说，**可靠的规则抽取 + 一次结构化 LLM** 比"多层 Agent 编排"更划算；
3. 更重要的是：三层 Agent 的"层级"（算法/代码/指令）已经被 `level` 字段保留为**标签**，不需要用多个 Agent 去实现——标签是知识，Agent 是实现手段。
若导师坚持"多层次 Agent"的表述，可以这样落地（成本 +1 天）：在每个算子的 S3 内部按 `level` 分三次短调用（algorithm/code/instruction 各一次，每次只给该层相关的 diff），仍然是同一 schema、同一缓存，只是把一次长上下文拆成三次定向调用——这属于**工程可选项**，不改变数据结构。

### 4.3 S2 差分抽取（本方案的核心抽取创新：**不用 LLM 自由发挥，用配对差分**）

同一算子的 `generic C` 与 `RVV C` 是**同一算法的两个实现**，它们的差异就是一条"优化策略实例"——这比让 LLM 看单版本代码去"猜"策略要可靠得多。

```python
# build/s2_diff.py（伪代码）
DELTA_RULES = [
  ("vectorize",   lambda d: d.new_intrinsics and not d.old_intrinsics),
  ("vectorize",   lambda d: d.new_vec_acc > 0 and d.old_vec_acc == 0),
  ("unroll",      lambda d: d.new_k_den != d.old_k_den),          # bk/4 -> bk/8
  ("blocking",    lambda d: d.new_n_acc != d.old_n_acc),          # 4 标量 -> 8 向量
  ("tail_mask",   lambda d: d.new_mask_ops and not d.old_mask_ops),
  ("lmul_tuning", lambda d: d.new_lmul != d.old_lmul),
  ("reorder",     lambda d: d.loop_order_changed),
]

def diff_extract(op_dir):
    for pair in pair_variants(op_dir):          # (generic, rvv) 或 (C 接口, RVV 接口)
        old = parse_impl(pair.generic)          # 循环树、累加器、intrinsic、常量
        new = parse_impl(pair.rvv)
        delta = {
            "include_added":   set(new.includes) - set(old.includes),
            "intrinsics_new":  sorted(new.intrinsics),
            "acc_old":         old.accumulators,       # {"n": 4, "kind": "scalar"}
            "acc_new":         new.accumulators,       # {"n": 8, "kind": "vector", "sew":64, "lmul":2}
            "k_unroll_old":    old.k_den,              # 4
            "k_unroll_new":    new.k_den,              # 8
            "tail_old":        old.has_tail, "tail_new": new.has_tail,
            "loop_order_changed": old.loop_order != new.loop_order,
        }
        actions = [name for name, pred in DELTA_RULES if pred(DeltaView(delta))]
        if not actions:
            continue
        yield {  # 一条"变换实例"，还不是最终策略（S3 负责命名与归类）
            "op": op_dir.name, "variant_pair": [pair.generic.path, pair.rvv.path],
            "before_anchor": old.hot_loop_span, "after_anchor": new.hot_loop_span,
            "delta": delta, "actions": actions,
            "params": infer_params(delta),   # reg_block_n=8, k_unroll=8, lmul=2, sew=64
            "provenance": pair.artifact_ids,
        }
```

**实际输出示例**（dgemm，来自真实文件 `dgemm_k.c` vs `dgemm_k_rvv.c`）：

### 4.5 S4 规范化与对齐（两阶段，阈值必须校准）

```

  "SIMD 向量化"/"向量化"/"RVV 向量化" → family=SIMD向量指令, action=vectorize
  "循环展开"/"loop unrolling"/"unroll k by 4" → family=循环展开, action=unroll
  ——词表在 schema/vocab.yaml，新增别名需 review（避免 v1 那种 LLM 自由命名）

  候选对 = 同 (family, action, stage, level) 且 name Jaccard ≥ 0.4
  相似分 = 0.4*name_sim + 0.4*desc_embedding_cos + 0.2*param_overlap
  自动合并：sim ≥ 0.90（且参数方案兼容）
  LLM 判定：0.75 ≤ sim < 0.90（每簇一次，输出 {merge: bool, reason, confidence}）
```

### 4.6 S5 证据解析（把 10,627 条日志变成可查询证据）

```python
# build/s5_evidence.py（伪代码）
PAT = re.compile(r"^\s*(\d+):Ref:\s+([\d.]+)\s*MFlops\s+([\d.]+)\s*ms\s*\|\s*Migration:\s+([\d.]+)MFlops\s+([\d.]+)\s*ms\s*\|\s*Speedup:\s*([\d.]+)x\s*=>\s*(\w+)")

def parse_log(path, op, platform, baseline, protocol):
    rows = [m.groups() for line in open(path) if (m := PAT.match(line))]
    ok = [r for r in rows if r[6] == "pass" and int(r[0]) >= 64]
    if not ok:
        return [Evidence(op=op, metric="pass_rate", value=0.0, ...)]
    sp = [float(r[5]) for r in ok]
    return [
      Evidence(id=f"ev:{op}:geomean", metric="speedup", value=geomean(sp),
               aggregation="geo_mean", workload={...}, platform_id=platform,
               baseline=baseline, protocol=protocol, raw_ref=path,
               confidence=0.35, rerun_needed=True),
      Evidence(id=f"ev:{op}:pass_rate", metric="pass_rate",
               value=len(ok)/len(rows), aggregation="ratio", ...),
      *[FailureCase(op=op, size=int(r[0]), speedup=float(r[5]))
        for r in rows if float(r[5]) < 0.9],   # 负例：进 P2 实体
    ]
```

### 5.1 选型对照（结论：文件/SQLite 真源 + NetworkX 图 + 可插拔向量索引）

### 5.4 检索算法（可解释打分 + 硬约束过滤 + 图扩展）

**输入**：用户代码（C/C++，可能含 BLAS 调用）+ `HardwareProfile`（`lscpu` 自动生成）。
**输出**：`StrategyPack`（≤6 条策略 + 模板 + 参数 + 证据 + 溯源）。

#### 五步流程

```
S1 查询分析（1 次 LLM + 确定性规则）
    · 函数签名/被调函数 → 映射到 Operator（如 dgemm_ → gemm, double）
    · LLM 输出 pattern 列表（只能选闭集 id，带 confidence 与代码区间）
    · 静态规则抽 characteristics（同 §4.2：dtype/loop_depth/stride/alignment/tail）

S2 候选生成（4 通道，不排序，先求全）
    通道A 精确 pattern：pattern → PATTERN_OPTIMIZED_BY → strategies
    通道B 条件命中：strategy.APPLIES_WHEN 谓词被 characteristics 满足 → strategies
    通道C 语义：把 query 的 pattern 描述 + 代码特征拼成文本 → embedding → top-k strategies
    通道D 图扩展：A/B 命中策略的 GENERALIZES 上行（d≤2）、COMPOSES_WITH 邻居（d=1）

S3 硬过滤（不过滤就没有"结构化"的价值）
    · ISA：strategy.REQUIRES_ISA.hard=true 且 target profile 不支持 → 丢弃
    · dtype：APPLIES_WHEN.hard=true 且 dtype 不匹配 → 丢弃
    · 条件互斥：CONFLICTS_WITH 已选策略 → 标记待消解
    · status=rejected → 丢弃

S4 打分（每一项都可在结果里展开，便于离线和人工审查）
    match_p = Σ_{p∈P_code} w(p)·conf(p)·[p 被策略覆盖] / Σ w(p)        # 计算流程覆盖率
    fit_c   = Σ_{c∈C_satisfied} weight_c / Σ_{c∈C_all}                  # 软条件满足度
    hw      = 1.0 if 硬约束全过 else 0 ；+ 0.5·fit(UARCH fit=ideal|good)
    ev      = clamp(log1p(Σ支持证据的归一化收益) / log1p(8), 0, 1)
              − 0.5·(contradicts 数量归一化)
    sup     = min(1, support_count/5)                                   # 知识支撑度
    tr      = 1 − 0.30·[证据平台≠目标平台] − 0.15·[证据 scope=operator]
    Score   = 0.35·match_p + 0.20·fit_c + 0.15·hw + 0.20·ev + 0.10·sup − 0.15·tr_penalty
```

> 与作者 PPT 里 `Score_core = |S_core∩P_code|/|P_code|`、`Score_total = Score_core + W_context·Score_context`（`ppt_kgmoshi.txt` Slide 14）的关系：`match_p` 就是它的加权版（权重全为 1 时完全等价），`fit_c`/`hw`/`ev`/`sup` 就是把"上下文分"拆成可核查的四项。**保留原公式的解释，补上可计算性**。

#### 伪代码

```python
# retrieval/retrieve.py
def retrieve(code: str, profile: HardwareProfile, top_k: int = 6) -> StrategyPack:
    q = analyze_query(code)                       # 1 次 LLM + 规则；返回 op/patterns/chars
    if q.operator is None:
        return StrategyPack.empty(reason="无法识别算子，仅返回通用策略")
    cand: dict[str, Candidate] = {}

    # 通道 A：精确 pattern
    for p in q.patterns:                          # [{"id","conf"}, ...]
        for e in graph.out_edges(f"pat:{p.id}", "PATTERN_OPTIMIZED_BY"):
            cand.setdefault(e.tail, Candidate()).add("pattern", p.id, p.conf, e.attrs["support"])

    # 通道 B：条件命中
    for s in graph.nodes_of_type("OptimizationStrategy"):
        ok, hard_fail = eval_conditions(s, q.chars)      # 谓词求值（§2.3 R6）
        if hard_fail: continue
        if ok > 0:
            cand.setdefault(s.id, Candidate()).add("condition", ok, 1.0, s.support_count)

    # 通道 C：语义 top-k
    vec = embed(q.pattern_text + q.char_text)
    for hit in vector_index.search(vec, limit=30):
        cand.setdefault(hit.id, Candidate()).add("semantic", hit.score, 0.6, 0.0)

    # 通道 D：图扩展
    for sid in list(cand):
        for e in graph.out_edges(sid, "STRATEGY_GENERALIZES"):
            cand.setdefault(e.tail, Candidate()).add("generalizes", 0.7, 0.4, 0.0)
        for e in graph.edges_both(sid, "STRATEGY_COMPOSES_WITH"):
            other = e.tail if e.head == sid else e.head
            cand.setdefault(other, Candidate()).add("compose", 0.6, 0.4, 0.0)

    # 硬过滤
    cand = {k: v for k, v in cand.items() if hard_constraints_ok(k, q, profile)}

    # 打分
    scored = []
    for sid, c in cand.items():
        s = graph.node(sid)
        parts = {
            "match_p": pattern_coverage(s, q.patterns),
            "fit_c":  condition_fit(s, q.chars),
            "hw":     hardware_fit(s, profile),
            "ev":     evidence_score(s) - 0.5 * contradiction_score(s),
            "sup":    min(1.0, s.support_count / 5),
        }
        tr_pen = transfer_penalty(s, profile)
        total = (0.35*parts["match_p"] + 0.20*parts["fit_c"] + 0.15*parts["hw"]
                 + 0.20*parts["ev"] + 0.10*parts["sup"] - 0.15*tr_pen)
        scored.append(Scored(sid, total, parts, c.channels))
    scored.sort(key=lambda x: -x.total)

    # 贪心选择：去同族重复 + 冲突消解 + 资源预算
    chosen, used_family, register_budget = [], set(), 0
    for item in scored:
        s = graph.node(item.sid)
        if (s.family, s.action) in used_family:            # 同族同动作只留最高分
            continue
        if any(graph.has_edge(item.sid, c.id, "STRATEGY_CONFLICTS_WITH") for c in chosen):
            item.note = "conflict_dropped"; continue
        register_budget += s.estimate_registers(profile)   # 由参数推算，超预算则降级
        if register_budget > profile.num_vector_regs * 0.8:
            item.note = "register_budget_exceeded"; continue
        chosen.append(item); used_family.add((s.family, s.action))
        if len(chosen) >= top_k: break

    return assemble_pack(chosen, q, profile)      # 按 stage 排序 + 填模板槽位 + 附证据
```

**可解释性**：`StrategyPack` 里每条策略都带 `score_breakdown` 与 `why_selected`（命中的 pattern、满足的条件、引用的证据）。这既是论文里的可解释性卖点，也是调试工具。

### 5.5 冲突消解与组合（比 v1 多出来的东西）

1. **资源预算**：寄存器分块类策略按 `num_vector_regs` 估算占用（`reg_block_n × k_unroll` 个活跃向量），超过 80% 就丢弃低分项——这条规则直接来自 §2.6 的 `par:lmul/reg_block_n` 与 hardware 参数，**是 KG 相对文本 RAG 的独有推理**。
2. **同族去重**：`(family, action)` 相同的策略只保留最高分（避免"循环展开×4"和"循环展开×8"同时注入）。
3. **冲突边**：`STRATEGY_CONFLICTS_WITH` 的 `resource` 字段用来解释"为什么不能同时用"（寄存器压力/缓存容量/精度）。
4. **组合顺序**：按 `stage`（prep→transform→core→post）排；同 stage 内按 `COMPOSES_WITH.order`。
5. **不组合**：生成端每轮最多注入 6 条策略、3 个模板，避免 prompt 过长与指令冲突。

### 5.6 如何证明"图结构"相对扁平 RAG 的增量（与本方案设计的绑定）

### 5.7 可复现性与本地化降级方案（针对 DashScope + Milvus 双依赖）

现有代码的**两个外部硬依赖**：`DASHSCOPE_API_KEY`（LLM + embedding，`extractor.py:57-59`）+ Milvus 服务（`localhost:19530`）。这会让"论文复现"变成"你得先有阿里云 key 和一个 Milvus 实例"。降级方案按"接口抽象 + 逐项替换"做，**不改上层业务代码**：

**离线模式的关键设计（也是论文复现包的核心）**：
1. 每次 LLM 调用以 `sha256(model + prompt_version + input)` 为键落盘；`--offline` 时命中缓存直接返回，未命中则报错并列出缺失项（而不是偷偷联网）；
2. `manifest.json` 记录四元组 `{schema, extractor, prompt, model}` + 所有输入文件的 sha256；论文里的每个数字都能定位到 `runs/<timestamp>/`；
3. 一键脚本：`make kg`（重建图谱，纯本地，<5 min）、`make eval`（跑实验；LLM 走缓存则完全离线）、`make check`（schema + 不变量 + 单测）；
4. 降级等价性要在论文里诚实说明：本地 BGE-M3 与 DashScope 的检索指标可能差 1–3 个点，因此**正式实验用主实现、复现包用降级实现并给出差异**。

```python
# eval/run_case.py（伪代码）
def run_case(generated_c: str, op: str, profile: HardwareProfile, workdir: Path) -> CaseResult:
    # 1. 取该算子的真实编译参数（来源：原始 _command.txt，不手写）
    flags = parse_command_txt(op_dir[op] / "_command.txt")     # -march/-mabi/-I/-D...
    # 2. 编译 = 生成文件替换原 _k_rvv.c，其余文件不动
    srcs = [interface, kernel_generic, generated_c, bench_driver, lib.a]
    cp = subprocess.run([cc, *flags, "-DSHOW_TIME", *srcs, "-o", "case.out"], capture_output=True)
    if cp.returncode != 0:
        return CaseResult(status="compile_error", stderr=cp.stderr[-4000:])
    # 3. 运行（QEMU 或 native），driver 自己写 log
    if profile.measure_env == "qemu":
        run = subprocess.run([qemu, "-cpu", "rv64,v=true,vlen=256,vext_spec=v1.0", "case.out"], timeout=600)
    else:
        run = subprocess.run(["case.out"], timeout=600)
    # 4. 解析 log（同 §4.6 的 PAT），三次取中位数
    ev = parse_operator_log(workdir / f"{op}_log.txt")
    return CaseResult(status="ok" if ev.pass_rate == 1.0 else "wrong_result",
                      speedup=ev.geomean, pass_rate=ev.pass_rate, evidence=ev)
```

**测量协议（写进论文 4.1 节，W7 冻结）**：
- 编译：`-O3 -march=... -mabi=lp64d -ffast-math -static`（完全沿用原 `_command.txt`，保证与语料同条件）；
- 正确性：driver 内建的 Ref/Migration 逐元素比较，200 个尺寸全 pass 才计正确；
- 性能：`size ∈ [64, 200]` 几何平均；每 case 重跑 3 次取中位数；记录 min/max；
- 环境：记录 `gcc -v`、QEMU 版本、`lscpu`、日期、GPU/负载（无关进程）；
- 归因：每个 case 同时保存生成的 `knowledge_used`（用了哪些策略/参数），便于做"策略 → 收益"归因分析。

### 6.5 失败反馈如何回写图谱（知识动态更新的最小实现）

| 失败类型 | 判定 | 回写动作 | 是否改 `confidence` |
|---|---|---|---|
| `compile_error` | 编译非 0 | 新增 `FailureCase(symptom=compile_error)` + `STRATEGY_FAILS_ON`；模板 `check_hints` 追加错误模式 | 否 |
| `wrong_result` | 有尺寸 fail | `FailureCase(symptom=wrong_result)`；若定位到尾部/掩码问题 → 模板标 `needs_review` | 否 |
| `perf_regression` | geomean < 0.95×baseline | 新增 `PerformanceEvidence(role=contradicts)`，绑定该策略+平台+参数 | 仅当 3 次重复且 native 测量时：`confidence` 可升到 0.6 |
| `timeout/crash` | 超时或信号 | `FailureCase(symptom=crash)` | 否 |

**闸门（防止图谱被污染）**：
1. 只有满足 `{measured=true, repeats≥3, 协议固定}` 的证据才允许 `confidence ≥ 0.6`；
2. LLM 事后归因（"失败是因为策略 X 不适用"）只能生成 `status=inferred` 的候选边，**必须**经过一次实验或人工确认才转正（`status=verified`）；
3. 每轮回写生成新快照（`snapshot_*`），旧快照只读——保证论文数字可追溯到当时的知识库版本。
