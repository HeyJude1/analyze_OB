# 19 自建 OpOptBench：可以，但要按"基准"来做，不是"拍脑袋数据集"

> 2026-11-15｜Lead｜回答："你的意思是我自建数据集？这样可以吗？"
> **一句话：可以，而且是必要的；但论文里要叫"可执行基准（benchmark）"，并给出构造协议、质量评估、防泄漏和可复现证据。**
> 自建 benchmark 在软件工程/编译器/LLM 代码生成里是常态（SWE-bench、KernelBench、TritonBench 都是构造出来的），评审不会因为"自建"扣分，扣分的是"自建 + 自评 + 只挑赢的"。

---

## 1. 为什么必须自建：现有 benchmark 不匹配

| Benchmark | 任务/语言 | 硬件 | 为什么不能直接用 |
|---|---|---|---|
| KernelBench | PyTorch → CUDA/Triton kernel | NVIDIA GPU | 不是 C/OpenBLAS，不是 RISC-V |
| TritonBench | Triton 算子 | GPU | 同上 |
| KernelBench-Verified | 同上，修 reward hacking | GPU | 同上 |
| PolyBench/C | C 小程序（gemm 等） | CPU | 没有"专家优化实现"作参照，也没有多架构知识 |
| OpenBLAS 自带 test/benchmark | BLAS 调用 | CPU | 只测库本身，不是"给 LLM 的生成任务" |

你的课题是 **C 语言 + OpenBLAS 多架构 kernel + RISC-V/x86 真机**，公开 benchmark 里没有对应物。所以：
- 从 **公开源码**（OpenBLAS v0.3.27，BSD-3）构造任务，是合理且常见的做法；
- 你的贡献不是"发明一个数据集"，而是"**为多架构算子优化构造一个可执行、可复现的评测基准**"，它是方法验证的载体，不是主创新点。

---

## 2. 自建基准的 7 条"合法化"要求

### 2.1 来源公开、版本固定、许可清楚

- 固定 `OpenBLAS v0.3.27`（commit hash + tarball sha256）；
- 保留 `LICENSE`/`NOTICE`，在论文与仓库写清来源；
- 每个输入文件记录 `path + sha256 + 行号`（你的 KG 已经这么做）。

### 2.2 任务构造规则先写死，不能"看结果挑任务"

- 选 12/14 个算子：按 BLAS 层级（L1/L2/L3）预先选，覆盖向量化/访存/分块三类，**不是挑方法赢的**；
- 每个算子取 `generic.c` 作为输入，优化实现只作为 P1 上界与知识来源，**不进入 prompt**；
- 尺寸集合先定（如 1024/16384/1048576），不因结果改；
- S1（进 KG）/ S2（留出）在实验前固定，S2 不参与建图、不参与调参。

### 2.3 隐藏测试独立、容差独立

- D1 随机、D2 不规则尺寸、D3 参数边界、D4 数值极端；
- 容差由"参考 vs 参考"自校准（η0 的 10×），不按生成结果调；
- 测试代码不放进 prompt；S2 的测试更不暴露。

### 2.4 上界/下界与公平对照

- C0 输入 `-O2`、C1 编译器 `-O3`、P1 OpenBLAS 专家实现；
- B0/B1/B2/B3 同 LLM、同 token 预算、同尝试次数；
- 外部 AI 方法（KernelBlaster/Xe-Forge/QiMeng）只做方法对照，不硬拼数字（架构/语言不同）。

### 2.5 防泄漏（最容易被问）

- S2 算子不进入 KG、检索库、prompt；
- 不把专家实现/隐藏测试喂给 LLM；
- 版本/时间隔离：知识只来自目标版本之前已合并的实现（至少不与测试任务同文件）；
- 每次 run 保存 `manifest` + 检索 trace + 输入快照（你的可复现包已经做到）。

### 2.6 基准质量评估（不是"建完就用"）

至少报告 5 个数：

| 维度 | 指标 | 目的 |
|---|---|---|
| **覆盖** | 算子数 × 架构 × 尺寸 × 层级 | 说明不是只挑几个 |
| **难度分布** | C1 vs P1 差距（如 ≥2× 的任务占比） | 任务不能全易/全难 |
| **区分度** | B0 vs B3 的 FCR/性能差；不同 seed 方差 | 能区分方法 |
| **稳定性** | 同一代码 20 次计时 CV；参考 vs 参考 η0 | 计时可信 |
| **正确性** | 隐藏测试覆盖分支；参考实现自检 | 测试可信 |

如果某维度不达标，就在论文里如实写"基准的局限"，不要藏。

### 2.7 可复现

- 每个 run：`results.jsonl` + 报告 md + `artifacts/<run_id>/repro/`（输入/硬件/检索链/每轮迭代/最终算子）；
- 一键重建：`kg_agent` 离线 build（manifest 含 112 个输入 sha256，两次 build 字节级一致）；
- 环境版本：gcc/qemu/OS 写进 `env.txt`。

## 3. 论文里怎么写（可直接用）

### 3.1 贡献表述（放"研究内容"第 3 条，不抢主创新）

> "构建了面向多架构算子优化的可执行基准 **OpOptBench-12**：以 OpenBLAS v0.3.27 的通用实现为输入、架构优化实现为专家参照，包含 12 个算子 × 2 类硬件 × 3 个尺寸的任务实例、D1–D4 隐藏测试与双平台计时协议，并提供可复现包。"

### 3.2 放在哪一节

- 第 4 章 §4.1 "评测基准与任务构造"（或第 5 章 §5.1 "实验设置"）；
- 内容包括：任务定义、来源与许可、构造流程、隐藏测试、split、统计口径、质量评估表；
- 不要写"我发明了一个数据集"，写"**构造并验证了一个基准**"。

### 3.3 基准质量表（论文表 5-1 模板）

| 项 | 数值/说明 |
|---|---|
| 来源 | OpenBLAS v0.3.27（commit/sha256） |
| 算子 | 12（L1×6、L2×3、L3×3） |
| 架构 | x86 AVX2/AVX512、ARM NEON/SVE、RISC-V RVV（知识）；性能测 x86+RVV |
| 任务实例 | 12 × 3 尺寸 × 2 平台 = 72（E3/E4 子集） |
| 隐藏测试 | D1–D4，参考 vs 参考自校准 |
| 难度 | C1/P1 差距 ≥2× 的任务占比 X% |
| 区分度 | B0 vs B3 的 FCR 差 Δ |
| 稳定性 | 计时 CV ≤3%，η0 ≤1e-10 |
| 泄漏控制 | S2 不进 KG；manifest 可审计 |

## 4. 导师/评审可能问的 5 个问题（准备答案）

**Q1：自己建数据集，是不是自说自话？**
> "不是数据集，是 benchmark。来源是公开 OpenBLAS，构造规则先写死，S2 留出，隐藏测试独立，所有 run 可复现；SWE-bench/KernelBench 也都是从公开仓库构造的。"

**Q2：为什么不用现成的 KernelBench/TritonBench？**
> "它们是 GPU/PyTorch/Triton，我是 C + OpenBLAS + RISC-V/x86；任务语言、硬件、专家参照都不同。PolyBench 没有专家优化实现，OpenBLAS 自带 benchmark 不是给 LLM 的生成任务。"

**Q3：12 个算子会不会太少？**
> "12 个覆盖 L1/L2/L3 三类优化；每个算子 × 3 尺寸 × 2 平台 × 3 seeds，E3/E4 合计约 1000 次生成/编译/运行；再用 S2 留出 + 消融补外部效度。少而深，不是少而浅。"

**Q4：怎么保证不是你调出来的？**
> "S1/S2 实验前固定；S2 不参与建图/调参；B2/B3 同 token 预算；3 seeds + 配对检验；负结果也报告（比如 B4 目前只有成本没有正确性增量）。"

**Q5：基准本身怎么证明可信？**
> "报告覆盖、难度分布、区分度、计时稳定性、参考自校准 5 项；每个 run 有 manifest + 输入快照 + 检索 trace；代码/脚本可复现。"

## 5. 如果导师仍坚持"用公开数据集"

可以退一步，但不要换赛道：

1. **主实验**仍用 OpOptBench（因为任务匹配）；
2. **补充外部效度**：从 **BLIS** 或 **ARM Optimized Routines** 再抽 2–4 个 kernel，做"held-out source"小实验，证明不是只对 OpenBLAS 过拟合；
3. **引用公开 benchmark**（KernelBench/TritonBench）做 Related Work 与指标对齐（fast_p、Pass@1 等），说明"我们不是重复造轮子，而是补 RISC-V/C 的空白"；
4. 如果时间不够，第 2 条可以只做 1 个 kernel 的案例，写进"外部效度"讨论。

---

## 6. 一句话总结

**自建可以，而且必须；关键是把它做成"有协议、有质量评估、有防泄漏、可复现"的 benchmark，而不是"我挑了几个算子跑出好结果"。**
你现在的 `OpOptBench-12 + E09 可复现包 + 24-cell 网格` 已经具备这个雏形；下一步把"基准质量评估表"补齐（覆盖/难度/区分度/稳定性/正确性），这一章就站得住。
