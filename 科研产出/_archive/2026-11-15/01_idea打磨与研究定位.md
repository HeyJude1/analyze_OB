## 1. 判决：「没有 baseline」是伪问题，但下面这个才是真问题

**先纠正一个事实性误判。** 你不需要"前人做过同一个 KG"，你需要的是"同任务、同预算的对照"。四层基线现在就能落地：

| 层 | 可用基线 | 现状 |
|---|---|---|
| L1 任务/性能 | 参考实现（Morph `best_sequential_runtime`）、OpenBLAS 该架构实现、`-O3 -march=native` 自动向量化版本 | 前两者已有；**第三个还没被当作基线**（它往往能吃掉 naive 实现 10× 以上的加速，不设它会严重高估你的贡献） |
| L2 方法对照 | B0 无知识 / B1 仅硬件信息 / B2 扁平文本 RAG / B3 图谱条件感知注入 | **B0 与 B1 在 Morph 里已经做过**（README 实验 2/3，282 条），**B2 缺，这是唯一的缺口** |
| L3 传统自动优化 | Ansor / AutoTVM / OpenTuner 的移植版本 | 可作为"非 LLM 上限"引用，不必复现 |
| L4 近期 LLM 系统 | MARCO（web-search 知识注入）、PRAGMA（profile 反馈）、QiMeng-GEMM/Attention/Kernel | 机制可复现对照，规模不必对齐 |

**所以"没有 baseline"是伪问题。** 依据很硬：KernelBench 给了 250 个任务的 `fast_p` 协议；KernelBench-Verified（2026-06）进一步给出 TF32 真实基线 + 隐藏分布 + 显存指标；PRAGMA 在 KernelBench 上做 profile 引导并报 2.81×/2.30×；MARCO 用 web-search 做"实时知识注入"。你想做的那件事，**对照物在论文里都写好了**。

**但真问题在这里**，而且比"没 baseline"更致命：

1. **"知识质量"没有公认真值（ground truth）**。你用 LLM 建图、用 LLM 对齐、再用 LLM 生成——全链路没有一处可被独立核验。这是领域开放问题，不是你的锅，但你必须自建一个小规模 gold 子集，否则"图谱质量高"这句话无法进入论文。
2. **"跨架构策略迁移"没有任何基准、协议或指标**。没有人在公开数据上系统回答过：从 x86 学到的"循环展开 4 次""预取到 L1"，到 ARM NEON 或 RISC-V RVV 上还成不成立。**这才是你能把"没有 baseline"转化成贡献的位置**——不是"我补一个 baseline"，而是"**我给这个空白领域定义第一个基线**"。

> **一句话**：不要再纠结"没人可比"。你的处境是"**没人比过，所以你来定赛道**"，而不是"没人可比，所以我做不了"。

### 三条最致命的，展开说

**（1）F2+F1：你的题目承诺了一个你从没测过的量。**
"高性能"在本文语境里只能是三个可测量：
①相对**本机参考实现**的加速比；②相对 **OpenBLAS 同架构实现**的性能占比（QiMeng-GEMM 用 211% of OpenBLAS 这种说法就是这么来的）；③相对**同 LLM 无知识基线**的增量。
现在这三个一个都没有。答辩老师第一问必然是"加速比多少"，你答"构建成功率 76.6%"，就结束了。

**（2）F3：你以为的"KG 增强生成"目前只是一句叙事。**
你有两台仪器：KG（抽取/对齐/检索/57 簇）和生成测量台（Morph：180 prompts + 9 算子 248 策略变体 + build/run/runtime 驱动 + `[OPT_ANNOT]` 策略注解）。但**它们之间没有电缆**。把 KG 检索接到 prompt 上是 0.5–0.8 人月的事，可它是所有后续实验的关键路径——**必须在 12 月前完成，否则后面全部坍塌**。

**（3）F4：真正的时间黑洞不是"写代码"，是"跑实验+写论文"。**
你花了一年把系统建到 80%，这是好事；但论文不会因为系统 80% 就自动出现。剩下 4.5 人月里，**至少 2.5 人月必须留给实验与写作**，留给"再加功能"的预算是 **0**。

## 3. 模拟评审会：4 个角色 × 5 条最尖锐意见（含你该怎么回应）

### 3.1 HPC 系统审稿人（目标：SC/ICS/IPDPS/Euro-Par 或中文 EI）

1. **"你和谁比加速比？和 naive C 比 10× 没有意义，`-O3` 就吃掉一大半；和 OpenBLAS 比你必输。"**
   → 回应：三级报告——相对参考实现、相对 `-O3 -march=native` 编译版、相对 OpenBLAS 的**百分比**；**不声称超过 OpenBLAS**（你 PPT 里"聚焦自动优化而非超过 OpenBLAS"的判断是对的，写进论文）。
2. **"只有 4 个算子、20 个文件、57 个策略，还想给一般性结论？"**
   → 回应：扩到 3 架构 × 4–6 算子并把 cx_operator_tool 的 RVV/SVE 语料纳入；结论限定在"BLAS 类稠密算子"，明确不外推。
3. **"性能测量没有统计功效：单次运行、无重复、无置信区间。"**
   → 回应：每配置 ≥10 次重复取中位数 + IQR；固定容器镜像/编译器版本/CPU 亲和性；配对 Wilcoxon + bootstrap CI。
4. **"你的'知识'就是 OpenBLAS 源码本身，LLM 不看你图谱也能说出来。"**
   → 回应：这正是 B2（扁平 RAG，同 token 同知识量）存在的意义；并且引入"组合/条件冲突"任务，这类任务扁平 top-k 检索天然做不好。
5. **"迁移到 RISC-V 你在 QEMU 上测的加速比？"**
   → 回应：**主动承认**——QEMU 只用于功能正确性；性能指标分两层（真机实测 / 静态代理：向量化宽度、FMA 使用、预取指令、展开因子、寄存器压力估计），并单列"指标可信度"一节。

### 3.2 KG / IR 审稿人

1. **"两阶段实体对齐（embedding 粗筛 + LLM 判别）是标准实体消歧范式，不是创新。"**
   → 回应：完全同意，**不作为创新点**，只作为管线组件 + 一个消融（对齐 on/off 对检索与生成的影响）。
2. **"没有 gold KG，凭什么说图谱质量高？"**
   → 回应：建 150 条策略–条件对 gold 子集，2 人独立标注报 Cohen's kappa；报实体级/关系级 P/R、schema 合规率、**来源可追溯率**（每条知识能回指源文件行号，这是你比 MARCO 的 web search 强的地方，一定要做）。
3. **"图结构在你的下游到底用在哪？你的检索是『模式→相似模式→策略』，本质是 2-hop join，向量库也能做。"**
   → 回应：把图的价值限定在三个**离不开关系**的操作：适用条件谓词过滤、策略冲突消解、跨架构策略替代（`SIMILAR_TO` 的 `difference_description="仅硬件平台不同"` 已在你的 3KG 设计里）。并用扁平 RAG 做对照证明增量只出现在这三类任务上。
4. **"Milvus + 图双存储的一致性、版控、更新协议没交代。"**
   → 回应：单机 SQLite/Postgres 存三元组 + 导出图，schema 版本化，diff 审计；Milvus 仅作索引，可重建。
5. **"'知识涌现/自动发现新策略'呢？"**
   → 回应：**删掉这个说法**。7 个月内无法验证；改为"策略组合推荐"这一可验证的弱版本。

### 3.3 软件工程 / LLM 审稿人

1. **"这就是 RAG + prompt engineering，提升可能只来自 prompt 更长。"**
   → 回应：B2 与 token 预算严格对齐（把图谱内容文本化到相同 token 数），相同重试次数、相同温度/种子。
2. **"你的 pipeline 有生成–验证–重试，性能提升可能来自重试次数。"**
   → 回应：knowledge × retry 的 2×2 设计，固定 K 次重试。
3. **"可复现性：闭源 API 版本会漂。"**
   → 回应：主实验用两个锚点（固定版本 API + 一个本地开源 7B），发布代码/数据/prompt/随机种子，记录模型版本日期。
4. **"KernelBench-Verified 已经证明：在 TF32 真实基线下，最好的模型几何均值只有 0.88×，28% 的 kernel 还更费显存。你凭什么相信你的加速比？"**
   → 回应：采用 verified 协议（真实基线、隐藏输入分布、内存指标、禁止 hardcode）；报告 fast_p 与显存开销；把"低于 1×"如实写出来——负结果比假加速比安全一百倍。
5. **"三个创新点里有两个是方法细节。你真正的 delta 是什么？"**
   → 回应：见 §5 的一句话定位——**delta = 首次把"策略可迁移性"从经验判断变成可测量量，并给出条件边界**。

### 3.4 统计方法审稿人

1. **"n=20 任务、3 个 seed 还想做检验？"** → 回应：≥100 个任务实例；配对设计（同任务同模型）；bootstrap CI + 非参数检验 + 效应量。
2. **"多模型多任务多条件不做多重比较校正，结论都是 p-hacking。"** → 回应：预注册 1–2 个主假设，其余标为探索性；Holm–Bonferroni；**报告所有条件**，不许只报赢的。
3. **"LLM 输出方差极大，温度 0 也不确定。"** → 回应：每配置 ≥3 次独立采样，报方差分解；固定 seed 并记录。
4. **"加速比是重尾分布，不能用均值。"** → 回应：中位数 + 几何均值 + `fast_p`（p=1.0/1.25/1.5）+ 失败率。
5. **"『策略命中率』是你定义的、还用 LLM 判，循环了。"** → 回应：用**可执行证据**替代主观判断——Morph 已把策略以 `/* [OPT_ANNOT] | Strategy: xxx | Confidence: 0.95 */` 注进生成代码，配合 `objdump`/源码规则自动判定"是否真实现了"，再抽 100 条做 2 人人工校准。

| 失败后果 | 无论结果都能写（负结果=消融表） | 能写，但价值平庸 | **失败可退化为 A**，不白做 |

### 推荐排序：**C ≫ B > A**（理由是决策论，不是口味）

1. **C 的实验矩阵是 A 的超集**：A = {4 条件 × 1 架构 × N 算子}，C = {4 条件 × 3 架构 × N 算子}。做 C 的过程天然产生 A 的全部数据；做 A 却答不了 C。**同样的时间，C 的可发表上限严格高于 A。** 这是支配性选择。
2. **C 的新颖性缺口是真实且可验证的**：QiMeng 系列做的是"硬件知识参与的生成"（单架构族）、HPCTransCompile 做的是"CUDA→多平台代码翻译"（可移植性，非优化策略）、MARCO 做"实时 web 知识注入"（无跨架构）、PRAGMA 做"单平台 profile 反馈"。**没有人系统回答"策略的可迁移性"**。而你的 `3KG设计.md` 里已经有 `TARGETS_HARDWARE(match_score, is_required, alternatives)`、`APPLICABLE_TO(match_conditions)`、`SIMILAR_TO(difference_description="仅硬件平台不同")`——**这些关系就是为这个问题准备的数据结构，KG 不是装饰而是机制**。这一点极其关键：你的 KG 第一次有了"非它不可"的下游用途。
3. **C 的指标最客观、最不容易被质疑**：策略是否被实现（可自动判定）、代码是否正确（可执行）、相对本机参考实现的性能（可测）——三档判定，不依赖"知识质量好不好"这种主观判断。
4. **C 的预算最省**：你已有 `operator_extract/{openblas, openblas_0515, csparse, openDNN, tcx_toolchain}` 的多架构语料、`qemu-riscv64 + riscv-gcc-14.3`、`benchmark_c/`（含 Makefile 与 benchmark 驱动）、`drivers/driver_wrapper.py`（解析 `Time` 与 `BestSequential`）。**跨架构实验的地基已经打好了，缺的是把架构这一维接进 prompt 和 KG。**
5. **B 不该独立做**：B 的人工标注是纯成本，且"数据集论文"在 CCF 体系里很吃亏。**把 B 的协议贡献折叠进 C**（C 本来就产出一套评测协议），一份工作两个卖点。

> **对 A 的最终处理**：不淘汰，**降级为"系统实现与工具"章节（学位论文第 6 章）+ C 的实验对照之一**。你花一年建的系统不是废的，它是 C 的仪器。

## 5. 打磨后的定位（可直接拿去写开题修订说明 / 小论文引言）

### 5.1 一句话定位

> **面向 BLAS 类稠密算子，本文把算子库中的优化策略组织成"计算模式—优化策略—适用条件—硬件约束"的知识图谱，并以"同一策略在 x86 / ARM(SVE) / RISC-V(RVV) 之间能否被正确实现、是否正确、是否更快"为可证伪指标，首次定量刻画大语言模型优化策略的跨架构可迁移性及其边界条件。**

（题目**不需要改**——"基于知识图谱的大语言模型自动生成高性能算子代码方法研究"完全容纳这个定位；按学院规定，重大调整才需重新开题。）

### 5.2 三个研究问题（RQ）

| RQ | 问题 | 可测指标 | 对应章节 |
|---|---|---|---|
| **RQ1** 知识表示与质量 | 从多架构算子库中抽取的"策略—适用条件—硬件约束"知识，其准确性与一致性如何？ | 150 条 gold 子集的 precision/recall、2 人 kappa、跨架构同一策略的合并准确率、来源可追溯率 | 第 3 章 |
| **RQ2** 迁移保真度与增量 | 同一条策略注入后，从源架构迁移到目标架构时被**正确实现**的比例、代码正确率、相对参考实现的性能是多少？相对 B0/B1/**B2 扁平 RAG** 的增量是多少？ | 策略实现保真度、构建/运行/数值正确率、加速比（或静态代理）、fast_p、成本 | 第 4–5 章（主实验） |
| **RQ3** 边界条件与归因 | 哪些策略架构无关（可迁移）、哪些架构特定（不可迁移/负迁移）？失败原因分布是什么？图的硬件谓词能否**预测**迁移成败？ | 可迁移性分层表、失败归因分类（条件不满足/生成能力不足/参数错配）、谓词过滤的预测准确率 | 第 5 章 |

### 5.3 三条可辩护的贡献（按可辩护强度排序）

1. **【主】首个跨架构算子优化策略迁移的受控测量与评测协议**：4 条件 × 3 架构 × 4–6 算子 × 2 模型的嵌套实验矩阵；策略实现保真度的**可自动判定方法**（`[OPT_ANNOT]` 注解 + 静态规则 + 抽检校准）；真机/QEMU 分层指标协议。→ 把"没有 baseline"变成"我定义了 baseline"。
2. **【支撑】硬件感知的算子优化知识图谱 + 条件过滤检索**：≥3 架构语料、带来源溯源与适用条件标注、150 条人工校验；并给出"条件过滤相对无条件检索"的增量证据。（注意：**不把两阶段对齐当创新点**）
3. **【发现】策略可迁移性的分层结论与工程建议**：哪些策略能跨架构、哪些不能、为什么；并据此回答"知识注入应该注入什么"——这条即使结果是负面的也成立，是本文最稳的保险。

### 5.4 明确的"不做什么"（写进论文的 Scope 段，也是你对自己的纪律）

- ❌ **不做"超过 OpenBLAS"的性能竞赛**。只报"相对参考实现"与"相对 OpenBLAS 的百分比"。
- ❌ **不在 QEMU 上声称加速比**。QEMU 只用于功能正确性；性能分"真机实测"与"静态代理"两栏，并写进 Limitations。
- ❌ **不做知识涌现/自动发现新策略**（PPT 里的"动态知识库、知识涌现"删掉或降级为"策略组合推荐"的可验证弱版本）。
- ❌ **不做 CUDA/GPU 全算子生成**。GPU 若环境稳定只做一个对照点；不扩展。
- ❌ **不再新增 schema 关系类型、不再调对齐规则、不再加 Agent 层**（现有 7 实体 12 关系、57 簇已足够；冻结）。
- ❌ **不做大规模微调/预训练**。固定 1 个 API 模型 + 1 个开源模型做复现锚点。
- ❌ **不把"两阶段实体对齐""结构化 Prompt 模板"写成创新点**——它们是工程组件，写进"实现"。

### 5.5 最小可发表单元（MPU）

**一个能立刻投 EI（D 类，满足毕业）的最小闭环：**
- **算子**：4 个（GEMM、AXPY、HEMV、TRMM 或 conv）
- **架构**：x86_64（真机）/ ARM64-SVE-NEON（真机或静态代理）/ RISC-V RVV（QEMU 正确性 + 静态代理）
- **源→目标**：x86→ARM、x86→RISC-V（可选反向）
- **条件**：B0 无知识 / B1 仅硬件信息 / **B2 扁平文本 RAG（新建）** / B3 图谱条件感知注入
- **模型**：qwen-plus（固定版本日期）+ 1 个开源 7B
- **规模**：每格 15–20 个任务实例 × 3 seeds × 2 模型 → 约 2000–3000 次生成（现有 `run-all.py` 可批量，机时约数小时）
- **指标**：构建/运行/数值正确率、策略实现保真度、相对参考实现加速比或静态代理、fast_p、成本
- **人工校验**：150 条策略–条件对（2 人，报 kappa）
- **产出**：8–10 页论文。**这套东西就是 MPU，多一个模块都不要加。**

### 5.6 六模块 → 学位论文章节的收敛映射（向导师解释"内容没缩水"）

| 开题六模块 | 落点 |
|---|---|
| ①算子库预处理 ②三层解析 ③图谱构建 ④对齐融合 | **第 3 章 + 第 6 章（系统实现）** |
| ⑤策略推荐 | **第 4 章**（条件感知检索，RQ2 的方法部分） |
| ⑥结构化 Prompt 生成 | **第 4 章**（与 ⑤ 合并，并接入 Morph） |
| （新增，来自本次打磨）跨架构迁移实验 | **第 5 章**（RQ2/RQ3 主实验） |

六模块收缩为 2.5 章，腾出的篇幅给实验——**这在评审眼里不是缩水，是把"系统说明书"升级成"研究论文"**。
