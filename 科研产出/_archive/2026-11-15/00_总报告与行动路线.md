## 3. 核心判决一：idea 值不值得做？——值得，但三个创新点要重写

### 3.1 判断（三份独立团队文档与 Lead 一致）

- **"KG+LLM 融合"本身已不新**：2025–2026 年至少 4 条线在做"结构化/可检索的优化知识"——Xe-Forge（IntelLabs，curated 硬件约束知识库 + 9 阶段优化，已开源）、KernelBlaster（NVlabs，Persistent CUDA Knowledge Base，KernelBench 1.43/2.50/1.50×，已开源）、QiMeng-Kernel（AAAI 2026，策略与实现解耦）、Leeroopedia（工业界 2.7 万页结构化知识库）。**把"首次/填补空白"写进论文会被当场打掉。**
- **两个创新点直接不成立**：
  - "两阶段实体对齐（向量粗筛 + LLM 判别）"是 2023–2024 年通用做法（你自己的灵感来源 Carta et al. 就是），**没有 HPC 特异性**，只能作为方法章组件 + 一个消融。
  - "多层次 Agent 解析"实质是一次三段式 prompt，没有规划/工具/交互，**称 Agent 属 overclaim**，降级为实现细节。
- **真正可辩护的三条**（团队收敛）：
  1. **实现差异驱动的知识获取**：同一算子的通用 C 实现 vs RVV/优化实现之间的差异，就是"专家做过哪些优化决策"的**弱监督信号**——不需要人工标注全部策略，且可溯源到行号。
  2. **带条件与证据的结构化知识**：策略必须带"适用条件 / 失效条件 / 硬件约束 / 可调参数区间 / 性能证据 / 来源"，让"约束过滤"和"冲突消解"成为 **flat RAG 无法表达**的两种操作。
  3. **跨架构/跨算子的策略可迁移性**：没有人系统回答"x86 上学到的策略，到 ARM/RVV 上还成不成立、边界在哪"。**你手上的多架构 OpenBLAS 语料是别人拿不到的差异化资产。**

### 3.2 打磨后的定位（可直接用于论文引言/答辩）

> 面向 BLAS 类稠密算子，把算子库中隐含的优化策略组织成"**计算流程—优化策略—适用条件—硬件约束—性能证据**"的知识图谱，让 LLM 在生成代码前先"查图"做**条件过滤与冲突消解**；并以"同 LLM、同 token 预算"的受控实验回答：**结构化知识相对扁平文本检索是否带来可测量的增量？这种知识能否跨算子、跨架构迁移？边界条件是什么？**

**题目不必大改**（避免重新开题）：学位论文保留原题，可加副标题"——面向跨架构算子优化知识"；小论文用《基于实现差异挖掘的高性能算子优化知识图谱构建与跨架构代码生成》（`05` 给了 5 个候选与中英文摘要草稿）。

### 3.3 三个研究问题（RQ）

| RQ | 问题 | 指标 | 对应实验 |
|---|---|---|---|
| RQ1 知识质量 | 从多架构算子库抽取的"策略—条件—硬件约束"知识准不准、一致吗？ | 150 条人工金标的 P/R、2 人 κ、对齐 P/R、来源可追溯率 | E2/E3 |
| RQ2 结构增量 | 同内容、同 token 预算下，图结构（条件过滤 + 冲突消解）相对扁平文本 RAG 带来多少增量？ | `R = GM(B3)/GM(B2)`（配对 + bootstrap CI）、FCR、fast_p、EGC、成本 | E1/E3/A1/A3 |
| RQ3 迁移边界 | 哪些策略跨算子/跨架构可迁移，哪些是架构特定？图的硬件谓词能否预测迁移成败？ | 可迁移性分层表、失败归因、谓词预测准确率、T2 策略推荐 R@k/nDCG | E4/E5/E6 |

## 4. 核心判决二："没有 baseline"是伪问题；真问题更值钱

### 4.1 四层 baseline 全部现成（`04` §5 有完整表）

| 层 | 基线 | 说明 |
|---|---|---|
| L0 下界/编译器 | C0 输入代码（`-O2`）、**C1 `-O3 -march=<profile>`**、C2 编译器 + `#pragma omp simd` | **C1 最关键**：不设它，审稿人一句"你的提升只是开了 O3"就否掉 |
| L1 性能参照 | P1 系统 OpenBLAS（固定版本，ST/4T 两口径）、P2 TVM Ansor（限时等预算）、P3 人工改写 | 只作分母/上界，不参与显著性检验 |
| L2 方法学（主对比） | **B0 零样本 / B1 +硬件信息 / B2 扁平文本 RAG（同内容） / B3 完整 KG**；另有 B4 few-shot、B5 扁平 RAG（同预算）、B6 无对齐 KG、B7 去硬件、B8 硬件错配、B9 去条件、B10 随机子图、B11 2-hop、B12 自精炼、B13 完整系统 | **B2/B3 是论文的生死对照**；全部同模型/同 token/同尝试次数。编号以 `04` v2.0 为准 |
| L3 已有系统 | X1 PRAGMA-lite（自实现 profile 反馈循环）、X2 QiMeng-GEMM（代码待核实）、X4 MARCO 机制复刻 | 只复现机制，不硬比数字 |

**公开可复现的强 baseline 已确认**：KernelBlaster（github.com/NVlabs/KernelBlaster，Apache-2.0，带 repro pipeline）、Xe-Forge（github.com/IntelLabs/Xe-Forge）、GEAK（AMD-AGI/GEAK）、TritonBench、KernelBench（ICML 2025）。QiMeng-Kernel 代码"coming soon"；PRAGMA/MARCO 未见公开仓库。**"没有 baseline"的担忧到此可以关闭。**

### 4.2 真问题：没有"评测协议"，而定义协议本身就是贡献

- 你的语料是 OpenBLAS 算子（CPU），不是 KernelBench 的 PyTorch workload（GPU）；没有人在这套语料上比过。**新任务的正常解法 = 自建可复现 benchmark + 三层参照 + 等预算消融**，而不是找一个不存在的 SOTA。
- 评测口径必须按 **KernelBench-Verified（arXiv 2607.16241）** 修正：隐藏测试分布、真实基线、内存开销、防 reward hacking。`04` 已设计 D1–D4 四个隐藏分布（标准随机 / 不规则尺寸 / 参数边界 / 数值极端）。
- **数据泄漏必须主动处理**：LLM 可能"记得"OpenBLAS 源码。`04` 设计了**匿名化对照（E7）**：去掉算子名/BLAS 签名、改函数名变量名，若 KG 方法在匿名化后不掉分而零样本掉分，反而是正面证据。

## 5. 你可能没意识到：性能数据已经在你硬盘里（Lead 实测复算）

`Morph/prompt_test/promptsv{1,2,3}_code_run.csv` 里有 `runtime` 与 `best_sequential_runtime` 两列——**加速比可以直接算**。Lead 的复算（细节与局限见 `07`）：

| 条件 | 配对任务数 | 几何平均加速比 | >1× 占比 |
|---|---|---|---|
| v1 基线（无知识） | 22 | **0.802** | 23% |
| v2 + 基础硬件信息 | 22 | **1.387** | 36% |
| v3 + 硬件信息推导的策略 | 22 | **0.699** | 32% |

- **v2/v1 = 1.73×**（硬件信息有用），**v3/v2 = 0.50×**（把策略直接塞进 prompt 反而更差）。
- 这个"策略注入反而变差"的 pilot 现象，恰好是论文 Introduction 最好的引子：**问题不在知识量，而在知识没有条件、结构与冲突消解。**
- **注意**：三组条件映射需你确认；有效任务仅 22 个、且是 ParEval 类并行编程任务（不是 BLAS 算子），所以只能当 pilot，不能当主结果。**但它证明了一件事：你的仪器能测性能，你缺的只是把对照设计好。**

## 6. 技术方案：12 周最小闭环（不推倒重来）

### 6.1 对现有原型的诊断（`03` 有逐行证据）

现有 7 实体/12 关系能复用约 40%，但有 7 个硬缺口：**硬件只是"教科书名词"没有参数值；性能收益是 LLM 形容词；来源只到文件名；适用条件不可执行；没有实施模板；只有成功知识没有失败；一半关系是死代码（8/12 从未产生实例，`OPTIMIZES_PATTERN` 甚至不在 v2 抽取器里发出）**。更严重：`prompts/`、`config/` 未入库，当前仓库**无法端到端重跑**。

### 6.2 Schema v2（`03` 给了完整表）

- **11 个核心实体**：`Operator`、`ComputationPattern`、`CodeCharacteristic`、`OptimizationStrategy`、**`ImplementationTemplate`（最关键新增，生成端注入接口）**、`TunableParameter`、`ISACapability`、`Microarchitecture`、`HardwareProfile`、**`PerformanceEvidence`（最重要新增，性能数字唯一合法来源）**、`SourceArtifact`（repo+commit+行号）。
- **15 个关系**：`PATTERN_OPTIMIZED_BY`、`STRATEGY_APPLIES_WHEN`（可执行谓词）、`STRATEGY_REQUIRES_ISA`、`STRATEGY_TARGETS_UARCH`、`STRATEGY_EVIDENCED_BY`、`STRATEGY_CONFLICTS_WITH`、`STRATEGY_COMPOSES_WITH` 等。
- **6 条设计原则**：证据优先（策略不存 speedup 数字）、可执行（模板 + 槽位）、可溯源、闭集词表（LLM 不能造词）、软合并（永不物理删除）、图-向量分离。
- **存储**：JSONL/SQLite 为真源 + NetworkX 图 + Milvus 可选；**不引入 Neo4j**（7 个月工期不划算）。抽取流水线 S0–S6：**规则/静态分析做事实，LLM 只做命名与解释**；**差分抽取**（generic C vs RVV）是核心，产出带 before/after 行号的可核查变换。

### 6.3 数据：OpOptBench-45

用 `cx_operator_tool` 的 45 个算子（L1=18、L2=17、L3=10），每个任务 = 通用 C 输入 + 接口契约 + 硬件画像 + 约束。划分：**S1 已见族 12 个进 KG**；**S2 未见算子 24 个为主结果集**；S3 复数/厄米特 9 个；S4 跨 ISA profile；S5 跨架构（QEMU 正确性）。**防泄漏硬规则：S1 ∩ S2 = ∅**。

### 6.4 最关键的一步：把 KG 接进生成（`kg_to_prompt.py`）

输入算子代码 + 目标架构画像，输出：计算模式匹配 → 条件过滤后的策略列表 → 策略实施步骤 + 参数区间 → 结构化 prompt。**目标：一条命令产出 B0/B1/B2/B3 四份 prompt。** 这是 12 月前唯一的"关键路径"任务；没有它，后面所有实验都是零。

## 7. 实验方案：12 周 + 6 周论文学期、三道门（`04` v2.0 全文）

- **任务定义**：T1 硬件条件化算子优化代码生成（主）；T2 优化策略推荐（机制诊断，可跨架构、无需硬件）；T3 跨架构代码迁移（只看 QEMU 正确性/结构泛化）。
- **主矩阵 E1–E8**：主对比、消融、**2×2 因子（结构 × 内容）**、策略级、跨 ISA-profile、跨架构泛化、污染控制、可选外部效度。
- **12 组消融 A1–A12**：核心是 A1（B2 vs B3：同内容异构）、A3（B10 随机子图：排除"上下文更长"）、A5/A6（B7 去硬件 / B9 去条件：证明"绑定结构"的贡献）、A10（B12 等尝试预算：排除"多轮迭代"）。
- **指标**：编译/功能正确率（四分布全过）、`S_comp`（相对编译器基线，主报告口径）、`S_naive`、`S_lib`、**EGC 差距闭合度**、fast_p、Roofline 效率；KG 侧抽取 F1/对齐 P/R/覆盖率；检索侧 R@k/nDCG/SAR/PIV；成本（token/时延/人工）。
- **统计**：每配置 3 seeds、计时 20 次取中位数；配对 Wilcoxon + bootstrap 10,000 次 CI + Cliff's δ；Holm–Bonferroni；**预注册主指标**。
- **门禁**：G1（约 12/12，20 算子 pilot，B3/B2 GM≥1.05 方向为正）→ G2（约 2027-01-20，B3 相对 B2 效应量 ≥10% 且 CI 不跨 1，同时 B3 显著优于 C1）→ G3（约 2027-02-08，全部图表可复现）。**任一不过就按 `04` §9.3 的 6 种负结果预案转 Plan B。**
- **排期**：2026-11-17 起 **12 周**（+ 6 周论文学期）；W1–W2 搭 OpOptBench/驱动；W3 隐藏测试 + KG v1 + C0/C1/C2/P1 基线；W4 pilot/G1（约 12/12）；W5–W8 主实验 + 消融 + 主结论数字；W9–W10 策略级/跨架构/污染控制 + G2（约 1/20）；W11 写实验章 + 投稿（约 1/31）；W12 复现核查/G3 + 缓冲。**LLM 成本约几十到几百元。**
