## 一句话结论

**是的，性能数据已经躺在 CSV 里了。** `promptsv1/2/3_code_run.csv` 的字段包含 `runtime`（生成代码实测毫秒）与 `best_sequential_runtime`（参考实现毫秒），直接相除即得加速比。复算显示：**加入基础硬件信息（v2）相对基线（v1）几何平均加速比约 1.73×，但直接注入"硬件信息推导出的优化策略"（v3）反而降到 0.50×（相对 v2）**——这个"策略注入反而变差"的现象，恰好是"需要带适用条件的结构化知识（KG）"最直接的经验动机，可以作为论文 Introduction 的一个引子（但样本仅 22 个可配对任务，只能作为 pilot 证据，不能当主结果）。

## 1. 复算方法

1. 三个条件各读入 CSV：`v1_baseline`（实验1，CodeGen）、`v2_hw_info`（实验2，prompt 加基础硬件信息）、`v3_strategy`（实验3，prompt 加由硬件信息推导的优化策略）。
2. 只保留 `is_valid=True`、`runtime>0`、`best_sequential_runtime>0`、且 `parallelism_model ∈ {omp, serial}` 的运行（排除只有 2 条、且明显单位异常的 cuda 运行）。
3. 单次运行加速比 `speedup = best_sequential_runtime / runtime`；剔除 `speedup ∉ (0.001, 1000)` 的异常值（原始数据存在 4.7 万倍的极端值，来自计时解析异常/极小 runtime，不能直接用）。
4. 同一任务可能多次运行（run_idx/output_idx），**取中位数**作为该任务在该条件下的加速比。
5. 三条件**按任务名取交集**做配对比较（同任务同模型，只变 prompt 条件）。

## 2. 结果

### 2.1 全量（各条件独立，未配对）

| 条件 | 有效任务数 | 中位加速比 | 几何平均加速比 | >1× 任务占比 |
|---|---|---|---|---|
| v1 基线（无知识） | 41 | 0.968 | **0.810** | 27% |
| v2 + 基础硬件信息 | 28 | 0.971 | **1.456** | 39% |
| v3 + 硬件信息推导的策略 | 32 | 0.945 | **0.867** | 41% |

> 中位数都≈0.95（略慢于参考实现），说明"能不能比参考实现快"高度依赖任务与实现；几何平均受少数任务影响大，需配对后才可解释。

### 2.2 配对（三条件共同覆盖的 22 个任务，同任务同模型）

| 条件 | 中位加速比 | 几何平均加速比 | >1× 任务占比 |
|---|---|---|---|
| v1 基线 | 0.943 | **0.802** | 23% |
| v2 + 硬件信息 | 0.956 | **1.387** | 36% |
| v3 + 策略注入 | 0.885 | **0.699** | 32% |

**配对几何平均比值**：v2/v1 = **1.729×**；v3/v2 = **0.504×**；v3/v1 = 0.871×。
**逐任务胜率**：v2 优于 v1 的任务占 59%；v3 优于 v2 的任务占 50%。

### 2.3 分并行模型（全量，仅参考）

| 条件 | omp 几何平均 | serial 几何平均 |
|---|---|---|
| v1 | 0.665（n=116） | 2.097（n=32） |
| v2 | 1.167（n=76） | 1.833（n=17） |
| v3 | 0.743（n=90） | 2.529（n=18） |

> serial 任务出现 >1× 是正常的（生成代码可能改变了算法/常量，或参考实现本身非最优）；omp 任务的加速比才是真正反映并行优化能力的地方。

## 3. 怎么解读（写给论文/汇报用）

1. **"硬件信息有帮助"有初步证据**：v2 相对 v1 的配对几何平均提升 1.73×，且 59% 任务变好。这与 MARCO（web 检索注入 +30.9%）、PRAGMA（profile 反馈）的结论同向。
2. **"把策略直接塞进 prompt 反而更差"**：v3 相对 v2 掉到 0.50×。可能原因：策略是"硬件信息→LLM 推导"得到的、**没有适用条件与冲突消解**，模型被不适用/相互冲突的策略带偏；也可能是 v3 的 prompt 更长、稀释了代码本身。
3. **这恰好是 KG 的切入点**：不是"多给知识"，而是"**给对的知识、按条件过滤、消解冲突、给可执行模板**"。论文的 Introduction 可以用这个反例开场："我们实测发现，直接把优化策略注入 prompt 会显著变差（0.50× vs 硬件信息条件）；问题不在知识量，而在知识没有条件与结构。"
4. **但必须补做公平对照**：v1/v2/v3 三组不是同一套 prompt 模板、有效子集不同、且 v3 的策略不是来自 KG。要作为论文主结果，必须重跑 **B0/B1/B2/B3 四条件 × 同一任务集 × 同一 token 预算**（见 `04_实验设计与评估协议.md`）。

## 4. 局限与必须核实的事项

1. **条件映射需用户确认**：本文把 `promptsv1` = 实验1基线、`promptsv2` = 实验2（硬件信息）、`promptsv3` = 实验3（策略）——依据是 README 与文件名，但 README 中实验2 的输出写的是 `prompt_test/prompts_code_run.csv`，与 `promptsv2_code_run.csv` 不完全一致。**请对照当时的运行命令/日志确认**；若映射有误，上表需重算（脚本只需改文件名）。
2. **样本小**：配对任务仅 22 个，且来自 ParEval 类并行编程任务（closest pair、geometry 等），**不是 BLAS 算子**。这只能作为"管线能测性能"的可行性证据，不能代替 OpenBLAS 算子实验。
3. **计时口径**：`best_sequential_runtime` 是"最佳参考实现时间"，用它做分母对生成代码偏严格（保守），是合理口径；但 `runtime` 的测量次数、warmup、线程数（CSV 有 `num_threads` 字段）需要固定并在论文中写明。
4. **异常值**：原始数据有 4.7 万倍等异常加速比，来自极小 runtime 或解析异常；论文必须写清洗规则，且不能只报清洗后的"好看"数字。
5. **cuda 仅 2 条**，不能做 CUDA 结论。
