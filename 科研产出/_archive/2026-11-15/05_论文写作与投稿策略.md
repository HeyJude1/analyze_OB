## 一句话结论

**毕业门槛被高估了、投稿窗口被低估了。** 学院对专业学位硕士的论文要求只是"**D 类及以上 1 篇**"（D 类 = CCF-C 国际会议 / EI 期刊 / CCF 中文 C 类 / 中国通信学会 C 类），不是 CCF-A/B、也不是 SCI；但从 2026-11 到 2027-06 只剩 7 个月，按"录用通知须早于 2027-03-31（送审前）"倒推，**全球范围内还来得及的国际会议只有 CCGrid 2027（2026-12-01 截稿，2027-02-01 通知）和 ICS 2027 第一轮（约 2026-12 上旬截稿，约 2027-02 通知）**，其余 CCF-C/B 会议（ICPP、Cluster、HPCC、ICCD）的通知都在 2027-06 之后。因此本文件的主建议是：**11 月内先提交软著 + 专利把毕业硬门槛兜住（2 个月可得），12 月主投 CCGrid 2027 或一本 CCF 中文 B/C 类期刊，二者只能选一（不可一稿多投）**；学位论文题目基本不动，小论文从"语料+图谱+条件化生成"这一刀切出。

## 1. 先把毕业门槛钉死（已核实事实，含原文）

### 1.1 学院规定原文要点

来源：`要求通知/2024毕业要求.pdf` → 提取文本 `_dsh_work/extracted/school_grad_req.txt`。原文件为《湖南大学信息科学与工程学院研究生申请学位学术成果要求》，第九条"本要求从 2021 级研究生开始执行"。

**专业学位硕士研究生 = 第六条**，满足下列**任一**即可申请学位（原文逐条摘录）：

| 条款 | 原文要点 | 对本人的可行性 |
|---|---|---|
| (一) | 制订本学科相关标准和行业指南 1 项 | 难 |
| (二) | 作为核心成员完成省部级及以上重大工程项目等被采纳实施 | 难 |
| (三) | 作为核心成员有效解决企业关键技术问题并被推广应用 | 难 |
| (四) | 获省部级三等及以上科技成果奖 1 项 | 难 |
| **(五)** | **获国内外发明专利授权 1 项（含进入实审）** | **★ 可行，3–6 个月** |
| **(六)** | **获参与课题相关软件著作权 1 项** | **★★★ 最可行，1–2 个月** |
| **(七)** | **在学院认定的 D 类及以上学术期刊/会议上发表学术论文 1 篇** | **★★ 主攻路径** |
| (八) | "互联网+""挑战杯""创青春"获奖 | 不现实 |
| (九) | "中国研究生创新实践系列大赛"获奖 | 可关注但不作为主路径 |

另注意**第二条**："用于申请学位的学术成果……研究生第一署名单位必须为湖南大学；非特别说明，研究生应为学术成果第一完成人，或指导教师为第一完成人、研究生为第二完成人。" → 投稿时单位必须是湖南大学，署名顺序提前和吴帆老师对齐。

### 1.2 学校 A/B/C/D 与 CCF 的映射（附件 2 原文）

来源：`要求通知/2024学术会议论文成果分类表.pdf` → `school_conf_rank.txt`：

| 等级 | 学院认定口径（原文） |
|---|---|
| A | CCF 推荐国际学术期刊/会议 **A 类**、SCI 中科院 1 区、中国科学-信息科学、热点论文、高被引论文 |
| B | CCF 推荐国际学术期刊/会议 **B 类**、IEEE/ACM 汇刊（Transactions 系列）、SCI 中科院 2 区、CCF 中文科技期刊 **A 类**、中国通信学会 A 类 |
| C | CCF 推荐国际**期刊** C 类、SCI 中科院 3 区或 4 区、CCF 中文科技期刊 **B 类**、中国通信学会 B 类 |
| D | **CCF 推荐国际学术会议 C 类**、EI 期刊、CCF 中文科技期刊 **C 类**、中国通信学会 C 类 |

**逐字细读有三点必须注意（决定我们的选刊策略）：**

1. **C 类那一行只写了"国际学术期刊 C 类"，没有写会议**；"国际**会议** C 类"被放在 **D 类**。也就是说：**CCF-C 会议 = 学校 D 类，刚好等于毕业线**，没有额外安全垫。
2. **CCF-B 会议 = 学校 B 类**，反而远超门槛。所以如果碰巧能中 CCF-B 会议，是"超额完成"，但**不该为它牺牲时间**。
3. CCF 中文期刊：**A 类 = 学校 B 类**、**B 类 = 学校 C 类**、**C 类 = 学校 D 类**。所以发《计算机科学》（CCF 中文 B）拿到的等效等级（C 类）**比发 CCGrid（CCF-C 会议 → D 类）还高一档**——这是很多人没算到的账。

另：`要求通知/2024权威期刊会议目录.pdf`（附件 1）只列 12 项（SIGCOMM、SIGMOD、ASPLOS、ISCA、ICSE、CCS、OSDI、SOSP、STOC、CVPR-oral、IEEE TIT、JSAC），这是"**权威**"等级，用于博士条件；**不是硕士的毕业门槛，千万别被这 12 项吓到**。

### 1.3 三条由此得出的结论

1. **不需要冲 CCF-A/B，也不需要 SCI 一区。** 对 7 个月的专硕而言，"CCF-C 会议 + CCF 中文 B/C 类期刊"就是最优解，录取概率才是第一目标函数。
2. **软著/专利是性价比最高的保险**。学院把"软著 1 项"和"D 类论文 1 篇"并列为人选一的条件——这意味着**即使论文全灭，只要办下软著就能毕业**。这个动作 20–40 小时、1–2 个月拿证，必须在 11 月内启动。
3. **导师要求可能高于学校要求**（不少导师默认"必须有一篇论文"）。这是**软约束但优先级更高**，必须在启动前和吴老师明确一句："学校第六条(六)(七)任一即可，我们按论文走，同时我先把软著办了兜底，您看可以吗？"

### 1.5 从 2027-06 答辩倒推的时间硬约束


### 3.1 一句话定位（论文主线，必须背下来）

> **把 OpenBLAS 这类手工优化库里"看不见的优化知识"——同一算子在标量实现和向量实现之间的那批差异（分块、pack 布局、微内核展开、SIMD 宽度、尾循环、数据布局）——抽成一张带"适用条件 + 硬件约束 + 可调参数区间 + 策略冲突"的知识图谱，让 LLM 在生成算子代码前先"查图"，从而把"会写"变成"写得快、还能跨架构迁移"。**

这条主线同时干了三件救命的事：

1. **解决了"没有 baseline"的担忧**：`cx_operator_tool` 里 45 个 OpenBLAS 算子每个都有 `X.c`（通用实现）/ `X_k.c`（深层 kernel）/ `X_rvv.c`（RVV 向量实现）三份配对文件，**配对实现本身就是"策略是否被应用"的 ground truth**，不需要人工从零标注全部知识。方法学 baseline 也很干净：同 LLM、同 token 预算、无知识 / 扁平文本 RAG / 有图无约束 / 完整图谱。
2. **给了"创新点"一个可测形式**：不是"KG+LLM 融合"这种组合式说法（审稿人不认），而是"**用实现差异做弱监督来获取优化策略**"——这是一个具体的、可被复现和质疑的方法主张。
3. **天然分出"跨架构"这条差异化支点**：x86 与 RVV/CX 两侧对照，讨论"哪些策略可迁移、哪些是 ISA 相关"，这正是 QiMeng 系列（AAAI 2025 的 QiMeng-GEMM、arXiv 2511.20100 的 QiMeng-Kernel）没有正面回答的问题，也是我们能站住的位置（相关工作的精确 delta 见同目录 `02_相关工作与baseline地图.md`）。

### 3.3 Abstract 中文版（可直接用，`【】`处等实验数据填）

> 大语言模型（LLM）已能生成语法正确的高性能算子代码，却难以稳定达到接近手工调优的性能，根源在于算子优化知识大多以**代码形态**隐含在 OpenBLAS 等手工优化库中：分块尺寸、数据 pack 布局、微内核展开、SIMD 宽度选择、尾循环处理等策略与"计算流程 + 硬件约束"深度耦合，无法作为文本被检索复用。本文提出一种实现差异驱动的优化知识图谱构建与条件化代码生成方法。首先，以 45 个 BLAS 算子在通用标量实现与 RISC-V RVV 向量实现下的**配对代码**为平行语料，通过结构对齐与 LLM 层次化解析，将两份实现之间的差异归因为可复用的优化策略，从而同时获得策略实体与"策略—计算流程—硬件约束"关系；其次，设计"向量粗筛 + LLM 判别"两阶段实体对齐，以关联计算流程的重叠度作为辅助证据，把图谱冗余节点从【N₁】压缩到【N₂】，对齐精确率/召回率为【P/R】；最后，将计算流程指纹检索、硬件约束过滤与策略冲突消解相结合，把"实施步骤 + 可调参数区间 + 适用条件"填充为结构化提示，引导 LLM 生成目标架构代码。在留出算子集上的实验表明：本方法将生成代码的编译通过率从【x%】提升到【y%】，相对标量参考实现的几何平均加速比为【z×】，达到手工向量实现性能的【w%】；在相同 token 预算下，相比扁平文本检索增强基线，几何平均加速比再提升【Δ×】，消融实验证实增益主要来自图谱的**约束过滤与冲突消解**而非知识文本量。

### 3.4 Abstract 英文版（投 CCGrid 用，`【】`处等数据填）

> Large language models (LLMs) can already emit syntactically valid HPC operator code, yet they rarely approach hand-tuned performance. The root cause is that operator optimization knowledge is encoded **as code** inside libraries such as OpenBLAS: blocking factors, packed data layouts, unrolled micro-kernels, SIMD width choices and tail-loop handling are entangled with both the computation pattern and the target micro-architecture, and therefore cannot be retrieved as plain text. We present an implementation-delta-driven approach that builds an optimization knowledge graph and uses it to condition LLM code generation. Starting from **paired implementations of 45 BLAS operators** — each available in a generic scalar form and an RVV-vectorized form — we align the two versions structurally and apply a layered LLM analysis to attribute their differences to reusable optimization strategies, simultaneously yielding strategy entities and strategy-pattern-hardware relations. A two-stage entity alignment (embedding-based coarse clustering followed by LLM adjudication, with computation-pattern overlap as auxiliary evidence) reduces redundancy from 【N₁】 to 【N₂】 nodes at 【P/R】 precision/recall. At generation time, computation-pattern fingerprints are matched in the graph, hardware constraints are used to filter inapplicable strategies, and conflicting strategies are resolved before the selected templates are injected into a structured prompt. On a held-out operator set, our approach raises compilation pass rate from 【x%】 to 【y%】, attains a geometric-mean speedup of 【z×】 over scalar references and 【w%】 of the hand-tuned vectorized implementation, and improves over a flat-text RAG baseline with an identical token budget by 【Δ×】; ablations attribute the gain to graph-based **constraint filtering and conflict resolution** rather than to the sheer volume of retrieved text.

### 4.4 叙事线（storyline）

```
① 现象：LLM 写的 GEMM 能跑对，但比 OpenBLAS 慢一个数量级。
② 归因：不是模型不会写代码，而是"什么条件下该做哪个优化"这条知识不在语料里，
        它藏在 OpenBLAS 的代码形态里（pack、微内核、展开、尾循环）。
③ 洞见（本文卖点）：同一个算子在同一库里的"标量版 vs 向量版"，
        二者的差异 = 有人已经替我们做过的优化决策 → 天然的弱监督。
④ 做法：差异归因 → 策略实体 + 适用条件 + 硬件约束 + 参数区间 + 冲突 → 图谱
        → 生成前：指纹检索 + 约束过滤 + 冲突消解 → 结构化提示。
⑤ 证据：正确率↑、speedup↑、同 token 下比扁平 RAG 更好（证明"图"不是噱头）、
        跨架构仍有效（证明知识可迁移）。
⑥ 边界：只覆盖 OpenBLAS 的 45 个算子、2 个架构、性能上限受参考实现限制 → 未来工作。
```

**电梯稿（30 秒版，给导师汇报用）**："OpenBLAS 里每个算子都有标量版和向量版，人做的优化决策就藏在两版的差异里。我把这些差异变成一张带适用条件和硬件约束的图谱，让 LLM 生成前先查图。在 45 个算子上，生成代码的编译通过率从 X 到 Y、平均加速 Z 倍，同样 token 下比纯文本检索再好 Δ 倍。"
