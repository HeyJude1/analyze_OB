## 1. 硬件画像是什么？输入里要不要包含"多平台性能结果"？

### 1.1 定义

**硬件画像（HardwareProfile / Microarchitecture）描述"这台机器能做什么、怎么测"，不描述"跑得多快"。**

字段（`schema/hardware_profiles.yaml`，6 个 profile）：

| 字段 | 例子（k1_rvv256） | 用途 |
|---|---|---|
| vendor / uarch | SpacemiT / "K1 (Banana Pi F3)" | 标识 |
| isa | `RVV 1.0, Zba, Zbb, Zbc, Zbs` | **硬过滤**：策略 REQUIRES 的 ISA 必须在里面 |
| vector_bits / fp64_lanes | 256 / 4 | 过滤 + 模板参数（SEW/LMUL） |
| lmul_max / vector_regs | 8 / 32 | 参数推导 + 寄存器预算 |
| l1d/l2/l3 / cacheline_b | 32KB / 512KB / 0 / 64B | 分块大小推导 |
| cores / freq_ghz | 8 / 1.6 | 环境描述（freq 是标称值） |
| peak_gflops_fp64 / stream_bw_gbps | **0.0 / 0.0（未实测）** | 仅占位，**不是证据** |
| measure_env / compiler | native / `riscv64-linux-gcc 14.3 -O3 …` | **证据必须绑定**的测量环境 |

### 1.2 和"性能结果"的区别

```text
HardwareProfile  = 坐标系（能力 + 环境）
PerformanceEvidence = 读数（metric / value / aggregation / workload / baseline / platform / protocol / confidence）
```

- 性能结果**不是**画像的一部分，是独立节点 `PerformanceEvidence`（当前 88 个），通过 `STRATEGY_EVIDENCED_BY` 挂到策略、通过 `EVIDENCE_ON` 挂到 profile。
- 当前 88 条证据**全部**来自 `hw:qemu-riscv64-vlen256`，`scope=operator`（算子级继承），置信度 0.35；真机数字还没进来。
- 画像里 `freq/peak/stream = 0` 是**未实测占位**，不是"性能为 0"。这一点图里如果混在一起会被误读。

### 1.3 为什么画像必须作为"输入"

三个用途都是**检索/生成时要用**的，不是事后统计：

1. 过滤：`STRATEGY_REQUIRES_ISA` 的 ISA 必须 ⊆ profile.isa（硬约束）；
2. 推导：LMUL ≤ lmul_max、block_size 由 cacheline/L1 推、展开因子受 vector_regs 约束；
3. 绑定证据：证据必须写明在哪台 profile 上测的，否则不能跨平台比较。

**结论**：输入里要有"多平台的能力描述"和"测量环境"；**不要**把性能结果塞进画像。两者在图里是两类节点，在流程里是两条输入。

## 2. S0–S2 用规则真的能完全做到吗？

分三段回答，**不是"能/不能"，而是"各自能做到哪、哪里会漏"**。

### 2.1 S0 / S0b：能，完全规则

- 做什么：扫描、登记 `path + sha256 + 行数 + arch + ISA`；多架构源按 glob 自动发现并复制到自包含目录。
- 产出：`corpus_manifest.jsonl`（112 个输入）、`multiarch_manifest.jsonl`。
- 能力边界：**只保证"登记完整"，不保证"登记正确"**——清单是手写配置（`config.yaml` 的 `arch_sources.files`），会和算子注册表漂移。
- 实证：`symv` 在 `multiarch.arch_sources.x86_avx2.files` 里配了源文件，但 `corpus.operators` 没登记 → 抽出 3 条 `stg:symv:*` 策略，却**没有 `Operator` 节点**，检索永远取不到（孤儿策略）。这是 S0 的典型故障：不是解析错，是**清单不一致**。

### 2.2 S1：能覆盖"声明过的特征"，但有三类盲点

- 实现方式：**正则**（`re`），不是 AST。抽：函数签名与行号区间、循环嵌套深度、向量 intrinsic、SEW/LMUL、累加器个数、k 循环展开分母、掩码/动态 vl 尾部、步长分支、FMA、预取、归约、打包、复数；汇编侧抽 mnemonic 计数、向量寄存器宽度、FMA/prefetch 计数、寄存器分块线索。
- 规模：893 条特征记录，每条可指回行号。
- **盲点 1：宏与模板**。OpenBLAS 大量 `CTYPE`/`#define` 宏；正则看到的是源码文本，不是展开后的代码。缓解手段是只用 `.clean.c`（预处理过的语料），但宏参数化后的结构仍可能漏。
- **盲点 2：别名与指针分析**。正则判断不了 `restrict`、指针别名、越界；这部分只能作为启发式（`structural`/`stride`），不能作为硬事实。
- **盲点 3：编译器生成**。源码里没有的自动向量化、循环变换，S1 看不见；所以"源码特征"≠"编译后行为"。
- 汇编侧只能抽"特征存在"（指令计数、寄存器宽度、分块线索），**不能抽数据流/依赖**。

### 2.3 S2：只在"C 对 C"时是完整差分；汇编退回特征

- `diff.py` 的做法：把 S1 的结构化视图做差，按 10 条 `DELTA_RULES` 产 action/delta/params/行号锚点（vectorize、fma、blocking、unroll、tail、lmul、stride_dispatch、reduction、prefetch）。
- 现实数据：`diffs.jsonl` 51 条 = 12 条 RVV 差分 + 39 条多架构记录；其中 **C 可差分 18 条，汇编-only 21 条（`method=static`，只有特征没有差分）**。
- **边界 1：汇编不能差分**。generic C vs `.S` 汇编没有可比的结构化视图，只能说"汇编里有 vfmacc/prefetch/多少寄存器"，不能说"从 X 变成 Y"。
- **边界 2：算法不同≠优化不同**。如果两个实现算法本身不同（如分块策略不同但都叫 dgemm），差分会把"算法差异"记成"优化动作"。
- **边界 3：宏/模板/变量重命名**会制造伪 diff。

### 2.4 一句话结论

> S0 完全规则；S1 在**声明过的特征词表**内规则可做（约 9 类特征），但有宏/别名/编译器的盲点；S2 只有 C↔C 能差分，汇编只能抽特征。

**所以"规则抽取"不是万能的**——它抽的是**可静态判定的事实**；意图（为什么）、原理（trade-off）、跨架构类比，规则抽不出来，才需要 LLM。这也是为什么 LLM 的位置是"命名/解释/提假设"，而不是"决定事实"。

## 3. Schema 对账：12/14/10 是哪来的？你记的 5/4 是什么？

你记的 **5 类实体 / 4 类关系**，是**旧 KG（analyze_OB1）实际落地**的 schema；**12/14/10** 是**现在 kg_agent 声明**的 schema。两者不是一回事，四个口径对账如下。

### 3.1 四个口径

| 口径 | 实体 | 关系 | 谓词 | 来源 |
|---|---|---|---|---|
| A. analyze_OB1 **声明** | 7 | 12（docstring 写 13，`Rel` 类里 12） | 无（条件是散文） | `analyze_OB1/src/kg/extractor.py` |
| B. analyze_OB1 **落地**（20251114） | **5**（source_pattern / optimization_strategy / architecture_capability / code_example / tunable_parameter） | **4**（OPTIMIZES_PATTERN 326 / TARGETS 206 / IS_ILLUSTRATED_BY 206 / HAS_PARAMETER 67） | 无 | `relation_entity.json`（805 条） |
| C. kg_agent **声明** | **12** | **14** | **10** | `schema/entities.yaml`、`relations.yaml`、`condition_vocab.yaml` |
| D. kg_agent **落地** | **11**（`FailureCase` = 0 条） | **14**（全部有实例） | **9/10**（`stride_y` 未使用） | `data/nodes.jsonl` / `edges.jsonl` |

### 3.2 12 类实体（kg_agent，`entities.yaml`）

`Operator`、`ComputationPattern`、`CodeCharacteristic`、`OptimizationStrategy`、`ImplementationTemplate`、`TunableParameter`、`ISACapability`、`Microarchitecture`、`HardwareProfile`、`PerformanceEvidence`、`SourceArtifact`、`FailureCase`（未用）。

### 3.3 14 类关系（`relations.yaml`，头→尾）

`OPERATOR_HAS_PATTERN`（算子→流程）、`PATTERN_HAS_CHARACTERISTIC`、`PATTERN_OPTIMIZED_BY`、`STRATEGY_HAS_PARAMETER`、`STRATEGY_HAS_TEMPLATE`、`STRATEGY_APPLIES_WHEN`、`STRATEGY_REQUIRES_ISA`、`STRATEGY_TARGETS_UARCH`、`STRATEGY_EVIDENCED_BY`、`EVIDENCE_ON`、`EVIDENCE_SOURCE`、`STRATEGY_COMPOSES_WITH`、`STRATEGY_CONFLICTS_WITH`、`STRATEGY_GENERALIZES`。

### 3.4 10 个谓词（`condition_vocab.yaml`）

`dtype`、`precision`、`stride_x`、`stride_y`、`loop_depth`、`size_regime`、`aligned`、`tail_divisible`、`structural`、`reduction`。

**注意**：`isa`、`vector_bits`、`vector_regs` **不是谓词**，它们走 `STRATEGY_REQUIRES_ISA` 边 + profile 字段 + 寄存器预算。`22` 文档的表把它们列进"10 谓词"是**口径错误**，本文以 YAML 为准。

### 3.5 谓词实际使用分布（262 条策略，2026-11-16）

| 谓词 | 使用次数 | 占比 |
|---|---|---|
| dtype | 262 | 100% |
| loop_depth | 262 | 100% |
| size_regime | 262 | 100% |
| structural | 78 | 30% |
| precision | 61 | 23% |
| reduction | 34 | 13% |
| stride_x | 22 | 8% |
| aligned | 22 | 8% |
| tail_divisible | 12 | 5% |
| **stride_y** | **0** | **0%** |

**这条数据很关键**：三条谓词覆盖全部策略（dtype/loop_depth/size_regime），而真正区分硬件的 `stride_x/aligned/isa` 用得很少——**条件写得浅，硬件过滤承担了主要区分度**。这会影响第三章"条件质量"的论证：不能只说"262/262 可执行"，要说"3 条谓词覆盖 100%，区分度不足"。

### 3.6 provenance 的真实结构

`node.schema.json` 强制 `source_file` + `extractor_version`；实际字段：

```json
"provenance": {
  "source_file": "data/corpus_multiarch/x86_avx2/axpy/daxpy_microk_haswell-2.c",
  "origin_file": "kernel/x86_64/daxpy_microk_haswell-2.c",
  "line_start": 29, "line_end": 77, "line_confidence": "exact",
  "commit": "OpenBLAS 0.3.27 (git ce3f668)",
  "extractor_version": "kgagent-v1.5"
}
```

覆盖率（862 节点）：`line_confidence=exact` 844、`approx` 18；无 `line_start` 18；有 `sha256` 125（主要在 `SourceArtifact`）。**所以"每条实体带 provenance"成立，"每条都有精确行号+sha256"不成立**——图里应写"source_file + 行号 + 置信度 + 版本"，不要暗示 100% 精确。

## 4. 建图时有实体消歧吗？

### 4.1 现状：有三个"合并类"机制，但没有真正的实体消歧

| 机制 | 代码位置 | 做了什么 | 是不是消歧 |
|---|---|---|---|
| `_unique()` | `normalize.py:97` | ID 冲突时加 `_2/_3` 后缀（如 `stg:gemm:reorder_code_a_2`） | ❌ 唯一化，不是合并 |
| `_merge_params()` | `normalize.py:151` | 同名参数合并为全局 `par:<name>` | ⚠️ 参数级合并，不是实体级 |
| `ACTION_ABSTRACT` + GENERALIZES | `normalize.py:63-79` | 每个 action 挂一个抽象策略节点（6 个） | ⚠️ 抽象归类，不是消歧 |
| 跨架构合并 | `extract.py`（cross_arch 通道） | 同 (op, family, action) 跨架构合成 `_x` 节点，保留 `arches`/`arch_parameters` | ⚠️ 对齐，但保留各架构实例 → 会有重复 |

**缺失的四样**：别名表（alias）、合并日志（merges.json）、合并精度/召回评估、语义/嵌入层面的同义判定。

### 4.2 证据：6 组重复，全部发生在 `_a` × `_s` 交界

`kg_consistency_audit.py` 的 C5 检察出 6 组同算子、同族、同层、同 `arch_scope` 的策略，例如：

```text
stg:gemm:reorder_code_a  vs  stg:gemm:reorder_s
stg:gemm:unroll_code_a   vs  stg:gemm:unroll_s
stg:hemv:tail_handle_code_a vs stg:hemv:tail_handle_s
```

根因：同一条知识由"LLM 分析通道（`_a`）"和"规则通道（`_s`）"各生成一次，规范化层只做了 ID 唯一化，没做语义合并。

### 4.3 旧 KG 做过消歧，但很保守

analyze_OB1 有完整的 `cluster → refine → merge` 三阶段（embedding 聚类 + LLM 分组 + LLM 合并，跑 3 轮），但 20251114 这轮：

- optimization_strategy 45 簇，仅 **3 组** `similar_groups`；
- tunable_parameter 13 簇，仅 **1 组**；
- hardware_feature 64 簇，**0 组**。

说明它的消歧阈值/提示词偏保守，**也没报合并 precision/recall**。

### 4.4 为什么不能简单按名字去重

862 个节点里"同类型同名"有 86 组，但大部分是**合法的按算子重复**：`参数合法性校验` 在 14 个算子里各有一条 `pat:<op>:prep.parameter_validation`。按名字合并会把不同算子的流程节点错误合并。

**正确的合并键**应是：`(type, operator, action, level, arch_scope)` + 参数区间兼容性 + 冲突边检查；跨算子默认不合并。

### 4.5 结论

> 现在只有"ID 唯一化 + 参数合并 + 抽象归类 + 跨架构对齐"，**没有实体消歧**；6 组重复是证据。
> 要补的是：合并键规则 + alias 表 + merges.json + 50 组人工合并 P/R 评估。
