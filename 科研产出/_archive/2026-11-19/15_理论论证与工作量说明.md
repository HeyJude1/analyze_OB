## 0. 一句话结论

**不要说"KG 自动提升性能"，要说"在三个可测的单调性条件下，KG 通过提高可行候选比例、参数准确率、减少策略冲突，期望提升生成代码的正确性与性能；这三个条件用 E2/E6 的消融逐条验证，不成立就报告边界"。**
工作量不在"架构图有几个框"，而在：**多架构语料与映射（70 个实现）→ 可执行 Schema（262 策略/模板）→ 抽取流水线（6.8k 行）→ 评测基准（12 任务 × 隐藏分布）→ 7 组实验（约 1000+ 次生成/编译/运行）→ 4.9 万字论文**。创新点按"知识表示 / 知识获取 / 检索规划 / 迁移评测"四条写，每条都有对应实验证据。

## 1. 先把问题说清楚：优化代码生成到底在做什么

设：

- `x`：输入代码（通用 C 实现）+ 接口契约；
- `h`：目标硬件画像（ISA、向量宽度、寄存器数、缓存、频率）；
- `S`：候选优化策略集合（向量化、分块、展开、预取、打包、尾处理…）；
- `Θ`：每条策略的参数空间（unroll 因子、块大小、VLEN/LMUL、预取距离…）；
- `C(s; x, h)`：策略 `s` 在代码 `x` 与硬件 `h` 下是否**可行**（硬条件 + 资源预算 + 冲突约束）；
- `P(y; h)`：生成代码 `y` 的性能（如相对编译器基线 `S_C1` 或差距闭合度 EGC）。

LLM 的任务实际是：

> 从 `S × Θ` 中选一个**可行**且**性能好**的组合计划，再把它写成代码。

LLM 做这件事有三个结构性缺陷：

| 缺陷 | 具体表现 | 对应机制 |
|---|---|---|
| **知识缺口** | 长尾硬件优化策略不在预训练语料里（如 RVV 的 LMUL/SEW 调参） | M1 覆盖 |
| **约束不可判** | 知道"有循环展开"但不知道"当前 dtype/stride/寄存器数下能不能用" | M2 过滤 |
| **参数不会算** | 知道"要分块"但块大小/展开因子拍脑袋 | M3 实例化 |
| **组合不会排** | 两个分块策略同时用会爆寄存器/冲突 | M4 组合 |
| **换架构不会迁** | x86 的 unroll=4 直接搬到 RVV 上不一定对 | M5 迁移 |

**KG 的作用不是"多给几段文本"，而是把上面五件事从"LLM 隐式猜"变成"图上显式算"。**

## 2. 五条机制（每条都是一个可测假设）

### M1 覆盖（Coverage）

- **定义**：知识图谱覆盖了多少"任务 × 硬件"下的可行策略。记 `κ = |S_feasible ∩ S_KG| / |S_feasible|`。
- **为什么平文本做不到**：文本 RAG 只能检索"相似段落"，检索不到"没被写进文档的长尾策略"；KG 是结构化索引，可按算子 × 架构 × 策略族精确定位。
- **可测假设 H1**：`κ` 越高，候选召回越高，生成代码命中可行策略的比例越高。
- **对应实验**：E2（R@5 / nDCG / SAR）、E3（生成代码中策略使用率）。
- **预期方向**：L2/L3 算子（分块/寄存器）增益 > L1（编译器已饱和）。

### M2 过滤（Feasibility）

- **定义**：KG 的边/属性给出硬条件（`dtype ∈ {d}`、`stride_x == 1`、`loop_depth ≥ 2`、`requires AVX512`、`VLEN=256`），可以**精确判定**策略是否可行。
- **为什么平文本做不到**：文本里即使写了"适用于连续内存"，LLM 仍可能忽略；KG 的谓词求值是确定性的，不满足就淘汰（可审计）。
- **可测假设 H2**：加入硬过滤后，不可行策略比例下降，编译失败率/数值错误率下降，FCR 上升。
- **对应实验**：E6 消融 A2（去硬件过滤）、A3（去条件过滤）→ 看 CR/FCR 变化；E3/E4 主表。

### M3 实例化（Parameterization）

- **定义**：参数不是常数，而是由硬件推导：`unroll_factor = min(4, vector_regs/4)`、`reg_block_n = min(vector_regs/2, N_tile)`、RVV 的 `VLMAX = VLEN×LMUL/SEW`、块大小受 L1/L2 容量约束。
- **为什么平文本做不到**：文档只写"块大小要适配缓存"，不会给当前机器的具体数；KG 存了推导式和硬件数值，可以算出候选值。
- **可测假设 H3**：参数由硬件推导后，参数错误率下降，S_C1/EGC 上升。
- **对应实验**：E6 消融 A4（去参数/参数错配）→ 看 S_C1 变化；E7 案例（块大小/展开因子对比）。

### M4 组合（Composition）

- **定义**：策略之间有 `COMPOSES_WITH`（可组合、有顺序）与 `CONFLICTS_WITH`（互斥/资源冲突）；还有寄存器预算：`reg_block_n × k_unroll` 不能超过 `vector_regs × 80%`。
- **为什么平文本做不到**：文本 RAG 给的是"策略列表"，不会给出"这两条不能同时用"的约束；LLM 往往"多给几条都用上"，导致负优化。
- **可测假设 H4**：做组合/冲突消解后，负优化（比 C1 慢）比例与性能方差下降。
- **对应实验**：E6 消融 A8（去冲突消解）、A10（等尝试预算）→ 看性能回退率/方差；E7 失败案例。

### M5 迁移（Transfer）

- **定义**：同一策略在 x86/ARM/RVV 上的实现不同，但抽象层次可分三层：
  - `arch_agnostic`（架构无关，如"减少访存"）；
  - `parameterized`（同族不同参数，如 vector_width 128/256/512、unroll 4/8）；
  - `arch_specific`（架构特定，如 `vfmacc`、`prefetcht0`、mask 尾处理）。
- **为什么平文本做不到**：文本没有"这条策略在哪些架构上成立、参数怎么换算"的结构化标注；KG 有 `arch_scope` 与各架构参数，可以做**参数映射**。
- **可测假设 H5**：`arch_scope` 分类越准，跨架构迁移保真度越高；架构无关/参数化策略迁移收益大，架构特定策略迁移收益小甚至为负。
- **对应实验**：E5（Kx86 / KARM / KRVV 三种知识源 → 目标架构）、E4（RVV 生成）。

### 2.1 把五条机制合成一个"充分条件"论证（写进论文 3.3）

设生成质量 `Q` 是四个比例的单调增函数：

```text
Q = f(π_feasible, π_param_ok, π_no_conflict, κ)
    π_feasible      = prompt 中可行策略的比例
    π_param_ok      = 参数落在合理范围的比例
    π_no_conflict   = 无冲突策略组合的比例
    κ               = 知识覆盖率
```

KG 的 M1–M4 分别提高 `κ、π_feasible、π_param_ok、π_no_conflict`；**若 `f` 单调**，则 `E[Q]` 不降。`f` 的单调性是**可测假设**：E6 的 A2/A3/A4/A8 分别改变四个比例，看 Q（FCR/S_C1/EGC）是否同向变化。
- 若同向 → 机制成立；
- 若不同向 → 说明"LLM 能力/编译器基线"等更强因素主导，这就是**边界结论**（例如 L1 算子编译器已饱和，KG 增益小），同样是论文贡献。

> 论文写法：**不要写"证明了 KG 提升性能"；写"提出机制假设 + 形式化充分条件 + 可证伪预测 + 实验验证/边界分析"。** 这是硕士论文能站住、答辩不被抓的写法。

## 4. 为什么这不是"只是 RAG"（形式化对比）

| 维度 | 扁平文本 RAG（B2） | 完整 KG（B3） |
|---|---|---|
| 知识单元 | 文本块/段落 | 策略卡：id + 条件 + 参数 + 模板 + 证据 + 来源 |
| 检索结果 | 相似文本列表 | 满足硬约束的候选策略集合 |
| 可行性判断 | LLM 自己读文本判断 | 谓词求值（确定性、可审计） |
| 参数 | 文本里提到"块大小" | 由硬件推导的具体数值 |
| 组合/冲突 | 文本里可能没写 | 显式 `COMPOSES/CONFLICTS` 边 + 预算 |
| 多跳 | 不能 | 算子→流程→策略→模板/证据/来源 多跳 |
| 可追溯 | 链接到文档 | file + line + commit |

**关键区别**：RAG 改变的是"LLM 看到的文本分布"；KG 改变的是"候选策略的可行域"。前者是信息检索问题，后者是**约束满足问题**。B2 vs B3 的消融（同内容、同 token）就是用来证明这个区别的。

## 5. 创新点（硕士论文版，四条，均可辩护）

> 写法纪律：不写"首次/填补空白/国际领先"；每条都写"是什么 + 为什么不是已有工作 + 怎么证明 + 对应章节/实验"。

### 创新点 1：多架构、可执行的优化策略知识表示

- **是什么**：把策略从"自然语言经验"升级为"带适用条件、可调参数、实施模板、性能证据、来源行号的策略卡"，并加 `arch_scope`（架构无关/参数化/特定）与各架构参数。
- **为什么不是已有**：Xe-Forge/KernelBlaster 的知识库是"文本/经验条目"，QiMeng 的硬件知识是"人写规则"；它们没有"可被程序求值的条件 + 参数推导 + 跨架构参数保留"三件套。
- **怎么证明**：E1（抽取/对齐 P/R/F1、溯源率）、E2（条件过滤带来的推荐质量）、E6 A2/A3。
- **对应**：第 3 章。

### 创新点 2：差分驱动的知识获取方法

- **是什么**：以"同一算子通用 C vs 架构优化实现"的配对差异为弱监督信号，规则抽事实（行号、参数、intrinsic），LLM 只做命名/解释；跨架构再对齐。
- **为什么不是已有**：现有工作多为"让 LLM 读单版代码总结策略"（幻觉大、不可溯源）；差分把"专家已做的决策"变成可核查的 before/after。
- **怎么证明**：E1（对比"直接 LLM 抽取"的 F1/溯源率）、抽取案例（262 策略/70 实现/30 跨架构）。
- **对应**：第 3 章 3.4–3.5。

### 创新点 3：硬件条件约束的检索与冲突消解式策略规划

- **是什么**：7 步检索（模式匹配→召回→条件过滤→硬件过滤→冲突消解→打分→StrategyPack），把"知识选择"变成可审计、可回放的决策链；策略参数由硬件推导。
- **为什么不是已有**：PRAGMA/MARCO 是"profile/网页检索 + prompt 迭代"，没有"条件谓词 + 寄存器预算 + 冲突边"的约束求解；扁平 RAG 无法表达。
- **怎么证明**：E2（推荐质量）、E6 A1/A2/A3/A4/A8（逐条消融）、trace 可视化（答辩现场可回放）。
- **对应**：第 4 章。

### 创新点 4：跨架构可迁移性的度量与评测基准

- **是什么**：给出"架构无关/参数化/特定"三层分类 + 迁移保真度指标 + OpOptBench-12（12 算子 × D1–D4 隐藏分布 × 双平台）+ EGC/fast_p 等指标。
- **为什么不是已有**："算子优化知识迁移"没有公开 benchmark/协议；现有工作要么单架构，要么只看正确性。
- **怎么证明**：E5（三层迁移表）、E3/E4（双平台主表）、E7（失败归因）。
- **对应**：第 5 章。

> 第 5 条可写成"工程与可复现贡献"（Agent 流水线 + 可视化回放 + 43 测试 + 离线重建），放在"系统实现"而不是创新点，避免被说"工程不算创新"。

## 8. 答辩话术（三个必问）

**Q：你的 KG 凭什么能提升性能？**
> "我不声称图一定比文本好。我把优化代码生成拆成四个比例：可行策略比例、参数正确比例、无冲突组合比例、知识覆盖率；KG 的覆盖/过滤/参数推导/冲突消解分别提高这四个比例。在这四个比例对质量单调的假设下，期望性能提升；这个假设用 E6 的四组消融逐条验证。如果某条不成立，就是边界结论——比如 L1 算子编译器已饱和，KG 增益小。"

**Q：你的工作量在哪？看起来就是几个框。**

**Q：创新点是什么？**

## 10. 诚实边界（写进论文 5.7，答辩主动说）

- 语料只来自 OpenBLAS，不外推到所有算子库；
- ARM 只有知识、没有硬件性能实验；
- x86/ARM 汇编内核只做静态特征抽取，语义抽取只覆盖 C 内核；
- QEMU 证据只用于正确性，不参与性能排序；
- "性能提升"用 S_C1/EGC 度量，不声称超过 OpenBLAS；
- 机制是"假设 + 验证"，不是"定理"。

> **一句话**：硕士论文不要求"证明一个定理"，要求"问题清楚、方法自洽、实验可证伪、工作量可见、边界诚实"。这套东西按上面写，四样都占。
