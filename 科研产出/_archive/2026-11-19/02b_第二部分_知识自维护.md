## 2. 第一部分：对比实验怎么设计才充分

### 2.1 先纠正一个说法：不是"把方法跑在 OpenBLAS 上"

OpenBLAS 在你的论文里扮演三个角色，不是"测试集"：

1. **任务来源**：从 OpenBLAS v0.3.27 抽 12/14 个算子的 `generic.c`（通用实现）作为输入；
2. **专家参照**：对应的优化实现（RVV/x86/ARM kernel）作为 P1 上界和知识抽取来源；
3. **评测环境**：用同一套 driver + 隐藏测试（D1–D4）+ 计时协议，在 x86/RISC-V 上跑生成代码。

所以你的"数据集"应该叫 **OpOptBench**：`任务 = 算子 × 尺寸 × 硬件`，每个任务有：
输入 `generic.c` + 接口契约 + 硬件 profile；隐藏测试 D1–D4；参考实现/上界；计时脚本。
这不是静态标注数据集，而是**可执行基准**——这比"在现成数据集上算 accuracy"更硬，也更能证明"性能"。

### 2.2 对照组的三个层次（缺一不可）

| 层次 | 条件 | 作用 | 是否公平可比 |
|---|---|---|---|
| **下界/上界** | C0：输入代码 `-O2`；C1：编译器 `-O3`；P1：OpenBLAS 专家实现 | 回答"有没有超过编译器和专家" | 同任务同硬件，公平 |
| **同 LLM 的方法对照** | B0 零样本、B1 +硬件、B2 扁平文本 RAG、B3 完整 KG（主方法）、B4 MPSA（可选） | 回答"增量来自图结构还是多给文字" | 同 LLM/同 token/同尝试次数，公平 |
| **外部 AI 优化方法** | KernelBlaster（CUDA）、Xe-Forge（Intel GPU）、QiMeng-Kernel（GPU）、PRAGMA/MARCO（HPC 代码）等 | 回答"和相关工作比处于什么位置" | **多数不可直接数字对比**（语言/架构/任务不同）：只做方法对照表 + 可移植子集 |

> **关键**：外部方法不能硬比数字。它们大多面向 GPU/CUDA，你面向 OpenBLAS C + RISC-V/x86；正确做法是：
> - 在 Related Work 里逐篇对照"知识表示/检索/生成/评估"四个维度；
> - 选 1–2 个**同语言/同硬件可复现**的方法做补充对比；
> - 其余用"报告数字 + 注明不可比原因"，不要拼一张"我们 SOTA"的表。

### 2.3 实验矩阵（第一部分）

| 实验 | 回答什么 | 规模 | 关键指标 |
|---|---|---|---|
| **E1 KG 质量** | 知识抽得准不准、可溯源？ | 6 个 S1 算子、120 条人工金标、2 人标注 | 抽取/对齐 P/R/F1、覆盖率、κ、溯源率 |
| **E2 策略推荐** | 给定代码+硬件，能否推荐对策略？ | 12 算子 × 2 profile × 4 条件（不执行） | P@5/R@5/nDCG/SAR |
| **E3 x86 生成** | 正确吗？比编译器快吗？ | 12 算子 × 6 条件 × 3 尺寸 × 3 seeds | CR/FCR/S_C1/EGC/token |
| **E4 RISC-V 生成** | 换 RVV 还成立吗？ | 12 算子 × 4 条件 × 2 尺寸（真机） | 同上 + RVV 指令使用率 |
| **E5 跨架构迁移** | 哪些策略能迁移？ | 6 算子 × 3 知识源（Kx86/KARM/KRVV） | 迁移保真度 + 三层分类 |
| **E6 消融** | 增量来自哪一部分？ | B2 vs B3、去硬件/条件/参数/模板/冲突、随机子图 | ΔFCR/ΔS_C1/Δtoken |
| **E7 案例与失败** | 为什么成功/失败？ | dgemm/daxpy/dtrmm + 20 个失败样本 | 失败分类 + 案例图 |
| **E9 MPSA（可选）** | 多视角分析是否有增量？ | 6 算子 × B3 vs B4 × 3 seeds | FCR/KCS/token（当前已跑 24 cells） |

### 2.4 "充分"的判定清单（答辩可逐条说）

1. **内部效度**：同 LLM、同模型版本、同 temperature、同 token 预算、同尝试次数；B2/B3 只改知识组织形式。
2. **外部效度**：S2 留出算子 + 两个平台（x86/RISC-V）+ 多个尺寸；不能只在 S1 上报告。
3. **构念效度**：正确性用 D1–D4 隐藏测试；性能用真机 `S_C1/EGC`；知识质量用人工金标 + κ；KCS 只作辅助。
4. **统计效度**：3 seeds、配对检验（Wilcoxon）、bootstrap 95% CI、多重比较校正；负结果/不显著也报告。
5. **可复现**：每个 run 一个 md + 可复现包（输入/硬件/检索 trace/每轮迭代/最终代码），已落地。
6. **成本**：token/时延/每任务成本；B3 vs B2 同预算，B4 的成本要明示。
7. **失败分析**：至少 20 个失败样本，分类到"知识不足/知识未被采纳/实现错误/性能回退"。

> 只要这 7 条都占，审稿人/答辩问"你的对比是否充分"就有话说；不要求"把所有 SOTA 都跑一遍"。

### 2.5 关于"别人有数据集，直接跑方法"的疑问

- 他们有静态数据集（如 KernelBench 的 250 个 PyTorch 算子），跑方法算 pass/fast_p；
- 你是**从开源算子库构造任务 + 执行评估**，本质一样：`benchmark = 任务集合 + 评测协议`；
- 你的优势是任务带**多架构知识 + 真实性能计时**；劣势是任务规模小（12/14 算子），所以要用**多尺寸 × 多 seed × 消融**补足；
- 不要声称"在 OpenBLAS 上全面超过"，只声称"在 OpOptBench-12 上，相对编译器/扁平 RAG 有增量"。

## 3. 第二部分：Agent 自维护（反馈式更新 KG）

### 3.1 先定义清楚，避免"自进化"被质疑

建议叫 **"经验驱动的知识库维护"（feedback-driven KG maintenance）**，不叫"Agent 自进化"：
- 不更新 LLM 参数；
- 只更新 KG（新增 `FailureCase`、修改策略条件/参数、增加模板/证据、合并同义策略）；
- 每次更新必须**可验证、可回滚、版本化**；
- Agent 只"提议"，验证器/人工"批准"。

### 3.2 反馈回路（和第一部分衔接）

```text
任务 → 检索 KG_r → 生成 → 编译/正确性/计时
   ├─ 首轮成功：总结"哪条策略/参数起了作用" → 正例
   ├─ 多轮修复成功：总结"首轮错在哪、修复改了什么" → 修复经验
   └─ 最终失败：总结"缺哪类知识/哪条条件写错" → 失败案例
        ↓（结构化：state / action / outcome / evidence / proposed update）
   更新提议 → 门控（schema + 证据 + 人工抽检）→ KG_{r+1}（版本化快照）
```

### 3.3 E10：自维护实验设计（关键）

**最重要的原则：维护用的任务 ≠ 评估用的任务。**

| 集合 | 用途 | 规则 |
|---|---|---|
| `D_evolve` | Agent 观察轨迹、提出更新 | S1 的 6 个算子（或按时间流分批） |
| `D_test`（冻结） | 每轮评估 KG_r 的 held-out 效果 | S2 的 6 个算子，**永远不参与更新** |
| `D_regression` | 检查遗忘/负迁移 | 之前已解出的任务，固定集合 |

**流程（5 轮）**：
1. `KG_0`：第一部分建好的初始图谱；
2. 在 `D_test` 上评估 `KG_0`（基线）；
3. 在 `D_evolve` 上跑一批任务，收集成功/修复/失败轨迹；
4. 生成更新提议 → 门控 → `KG_1`；
5. 在**同一个冻结 `D_test`** 上再评估 → 看纯 KG 带来的变化；
6. 重复 3–5，得到学习曲线；每轮保存 `KG_r` 快照 + 更新日志。

**对照组（同一 LLM/同预算）**：

| 组 | 更新策略 | 作用 |
|---|---|---|
| M0 静态 KG | 不更新 | 下界 |
| M1 仅失败案例 | 只加 FailureCase | 失败驱动是否有效 |
| M2 仅成功案例 | 只加正例 | 成功经验是否有效 |
| M3 成功+失败（提出） | 两类都用 | 主方法 |
| M4 随机更新 | 随机加/改条目 | 排除"更新本身"的安慰剂效应 |
| M5 无门控 | 不过滤直接写 | 证明门控必要 |

**指标**：
- 主：冻结 `D_test` 上的 FCR / S_C1 随轮次变化（学习曲线）；
- 次：`D_regression` 回归率（越改越差的比例）、知识精度（人工抽检 50 条更新）、更新采纳率（accepted/proposed）、检索命中率、KG 规模/增长率、token 成本；
- 统计：3 seeds × 5 轮，配对 bootstrap；报告"第 5 轮 vs 第 0 轮"和"曲线是否单调"。

**"正向维护"的判定标准（先写死，避免事后解释）**：
1. `D_test` 的 FCR 或 S_C1 在第 5 轮显著高于 M0；
2. `D_regression` 回归率 ≤ 5%（或不超过基线）；
3. 新知识人工精度 ≥ 80%；
4. 更新采纳率不是 100%（说明门控在工作）；
5. 成本在预算内。

> 如果只满足 1 不满足 2，就是"越改越忘"，也是重要结论；如果都不满足，就写"反馈维护在 L1 算子/当前知识量下无效"——这仍然是一章诚实的实证。

### 3.4 自维护与 E8（bandit）的关系

- E8 是"学**动作选择**"（检索多少条、用哪个 prompt、是否修复）；
- 自维护是"学**知识本身**"（改条件/参数/新增策略）；
- 两者可以合并成"经验驱动闭环"，但**12 周内建议只做一个**：优先自维护（更贴论文主线），E8 作为未来工作或消融。
- 你现在的 E09 结果正好提供素材：8 个 repair 触发、7 个转正、1 个负例——这些都是自维护的**第一批轨迹**。

### 3.5 自维护的"低成本试点"（强烈建议先做）

在写整章前，先做 **10 个任务 × 1 轮** 的 pilot：
- 用 E09 已保存的 `round0/round1` 代码和结果，人工/LLM 总结 10 条更新；
- 写回 KG（版本 KG_1）；
- 在 S2 的 2 个算子上跑一次，看 FCR 是否变化；
- 若完全没变化，及时止损，把第二部分缩成"机制 + 负结果/未来工作"，不占用主实验时间。

- 时间不够 → pilot 先行，负结果降级为"机制 + 小规模验证"。

## 6. 答辩口径（三句话）

1. **第一部分**："我不是把方法跑在 OpenBLAS 上，而是从 OpenBLAS 构造了 OpOptBench 任务基准；对照组分三层：编译器/专家上下界、同 LLM 的 B0–B3、外部 AI 方法只做方法对照（架构不同不硬比数字）。"
2. **第二部分**："自维护不是让模型自我进化，而是让 Agent 在**冻结测试集**外积累经验、经门控写回版本化 KG；我用 5 轮学习曲线 + 回归率 + 知识精度证明它是不是正向。"
3. **边界**："如果某条不成立，我报告边界（例如 L1 算子编译器已饱和、B4 成本高但无正确性增量），不硬吹。"
