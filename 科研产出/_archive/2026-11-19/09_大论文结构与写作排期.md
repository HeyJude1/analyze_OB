## 1. 论文总体设计

### 1.1 一句话主线（写进摘要、引言、答辩开场，背下来）

> **LLM 写 BLAS 算子"正确性有余、性能不足"，根因不是模型不会写代码，而是"什么条件下该用哪条优化策略"这类知识以代码形态隐含在算子库里、不可检索。本文把同一算子的通用 C 实现与向量实现之间的差异，抽成带"适用条件—硬件约束—可调参数—性能证据—来源行号"的策略知识图谱，在生成前做条件过滤与冲突消解，再用 x86 + RISC-V 双真机回答：这种结构化知识相对扁平文本检索是否带来可测量的增量，以及它能否跨架构迁移、边界在哪。**

### 1.2 题目与副标题

- 主标题**不动**（按学院规定，重大调整才需重新开题）：**基于知识图谱的大语言模型自动生成高性能算子代码方法研究**
- 建议加副标题（不改变题目实质，答辩时解释为"研究范围限定"）：**——面向 BLAS 类稠密算子的优化知识建模与跨架构验证**
- 英文题目备用：*Knowledge-Graph-Driven LLM Code Generation for High-Performance Operators: Modeling, Conditional Retrieval and Cross-Architecture Validation*
- 若导师不同意加副标题：删掉副标题即可，**不影响任何章节安排**。

### 1.3 三个研究问题（对齐 08 §1.1，只换措辞）

| 编号 | 问题 | 主指标 | 章节 | 实验 |
|---|---|---|---|---|
| **Q1 知识表示与质量** | 如何从多架构 OpenBLAS 实现中抽取"策略—适用条件—硬件约束—性能证据"，并保证可溯源、可对齐？质量如何量化？ | 抽取/对齐 P/R/F1、120 条金标 κ、覆盖率、来源可追溯率 | 第 3 章 | E1 |
| **Q2 结构化知识的增量** | 按硬件条件检索并注入 LLM 后，生成代码的正确性与性能是否提升？相对**同 token 预算的扁平文本 RAG** 增量多少？ | `R=GM(B3)/GM(B2)`、FCR、S_comp、EGC、fast_p、token 成本 | 第 4、5 章 | E2、E3、E4、E6 |

### 1.4 三条贡献（保守、可辩护，答辩照这个说）

1. **一套面向 BLAS 算子的优化知识图谱构建方法**：以"通用 C 实现 vs 向量实现"的配对差异为**弱监督信号**，用静态规则 + 差分抽取做事实、LLM 只做命名与解释，产出带适用条件、硬件约束、可调参数、性能证据、来源行号的策略知识；给出 120 条人工金标的质量评估与一致性检验。
2. **一种硬件条件感知的策略检索与结构化注入方法**：计算流程指纹匹配 + 硬约束过滤 + 策略冲突消解 + 实施模板填充；在**同 LLM、同 token 预算、同尝试次数**下与扁平文本 RAG 对照，给出"图结构是否有独立增量"的受控证据。
3. **一组 x86 + RISC-V 真机的双平台实验与跨架构可迁移性分析**：不只报"生成了代码"，而报编译/四分布正确性/加速比/差距闭合度 EGC，并给出策略可迁移性的三层分类（架构无关 / 参数自适应 / 架构特定）与失败边界。

**写法纪律**：不写"首次""填补空白""国际领先"；不把"两阶段对齐""多层 Agent""结构化 Prompt"当创新点（它们是工程组件，写进实现）；贡献表述以"系统完整 + 实验扎实 + 分析可信"为主（专利已覆盖新颖性主张，`08` §1.2）。

### 4.4 "实验没跑完也能先写"的 8 个技巧

1. **先写方法、后写结果**：第 3、4 章（2.35 万字）只依赖"系统实现"和"方法设计"，不依赖实验结果——这两章在 W3–W9 就能写完，占全文 48%。
2. **"死表"先行**：把表 5-3/5-4/5-5 的表头、行标签、指标定义、单位先写死（模板见本文附录 A），实验一出数只填数字；填一张表 ≤30 分钟。
3. **图先定坐标与分组**：所有实验图用脚本从 `raw.jsonl`/CSV 生成（`figures/<exp>.png`），数据更新后重跑脚本，正文图注不用改。
4. **双版本段落**：对每个结果段先写"若 B3>B2"和"若 B3≈B2/B3<B2"两版解释（各 150–250 字），数据到了删一版——避免"等数据"空转。
5. **结果分析"三问法"**：每段先写"发生了什么（数字）→ 为什么（机制/归因）→ 说明什么（回答哪个 RQ/边界）"，第三问可以先写，第一问等数据填。
6. **实验日志当素材库**：周五 30 分钟的实验日志直接改写成 5.2/5.3 的段落，比回忆快 3 倍。
7. **先写"讨论"再写"结果"**：5.6 讨论（什么时候有用/没用）不依赖具体数字，W9 就可以写，它反过来决定结果段要重点报哪些数。
8. **不要等第二模型/第二平台**：E3 先出 1 个平台 × 1 个 seed 就能写 5.2 的 70%，第二平台/复现结果作为补充段落插入。

### 5.2 五个必问问题及回答要点

#### 问题 1："你的创新点是什么？"（必问）

- **本质**：评委在判断"够不够硕士论文"。不要背开题的三条"融合创新/方法创新/模式创新"。
- **30 秒回答**："三条，按可辩护强度排：第一，**方法上**用同一算子的通用 C 实现与向量实现的配对差异做弱监督，把专家优化决策抽成带适用条件、硬件约束、参数区间、性能证据和来源行号的策略知识，LLM 只做命名不做数字——这解决了知识'不可溯源、不可执行'的问题；第二，**机制上**把图谱做成生成前的硬约束过滤与冲突消解，这是扁平文本 RAG 表达不了的；第三，**实证上**给出 x86 + RISC-V 双真机的策略可迁移性分层结论。"
- **展开要点**：每条给 1 个证据（E1 的溯源率、E6 的 A1/A2 消融、E5 的三层表）；主动说明"两阶段对齐、结构化 Prompt 是工程组件，不算创新点"（显得诚实，且堵住追问）。
- **证据页**：P5（贡献）、P9（E1）、P14（消融）、P15（迁移）。
- **不要说**："首次""填补空白""国际领先""把 KG 和 LLM 结合"。

#### 问题 2："你和 QiMeng / MARCO 有什么区别？"（必问）

- **本质**：评委熟悉这两个名字，在查你是否读过最近工作、是否有真差异化。
- **30 秒回答**："任务和知识来源都不同。QiMeng-GEMM/Kernel 是**单架构族、单算子/GPU kernel**，硬件知识是人写的规则库，先宏观后微观提示，代码未公开；MARCO 是**通用代码优化**，知识来自实时网页检索，评测是 LeetCode 类题目，不是 HPC 算子，也没有跨架构。我们做的是**BLAS 类 CPU 稠密算子**，知识来自**同一算子库内两版实现的差异**（可溯源到行号），并且用 **x86 + RISC-V 真机**做跨架构受控测量——这是它们都没做的。"
- **展开要点**：给一张 5 行对比表（任务/知识来源/知识形态/是否跨架构/代码可得性）；补充"我们规模小（12 算子），所以不比较绝对性能，只比较机制和可迁移性"；提到 PRAGMA/KernelBlaster 时说明"它们是 GPU 路线、已开源，我们只在方法上引用"。
- **证据页**：P4（现状对比表）、P12（实验设计）。
- **不要说**："我们的性能超过它们"（没有同台比较，说了就是送分）。

#### 问题 3："性能不如 OpenBLAS，你的方法有什么意义？"（必问，最危险）

- **本质**：评委在检验你是否清醒、是否诚实、论文定位是否站得住。
- **30 秒回答**："**我们从不声称超过 OpenBLAS**，论文里只报三个口径：相对输入 `-O2`、相对编译器 `-O3`、以及相对 OpenBLAS 的百分比与差距闭合度 EGC。OpenBLAS 是二十多年人工 + 汇编调优的上界；本文的目标不是刷新 SOTA，而是**把一次性的专家优化转成可检索、可约束、可迁移的知识**，衡量的是'生成代码向专家实现闭合了多少'以及'换一个架构还成不成立'。"
- **展开要点**：① 成本对比："专家写一个 dgemm 微内核要数天到数周，生成只要分钟级，二者不是同一赛道"；② 给出 EGC 与 `fast_1.25` 的真实数字（如果不好看，如实说）；③ 说明"L1 算子被 `-O3` 吃掉大半，我们的增益集中在 L2/L3——这本身就是有价值的边界结论"；④ 若追问"那谁会用"：答"会用库里已有的知识做新架构的冷启动，比如 RISC-V 上缺专家时"。
- **证据页**：P13（主结果）、P14（消融）、P18（局限）。
- **不要说**："因为模型小/数据少"（找借口）；也不要说"我们的方法更通用"（无证据）。

#### 问题 4："你这个知识图谱，不就是 RAG 吗？"（必问）

- **本质**：评委在判断"图"是不是包装。这是全文最需要提前准备的一问。
- **30 秒回答**："检索这一步确实是 RAG 的近亲，但**图不是用来多检索几条文本的**。我们的图谱让三种操作成为可能：①按目标架构的 ISA/寄存器/缓存做**硬约束过滤**——不满足的策略直接不进 prompt，扁平 RAG 只能靠 LLM 自己从文本里判断；②按 `CONFLICTS_WITH` 边做**冲突消解**——比如两个寄存器分块策略不能共存，扁平 RAG 给不出这个约束；③参数由硬件参数**推导**（VLMAX/LMUL/展开因子）。论文里的 A1 消融就是**同内容、同 token、只改组织形式**，如果 B3 比 B2 好，增量只能来自结构。"
- **展开要点**：给"扁平 RAG 能/不能"对照表（图 2-2、表 4-2）；主动说"如果 A1 结果显示没有增量，我们会如实报告'结构无独立价值'，并把它写成边界结论"（体现科学性）；若被问 GraphRAG：答"GraphRAG 面向社区摘要式问答，我们面向代码生成的可执行约束，检索单元从'文本块'变成'策略卡+条件+模板'"。
- **证据页**：P10/P11（方法）、P14（A1 消融）、备用页（能力对照表）。
- **不要说**："我们的图更大/更全"（规模不是理由）。

#### 问题 5："工作量够不够？系统完成度怎么样？"（必问）

- **本质**：专硕答辩核心关切。要拿数字说话，不要空谈辛苦。
- **30 秒回答**："系统侧：45 个 OpenBLAS 算子语料、12 个实验算子、11 实体/15 关系的 Schema v2、6 段抽取流水线、四通道检索、B0–B3 生成闭环、双平台验证 harness；数据侧：120 条人工金标 + 数千次生成/编译/运行 + 双真机计时；论文侧：4.9 万字、26 图 21 表、6 组实验。系统原型在开题前已完成约 70%，本论文的新增工作是**接线（KG→prompt）、补对照（B2）、做测量（E1–E7）、写论文**——不是重复建设。"
- **展开要点**：给一张"模块—规模—状态"表（代码模块数/行数、KG 节点边数、实验次数、图表数）；提专利（已发）与系统演示作为工程产出；**诚实说明"系统是前期积累"**——评委更反感把已有系统全算成本论文工作量，坦诚反而加分。
- **证据页**：P6（技术路线）、P8（Schema）、P12（实验设计）、P17（贡献总结）。
- **不要说**："代码都是我一个人写的"（无法核实，且显得不成熟）；也不要把开源库/导师课题的成果算成自己的。

## 6. 查重、格式与写作风格

### 6.1 避免"AIGC 味"与查重风险的 7 条做法

> 背景：2025 年起多校在答辩前增加 AIGC 检测，且**开题报告可能被纳入比对库**。第 1、2 章是重灾区。

1. **先写自己的中文草稿，再看资料**：每节先合上所有文档，用自己的话写 300 字"我认为这一节要说什么"，然后再查资料补细节——顺序反过来必然写成"翻译体"。
2. **每段必须有"三件套"之一**：具体数字、具体案例、具体引用。没有这三样的段落，删掉或合并。
3. **禁用/限量套话**：首先/其次/最后、综上所述、值得注意的是、不仅……而且、随着……的发展、具有重要的理论意义和实际价值。每千字最多出现 1 次。
4. **拆长句、去排比**：AIGC 文本平均句长偏长、四字短语密集。把 60 字以上的句子拆成两句；每段不超过 5 行。
5. **保留个人判断句**："本文认为……""我们选择 X 而不是 Y，原因是……""这个结果与预期不符，可能的解释是……"——这些是 AIGC 不会写的。
6. **图表全部自制**：不截图他人论文/网页；用论文数据重新画（图注写"数据来源：E3"或"作者自绘"）；表格用三线表、自己排版。
7. **与开题报告"物理隔离"**：第 1 章的选题背景、第 2 章的文献综述**不要复制开题原文**，重新组织论证顺序（开题按"领域发展"写，论文按"问题—差距—本文"写）；引用同一篇文献时换叙述角度。

**查重操作**：W11 用学校指定系统（知网/维普，以学院通知为准）自查一次；目标总文字复制比 <15%（学校常见阈值 15%–20%，**待核实**）；单章最高不超过 25%；查重前删除"修订痕迹/批注"，把大段代码移入附录；引用规范用 GB/T 7714-2015 顺序编码制，正文角标与文后条目一一对应。
