# 22 知识图谱（第一部分）完整构建指南

> 2026-11-15｜Lead｜目标：把"高性能算子编写经验"做成一个**能查询、能约束、能追溯、能复现**的知识图谱。
> 这份文档从"建什么"讲到"怎么建、怎么验、怎么用、怎么答辩"，你可以按它一步步执行。
> 当前 `科研产出/kg_agent/` 已经实现了下面这套流程；这份文档既是设计说明，也是你的执行清单。
> **补充**：文献依据、检索机制的原理与对照实验、三层评测协议，看 [`23_知识图谱构建_检索与评测.md`](23_知识图谱构建_检索与评测.md)。本文偏"怎么做"，23 偏"为什么这么做、怎么证明它有用"。

## 0. 先明确：你要建的到底是什么

不是画一张图，也不是做一个向量数据库。你要建的是：

> **把"某个算子在某种硬件上，为什么这样写更快"拆成一条条可执行的策略，并让每条策略都带：适用条件、参数、代码模板、性能证据、来源行号。**

所以一个合格的知识图谱必须有四样东西：

1. **实体**：算子、计算流程、代码特征、优化策略、模板、参数、硬件、证据、来源……
2. **关系**：谁属于谁、谁优化谁、谁在什么条件下适用、谁和谁冲突、谁和谁可以组合……
3. **条件**：不是"循环展开更好"，而是"当数据类型是 double、步长为 1、循环深度 ≥1、尺寸为大时，循环展开 4 次更好"。
4. **证据**：这条策略来自哪个文件的哪一行、有没有性能日志、是模拟器还是真机、置信度多少。

没有条件和证据的，叫"知识清单"；有条件、有证据、能被程序求值的，才叫"可执行知识图谱"。

## 1. 目标与边界

### 1.1 这个图谱要能回答的 10 个问题

建之前先写死"能力问题"，建完逐条检查：

1. 给定一个算子（如 daxpy），它由哪些计算流程组成？
2. 给定一个优化策略（如循环展开），它在哪些算子、哪些硬件上适用？
3. 给定代码特征（dtype、步长、循环深度、尺寸），哪些策略满足硬条件？
4. 给定目标硬件（RISC-V RVV 256 位、32 个向量寄存器），哪些策略可用？
5. 给定一条策略，它的参数（展开因子、分块大小、LMUL/SEW）取多少？
6. 给定一条策略，它的代码模板长什么样、要改哪些循环？
7. 两条策略能不能组合？有没有冲突（寄存器不够、顺序不对）？
8. 这条策略的性能证据是什么？来自哪个日志/哪次真机测量？置信度多少？
9. 这条策略来自哪个实现文件、哪一行？能不能回溯？
10. 同一条策略在 x86/ARM/RISC-V 上分别怎么实现、参数怎么变？

### 1.2 不做什么

- 不覆盖 GPU/CUDA（你的硬件是 x86 + RISC-V，ARM 只做知识）；
- 不做"全自动调参器"（参数是知识推导 + 小范围验证，不是搜索整个空间）；
- 不替代编译器（-O3 是基线，不是敌人）；
- 不追求"所有 BLAS 算子"，先 12 个，做深做透。

## 2. 本体设计：实体、关系、条件、字段

### 2.1 十二类实体（节点）

| 实体 | 作用 | 例子 | 必填字段 |
|---|---|---|---|
| 算子 | 任务对象 | daxpy、dgemm、ddot | 名称、层级、dtype、语义 |
| 计算流程 | 算子的阶段/模式 | 主循环、尾部处理、打包、写回 | 名称、阶段、父算子 |
| 代码特征 | 代码的静态属性 | dtype=d、步长 1、循环深度 3 | 特征名、值、来源 |
| 优化策略 | 一条优化动作 | 向量化、循环展开、分块、预取 | 名称、动作、条件、参数、模板 |
| 实施模板 | 策略对应的代码骨架 | vsetvl 循环 + vle/vfmacc/vse | 槽位、语言、阶段 |
| 可调参数 | 策略的参数 | 展开因子、块大小、LMUL、SEW | 名称、类型、范围、推导式 |
| 硬件画像 | 目标硬件 | K1（RVV 1.0，VLEN=256） | ISA、向量宽度、寄存器数、缓存、频率 |
| 指令集能力 | 硬件支持的 ISA | RVV 1.0、AVX2、NEON | 名称、版本、向量宽度 |
| 微架构 | 具体微架构 | K1、Haswell、Cortex-A57 | 名称、寄存器、缓存、流水线 |
| 性能证据 | 日志/实测结果 | QEMU 日志、真机计时 | 来源、指标、置信度、是否需重跑 |
| 来源 | 文件/行号 | `daxpy_k_rvv.c:46-213` | 路径、sha256、起止行 |
| 失败案例 | 失败原因 | 只取 lane0 未做归约 | 现象、原因、修复、关联策略 |

> 初期可以只建前 8 类；失败案例和性能证据在实验阶段补。不要一上来 12 类全做，容易卡住。

### 2.2 十四类关系（边）

| 关系 | 起点 → 终点 | 含义 | 例子 |
|---|---|---|---|
| 算子有计算流程 | 算子 → 计算流程 | 这个算子由哪些阶段组成 | dgemm → 主循环/打包/尾部 |
| 流程有代码特征 | 计算流程 → 代码特征 | 这个阶段的静态属性 | 主循环 → 循环深度 3 |
| 流程被策略优化 | 计算流程 → 优化策略 | 哪些策略作用于这个阶段 | 主循环 → 分块/展开 |
| 策略适用于条件 | 策略 → 条件谓词 | 什么条件下可用 | dtype=d、步长=1 |
| 策略有模板 | 策略 → 实施模板 | 代码怎么写 | 向量化 → vsetvl 模板 |
| 策略有参数 | 策略 → 可调参数 | 参数是什么 | 分块 → 块大小 |
| 策略需要指令集 | 策略 → 指令集能力 | 依赖哪个 ISA | 向量化 → RVV 1.0 |
| 策略面向微架构 | 策略 → 微架构/硬件 | 在哪个硬件上验证 | 向量化 → K1 |
| 策略有证据 | 策略 → 性能证据 | 性能证据 | 展开 4 次 → 日志 |
| 证据来自来源 | 证据 → 来源 | 日志/文件在哪 | 日志 → 文件行号 |
| 策略泛化到 | 策略 → 策略 | 同族/跨架构抽象 | x86 展开 → RVV 展开 |
| 策略可与…组合 | 策略 → 策略 | 可组合、有顺序 | 分块 + 打包 |
| 策略与…冲突 | 策略 → 策略 | 互斥/资源冲突 | 两个分块抢寄存器 |
| 策略在架构上实现 | 策略 → 架构实现 | 同一策略的不同架构版本 | 向量化 → x86/ARM/RVV |

> "冲突"和"组合"边很关键：没有它们，检索出来的策略会互相打架。

### 2.3 十个条件谓词（把"适用"变成程序能算的）

| 谓词 | 含义 | 例子 |
|---|---|---|
| dtype | 数据类型 | `dtype in [d, s]` |
| stride_x / stride_y | 访存步长 | `stride_x == 1` |
| loop_depth | 循环嵌套深度 | `loop_depth >= 2` |
| size_regime | 尺寸档 | `size_regime in [medium, large]` |
| aligned | 是否对齐 | `aligned == true` |
| tail_divisible | 尾部是否整除 | `tail_divisible == false` |
| reduction | 是否归约 | `reduction == true` |
| structural | 结构特征 | `structural == none` |
| isa | 指令集 | `isa has AVX2` |
| vector_bits / vector_regs | 向量宽度/寄存器数 | `vector_bits >= 256`、`vector_regs >= 16` |

> 条件必须是闭集词表，不能写自然语言"适合大矩阵"；否则程序无法过滤。

### 2.4 策略卡（最重要的数据结构）

一条策略不是一句话，而是这样一张卡：

```json
{
  "id": "策略:向量化:daxpy",
  "名称": "RVV 向量化主循环 + 尾部处理",
  "动作": "向量化",
  "阶段": "主循环",
  "适用条件": [
    {"谓词": "dtype", "运算": "in", "值": ["d", "s"], "硬条件": true},
    {"谓词": "stride_x", "运算": "==", "值": 1, "硬条件": true},
    {"谓词": "stride_y", "运算": "==", "值": 1, "硬条件": true},
    {"谓词": "loop_depth", "运算": ">=", "值": 1, "硬条件": true}
  ],
  "硬件条件": [
    {"谓词": "isa", "运算": "has", "值": "RVV 1.0"},
    {"谓词": "vector_bits", "运算": "==", "值": 256}
  ],
  "参数": {"LMUL": 8, "SEW": 64},
  "代码模板": "模板:向量化:daxpy",
  "证据": ["证据:QEMU:daxpy:16384"],
  "来源": {"文件": "daxpy_k_rvv.c", "起": 46, "止": 213, "sha256": "..."},
  "跨架构范围": "参数化（x86/ARM/RVV 同族，参数不同）",
  "置信度": 0.8,
  "状态": "已验证"
}
```

> 关键点：**条件、参数、模板、证据、来源，五样缺一不可**。只写"向量化更快"的不是知识，是口号。

## 3. 数据从哪里来

### 3.1 语料：OpenBLAS 的 12 个算子

| 层级 | 算子 | 通用实现 | 优化实现（示例） |
|---|---|---|---|
| 向量类 | daxpy、dasum、ddot、dscal、dnrm2、daxpby | `*_k.c` | `*_k_rvv.c`、x86/ARM kernel |
| 矩阵-向量 | dgemv、dsymv、chemv | `*_k.c` | RVV/NEON/AVX 版本 |
| 矩阵-矩阵 | dgemm、dsymm、dtrmm | `*_k.c` | RVV/AVX512/NEON/SVE 版本 |

### 3.2 配对规则

每个算子至少要有两版：

1. **通用版**：没有针对硬件优化的 C 实现（作为输入、作为差分基准）；
2. **优化版**：某个架构上专家写的实现（作为知识来源、作为性能上界）。

配对时要记录：

- 文件路径、版本（OpenBLAS v0.3.27）、sha256；
- 函数签名、参数语义；
- 起止行号；
- 语言（C/汇编）；
- 架构（x86/ARM/RISC-V）、ISA、微架构。

### 3.3 数据划分（防泄漏）

- **建图算子**：6 个，用来抽知识；
- **留出算子**：6 个，不参与建图、不参与调参，只用来测试"跨算子泛化"；
- 同一算子的不同尺寸不算不同算子；留出算子绝不能出现在知识库里。

### 3.4 许可与引用

OpenBLAS 是 BSD-3；论文里写清版本、来源、许可；仓库保留 LICENSE/NOTICE。

### 3.5 以 GEMM 为例：每个架构到底要准备哪些版本

建图不是"每个架构随便找一个实现"，而是每个架构都要有一条**从简单到优化的阶梯**，这样"差分"才能抽出策略。

**CPU（x86 / ARM / RISC-V）建议准备 3 层：**

| 层 | 作用 | 例子 |
|---|---|---|
| ① 朴素参考 | 语义基准、最低优化 | 三重循环 `C[i][j] += A[i][k]*B[k][j]` |
| ② 架构无关优化 C | 抽出高层策略（分块/打包/循环序） | OpenBLAS `kernel/generic` 的 GEMM 微内核、BLIS 通用 C 版本 |
| ③ 架构特定优化 | 抽出向量化/寄存器分块/展开/预取 | x86：`dgemm_kernel_4x8_haswell.S`、`dgemm_kernel_*_skylakex.c`；ARM：`dgemm_kernel_4x4_cortexa53.c`、SVE kernel；RISC-V：`gemmkernel_rvv_v1x8.c`、`dgemm_kernel_8x8_zvl256b.c` |

差分是**分层做的**：
- ①→② 抽出"分块、打包、循环重排、cache 分块"这类高层策略；
- ②→③ 抽出"向量化、寄存器分块、展开、预取、尾处理"这类架构相关策略。

> 如果只拿 ① 和 ③ 比，会漏掉"② 已经做了的高层策略"；如果只拿 ② 和 ③ 比，会认为"分块/打包"不是策略。所以要三层。

**GPU（如果要做）也要三层：**

| 层 | 作用 | 例子 |
|---|---|---|
| ① 朴素 CUDA | 一个线程算一个输出，只用全局内存 | CUDA samples `matrixMul` |
| ② 共享内存分块 | 抽出 shared memory tiling、线程块协作 | CUDA samples `matrixMulShared` |
| ③ 寄存器分块/库级优化 | 抽出 register tiling、warp tiling、pipeline、tensor core | CUTLASS GEMM、cuBLAS 作为性能参照（闭源，只作上界） |

**注意：CPU 的通用 C 不能当 GPU 的参考实现**。GPU 的"朴素版"必须是 CUDA kernel；否则语义和编程模型都不对。

### 3.6 要不要把 GPU 放进建图范围？

先分清导师说的"提 CUDA"是哪一种：

| 方案 | 做什么 | 工作量 | 风险 |
|---|---|---|---|
| A. CPU 主线 + CUDA 只在相关工作/展望提 | 知识图谱只建 CPU（x86/ARM/RISC-V）；GPU 作为未来工作 | 最小 | 导师可能觉得"没做 GPU" |
| B. CPU 主线 + 一个 CUDA GEMM 案例 | 只对一个算子做 2–3 个 CUDA 版本（朴素/共享内存/寄存器分块），作为"架构可扩展性"案例，不进主实验 | 中等 | 需要 NVIDIA GPU 和 CUDA 环境 |
| C. CPU + GPU 全量建图与实验 | 两个代码生成器（C 和 CUDA）、两套 benchmark、两套性能实验 | 约 2 倍 | 2–3 个月大概率做不完 |

**建议**：除非你已经有 NVIDIA GPU 且导师明确要求"GPU 实验"，否则选 **A 或 B**。论文里可以写"知识表示预留了 GPU 架构维度，本文实验覆盖 CPU/RISC-V，GPU 作为案例/未来工作"——这是诚实且有说服力的。

> 关键：生成 CPU 代码和生成 CUDA 代码是两条不同的生成链路（模板、编译、测试都不同）。不要承诺"一个模型同时生成 CPU 和 GPU 高性能代码"，除非你真的做了两套。

## 4. 构建流程：七步，每步都有输入/输出/验收

### 第一步：语料清单（把文件收齐、登记）

- **做什么**：扫描 OpenBLAS 源码，把 12 个算子的通用版/优化版复制到统一目录；记录路径、sha256、架构、行号。
- **输出**：`corpus_manifest.jsonl`（每个文件一行）。
- **验收**：12 个算子都有通用版；至少 8 个算子有 ≥2 个架构的优化版；sha256 可复核。
- **常见坑**：文件名相近但不是一个算子；汇编/内联汇编要单独标语言。

### 第二步：静态特征（能算的绝不让模型猜）

- **做什么**：对每个实现抽：
  - C 代码：intrinsic（`_mm256_*`、`vfmacc`、`svfloat64`）、循环层数、展开因子、打包/拷贝、预取、对齐假设；
  - 汇编：指令助记符（`vfmadd`、`vmla`、`prefetch`）、向量宽度、寄存器分块线索。
- **输出**：`characteristics.jsonl`（每个实现一条）。
- **验收**：每条特征能指回文件行号；不出现"大概/可能"。
- **常见坑**：把注释当代码；把宏展开后的代码漏掉。

### 第三步：差分（核心步骤）

- **做什么**：同一个算子的"通用版"和"优化版"逐段对比，记录：
  - 多了哪些 intrinsic；
  - 循环展开从几变几；
  - 累加器/分块/打包怎么变；
  - 尾部处理怎么加；
  - 数据布局怎么改。
- **输出**：`diffs.jsonl`（每条差分带 before/after 行号）。
- **验收**：每条差分能指出"改之前在哪、改之后在哪、改了什么"。
- **常见坑**：只对比函数名；忽略宏/模板；把不同算子的文件配错。

**例子（daxpy）**：
- 通用版：`while(i<n){ y[i] += da*x[i]; i++; }`
- 优化版：`vsetvl` 求向量长度 → `vle64` 读 x/y → `vfmacc` 乘加 → `vse64` 写回 → 尾部标量处理。
- 差分结论：向量化 + 尾部处理 + LMUL/SEW 参数化；条件：dtype=d、步长=1、循环深度≥1；硬件：RVV 1.0、VLEN=256。

### 第四步：策略抽取（规则抽事实，模型只命名）

- **做什么**：
  - 规则先给每条差分起"动作名"（向量化/分块/展开/预取/尾部处理/打包/布局）；
  - 大模型只写"为什么这样改能提速""适用条件怎么表述"；
  - **硬约束**：模型不许写性能数字、硬件数值、文件名；JSON 格式校验失败就重试。
- **输出**：`strategies_raw.jsonl`（策略草案）。
- **验收**：每条策略有动作、条件、参数、模板、来源；性能数字只能来自日志。
- **常见坑**：让模型"读代码猜策略"→ 幻觉；让模型写"提升 30%"→ 不可信。

### 第五步：规范化与跨架构对齐

- **做什么**：
  - 统一策略 ID 和名称（同义合并）；
  - 同一条策略在不同架构上合并成一条，但保留各架构参数；
  - 标注跨架构范围：
    - **架构无关**：如"减少访存"；
    - **参数化**：同族但参数不同，如向量宽度 128/256/512、展开 4/8；
    - **架构特定**：如 `vfmacc`、`prefetch`、掩码尾处理。
- **输出**：最终策略和模板（当前规模：262 条策略、262 个模板、30 条跨架构共有策略）。
- **验收**：同族策略能对齐；参数按架构保留；不会把 x86 的展开因子硬套到 RVV。
- **常见坑**：只按名字合并，导致不同策略被误合并；参数被覆盖。

### 第六步：证据挂接

- **做什么**：
  - 解析 QEMU 日志/真机计时，生成性能证据节点；
  - 标清楚：来源、指标、置信度、是否需重跑；
  - 模拟器证据只用于正确性，不参与性能排序；负例也要保留（如某些算子专家实现反而更慢）。
- **输出**：`evidence.jsonl`（当前 88 条证据）。
- **验收**：每条性能数字都能指回日志/实测；没有"模型编的性能"。
- **常见坑**：把 QEMU 计时当性能；只留正例不留负例。

### 第七步：校验、导出、版本化

- **做什么**：
  - 校验：ID 唯一、边两端存在、类型在闭集、条件谓词合法、冲突边对称、模板槽位完整；
  - 导出：节点文件、边文件、清单（版本 + 输入 sha256）；
  - 版本化：每次构建记录版本四元组（schema/抽取器/提示词/数据），两次构建字节级一致。
- **输出**：`nodes.jsonl`、`edges.jsonl`、`manifest.json`、`arch_coverage.json`。
- **验收**：校验 0 错误；可离线重建；manifest 能审计。
- **常见坑**：只存图不存来源；版本漂移；构建不可重复。

## 5. 一条完整策略卡（daxpy 例子）

```json
{
  "id": "策略:向量化:daxpy",
  "名称": "RVV 向量化主循环 + 尾部处理",
  "动作": "向量化",
  "阶段": "主循环",
  "适用条件": [
    {"谓词": "dtype", "运算": "in", "值": ["d", "s"], "硬条件": true},
    {"谓词": "stride_x", "运算": "==", "值": 1, "硬条件": true},
    {"谓词": "stride_y", "运算": "==", "值": 1, "硬条件": true}
  ],
  "硬件条件": [
    {"谓词": "isa", "运算": "has", "值": "RVV 1.0"},
    {"谓词": "vector_bits", "运算": "==", "值": 256}
  ],
  "参数": {"LMUL": 8, "SEW": 64},
  "代码模板": "模板:向量化:daxpy",
  "证据": ["证据:QEMU:daxpy:16384"],
  "来源": {"文件": "daxpy_k_rvv.c", "起": 46, "止": 213, "sha256": "..."},
  "跨架构范围": "参数化",
  "置信度": 0.8
}
```

**为什么这条能叫"知识"**：
- 条件明确（dtype/步长），程序能判断是否适用；
- 参数明确（LMUL/SEW），不是"看着办"；
- 模板明确（vsetvl 循环），模型知道怎么改；
- 证据明确（日志），不是"我觉得"；
- 来源明确（文件行号），可复核。

## 6. 建完怎么用：七步检索

1. **识别计算流程**：算子 → 主循环/尾部/打包；
2. **召回策略**：沿"流程被策略优化"的边，把所有可能策略拉出来；
3. **条件过滤**：用代码特征逐条判断硬条件，不满足就淘汰；
4. **硬件过滤**：ISA/向量宽度/寄存器数不满足就淘汰；
5. **冲突消解**：同族去重、检查冲突边、算寄存器预算；
6. **打分排序**：匹配度、适用度、硬件契合、证据强度、支持度；
7. **组装策略包**：取前几条，带上条件、参数、模板、证据、来源，交给生成模型。

**为什么不是普通文本检索**：
- 文本检索只能"找相似段落"；它不知道"这条策略需要 AVX512，而你是 AVX2"；
- 图谱能精确过滤、能算参数、能查冲突、能回溯来源；
- 这就是"结构化知识"相对"扁平文本"的增量所在。

## 7. 质量怎么保证

### 7.1 构建期校验

- 节点 ID 唯一；边两端存在；类型在闭集；
- 条件谓词和值域合法；冲突边对称；模板槽位完整；
- 每条策略至少 2 个可执行条件 + 模板 + 来源 + 硬件绑定。

### 7.2 人工金标准

- 抽 6 个建图算子、120 条策略，2 人独立标注：
  - 条件对不对；
  - 参数合不合理；
  - 模板能不能落地；
  - 来源对不对。
- 计算精确率/召回率/F1 和标注一致性（κ）。

### 7.3 覆盖与一致性

- 覆盖率：12 个算子 × 架构 × 策略族，哪些空着；
- 一致性：同义策略是否合并、参数是否冲突、跨架构是否对齐；
- 证据率：多少策略有日志/实测，多少只有源码证据。

### 7.4 可复现

- 每次构建记录版本四元组和输入 sha256；
- 两次构建字节级一致；
- 每个节点/边能回指来源文件和行号。

## 9. 怎么用实验验证这个图谱

### 9.1 知识质量

- 抽 120 条人工金标准，算精确率/召回率/F1、溯源率、覆盖率；
- 证明"知识不是编的"。

### 9.2 策略推荐（不执行代码）

- 给代码+硬件，看推荐的前 5 条里有多少是专家认可的；
- 指标：命中率、nDCG、可适用率。

### 9.3 生成效果（执行代码）

- x86 和 RISC-V 两平台；
- 对照：输入代码 -O2、编译器 -O3、OpenBLAS 专家、零样本、硬件提示、扁平文本、结构化图谱；
- 指标：编译通过率、功能正确率、相对 -O3 加速比、相对 OpenBLAS 百分比、差距闭合度、成本；
- 至少 3 次重复，报告均值和方差。

### 9.4 消融

- 去掉条件过滤、去掉硬件过滤、去掉参数、去掉模板、去掉冲突消解、把图换成随机子图；
- 看每一项对正确率/加速比的影响；
- 证明"增量来自图结构，不是多给文字"。

### 9.5 跨架构迁移

- 用 x86 学到的知识去生成 RISC-V 代码，反过来也做；
- 看哪些策略能迁（架构无关/参数化），哪些不能（架构特定）；
- 这是你论文最有特色的实验。

## 12. 答辩最可能问的 8 个问题

1. **"这和普通知识库/向量检索有什么区别？"**
   → "普通检索给相似文本；我给的是带条件、参数、模板、证据的策略卡，能精确过滤、能算参数、能查冲突、能回溯。"
2. **"知识从哪来，会不会是模型编的？"**
   → "结构事实来自差分/规则/日志，模型只负责命名和解释；每条策略有文件行号和证据。"
3. **"为什么不用 Neo4j？"**
   → "862 节点、3656 边，JSONL + 索引足够；离线、可复现、可版本化，部署简单。"
4. **"怎么保证不是背测试集？"**
   → "建图 6 个算子，留出 6 个只测试；留出算子不进知识库、不进提示词。"
5. **"知识图谱真能提升性能吗？"**
   → "不是定理，是机制：提高可行策略比例、参数准确率、减少冲突；用消融逐条验证，不成立就报边界。"
6. **"工作量在哪？"**
   → "70 个实现配对、112 个输入 sha256、262 条策略/模板、120 条金标准、双平台约 1000 次生成/编译/运行、可复现包。"
7. **"和 QiMeng 比呢？"**
   → "它做 GEMM + 提示搜索，baseline 是零样本/思维链/库；我做多算子 + 结构化知识 + 跨架构，对照更系统。"
8. **"如果效果不好怎么办？"**
   → "报告边界：哪些算子/条件下有效，哪些无效；负结果也是贡献。"
