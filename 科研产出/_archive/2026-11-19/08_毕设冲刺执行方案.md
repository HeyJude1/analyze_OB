### 2.4 你已经有的 RISC-V 数据（Lead 已解析，先看结论）

Lead 已写脚本解析了 `openblas_newtest1` 下 **44 个算子**的 `*_log.txt`（结果在 `科研产出/data/riscv_log_summary.csv`，脚本 `科研产出/tools/parse_riscv_logs.py`）：

| 事实 | 结论 |
|---|---|
| 日志格式 | 每个尺寸给出 `Ref MFlops/Time` vs `Migration MFlops/Time` + `Speedup` + `pass` + `max_diff`，末尾有 Average/Max/Min |
| 通过率 | **44/44 算子全部 pass**（正确性回归全过） |
| Migration vs Ref | 跨算子几何平均中位数 ≈ **1.01**；最好 dgemv 2.57、dsymm 2.45、dgemm 2.20；最差 idmin/idmax/idamax/idamin ≈ **0.18–0.20**、zdotu 0.52、dnrm2 0.56 |
| **关键问题** | `_command.txt` 里的运行命令包含 **`qemu-riscv64`**（44/44 都有），且 2×2 的 chbmv 耗时 2.1 ms——这是模拟器的量级。**所以这批日志不是真机性能，只能当正确性回归与格式参考。** |

**因此 E4 的正确做法**：
1. 复用日志的"解析器 + 正确性判定 + max_diff"逻辑；
2. **在真机上重跑** C0/C1/P1 与 LLM 生成代码（QEMU 结果只写"功能验证"一节，不能写"加速比"）；
3. 那 4 个 0.18× 的算子是很好的"反面案例"——说明"提取出来的专家实现"并不天然更快，正好用来论证"为什么需要带性能证据的 KG"；
4. 真机重跑前，先在板上用同一套 harness 跑 P1（OpenBLAS 库）确认量级（如 dgemm 256 应在几十 ms 级，而不是 QEMU 的百 ms 级）。

### 3.2 实验条件（6 个主条件）

| 编号 | 条件 | 说明 |
|---|---|---|
| **C0** | 输入代码（`-O2`） | 基线 1.0；定义"没优化" |
| **C1** | 编译器 `-O3 -march=<native/rv64gcv>` | **最重要下界**：回答"是不是只赢在 O3" |
| **P1** | 专家实现（OpenBLAS / RVV kernel） | 性能上界与 EGC 分母 |
| **B0** | LLM 零样本（只给代码 + 硬件描述） | 无知识下界 |
| **B1** | LLM + 硬件信息（无策略知识） | 分离"知道硬件"与"有策略知识" |
| **B2** | LLM + 扁平文本 RAG（同 token 预算） | **核心对照**：回答"这不就是 RAG 吗" |
| **B3** | LLM + 完整 KG（条件过滤 + 冲突消解 + 模板） | 主方法 |

> 公平性硬约束：同 LLM、同温度/最大 token、同尝试次数（每任务 3 个候选）、B2 与 B3 注入内容 token 差 ≤10%、同样的编译与计时口径。

### 3.3 E1：KG 质量（第 3 章的核心证据）

- **金标构造**：从 S1 的 6 个算子的 x86/RVV 优化实现里，人工标注 **120 条事实**：60 条策略实体（名称/层级/家族/实施方式/适用条件/硬件约束/参数）、40 条关系、20 对同义实体。
- **标注人数**：你 + 1 名同门（或导师抽检 30 条）；报告 Cohen's κ（目标 ≥0.7）。
- **指标**：
  - 实体抽取 P/R/F1（按类型）；
  - 关系抽取 P/R；
  - 实体对齐 P/R（20 对金标）；
  - 策略覆盖率（金标策略被 KG 覆盖的比例）；
  - 来源可追溯率（每条知识能回指文件 + 行号的比例）；
  - 去重率 `1 - |E_canonical|/|E_raw|`。
- **消融 A0**：不用"差分 + 静态规则"、直接让 LLM 读单版本代码抽取，比较 F1 与溯源率——证明你的抽取方法不是多此一举。

### 3.4 E2：策略推荐（第 4 章前半，且不依赖代码生成是否成功）

- **任务**：给定算子代码 + 目标硬件 profile（x86 AVX2 / RISC-V RVV1.0 VLEN=256），输出 top-5 适用策略及参数建议。
- **金标**：对每个算子的专家实现，用规则/AST 检测器自动判定所用策略（出现 RVV intrinsic → 向量化；`vsetvl` → 可变长向量；循环步长 → 展开；pack/copy → 分块；prefetch → 预取；tail 分支 → 尾处理），再人工抽检 30%。
- **条件**：B0 / B1 / B2 / B3（同一 LLM）。
- **指标**：P@5、R@5、nDCG@5、**策略可适用率 SAR**（人工判 top-5 中确实适用的比例）、**参数有效性 PIV**（推荐参数落在专家参数 ±50% 内的比例）。
- **跨架构应用**：分别在 x86 与 RVV 两个 profile 上做 E2——这是 E5 的数据基础。
- **预期**：B3 的 R@5 比 B2 高 10–20 个百分点；即使生成实验失败，这一章也成立。

### 3.5 E3：代码生成（x86 真机，第 4–5 章主实验）

- **任务**：输入 `generic.c` + 硬件 profile + 接口契约 + 约束（禁止调用 BLAS、单线程/4 线程二选一），输出单个 C 文件。
- **条件**：C1、P1、B0、B1、B2、B3（6 条）。
- **规模**：12 算子 × 3 尺寸（如 64/256/1024 或按算子定）× 3 seeds × 6 条件 = 648 次生成/运行（LLM 调用约 2000 次，成本可控）。
- **指标**：
  - 编译通过率 CR、四分布功能正确率 FCR（D1 随机 / D2 不规则尺寸 / D3 参数边界 / D4 数值极端）；
  - `S_C0`（相对输入）、`S_C1`（相对编译器，**主报告口径**）、`S_P1`（相对专家）；
  - **EGC 差距闭合度** `E = (T_C0 − T) / (T_C0 − T_P1)`；
  - fast_p（p=1.0/1.25/1.5）、峰值利用率、token 成本；
  - 失败类型分布（编译/数值/边界/超时/作弊）。
- **反作弊**：隐藏测试；禁止 `cblas_/openblas_/mkl`；内存上限 2×；抽 10% 代码人工 review；对 6 个算子做匿名化对照（去掉算子名/签名，检验是否靠记忆）。

### 3.6 E4：代码生成（RISC-V 真机，第 5 章跨架构核心）

- 同 E3 的任务，但目标平台是 RVV 真机；输入硬件 profile 换成 RVV 规格（VLEN=256、LMUL、RVV 1.0、可用 intrinsic）。
- 条件：C1、P1、B0、B1、B2、B3。规模可减半：12 算子 × 2 尺寸 × 3 seeds。
- 流程：LLM 生成 C（含 RVV intrinsics 或可自动向量化的 C）→ `riscv64-gcc -O3 -march=rv64gcv` 交叉编译 → scp 到板子 → `taskset` 绑核 + 20 次计时 → 正确性对拍。
- 指标：同 E3；另加 **RVV 指令使用率**（objdump 里出现 `vsetvl`/`vfmacc`/`vle` 的比例）、**移植失败率**（x86 生成代码直接重编译到 RVV 的失败率 vs RVV 条件生成）。
- **关键对比**：B3（用 RVV 硬件 profile + RVV 知识） vs B3（用 x86 profile，生成后直接重编译）——直接回答"知识是否真的按架构条件化"。

### 3.7 E5：跨架构可迁移性分析（论文的"科学发现"章）

- **知识源切分**：K_x86（只从 x86 优化实现抽的策略）、K_RVV（只从 RVV 实现抽的策略）、K_all（合并）。
- **目标平台**：x86 与 RISC-V。
- **实验**：对 6 个 S1 算子，分别用 K_x86/K_RVV/K_all 做 B3 检索与生成（或只做推荐），测：
  - 迁移保真度 = 目标平台上"推荐策略可正确实现/确实生效"的比例；
  - 性能增量（相对 B2）；
  - 失败原因（不能实现 / 能实现但更慢 / 编译不过 / 数值错误）。
- **分析产出**：策略可迁移性三层分类表——
  - **架构无关**：循环分块思想、寄存器分块思想、减少内存访问、算法重构；
  - **参数自适应**：展开因子、块大小、向量宽度（需按 VLEN/LMUL/寄存器数换算）；
  - **架构特定**：RVV intrinsic、prefetch 指令、mask 尾处理、x86 AVX512 mask；
  - 每类给 2–3 个真实例子 + 证据。
- 这一节即使生成性能不理想也能写：因为它回答的是"知识迁移的边界"，不是"谁更快"。

### 3.8 E6：消融（证明"图结构/条件/硬件"各自的作用）

| 编号 | 消融 | 对比 | 预期结论 |
|---|---|---|---|
| A1 | B2 vs B3 | 同内容、同 token | B3 高 5–15% → 结构有独立价值 |
| A2 | B3 去掉硬件约束过滤 | vs B3 | 去掉后编译失败率/性能下降 |
| A3 | B3 去掉适用条件 | vs B3 | 去掉后错误策略增多 |
| A4 | B3 去掉实施模板（只给策略名） | vs B3 | 去掉后生成质量下降 |
| A5 | B3 无对齐（原始冗余实体） | vs B3 | 差异小则对齐降级为工程细节 |
| A6 | 随机子图（同 token） | vs B3 | B3 更好 → 不是"上下文更长"的功劳 |

### 3.10 统计与可复现

- LLM 每条件 3 次采样（temperature 0.2），性能 20 次计时取中位数；报告中位数/IQR 或均值±95% CI。
- 配对 Wilcoxon（按算子配对）+ bootstrap 10,000 次 CI；多组消融用 Holm–Bonferroni。
- 所有原始输出（生成代码、编译日志、运行输出、KG 快照、prompt）存档；论文里每个数字能追溯到 `runs/<date>/`。

## 7. RISC-V 真机要点（详见 `08b`，以下为已实测结论）

- **好消息：P1 基线不用编 OpenBLAS**。语料里已有现成预编译静态库 `libopenblas_riscv64_zvl256bp_rvv-r0.3.27.dev.a`（55 MB，TARGET=ZVL256B，已验证可链接），直接链接即可得到板上专家参照；另有 generic 标量库可做策略归因。
- **工具链真名**：`riscv64-buildroot-linux-gnu-gcc`（GCC 14.3，Bootlin），不是脚本里写的 `riscv64-linux-gcc`；本机 WSL2 已实测：`-O3 -march=rv64gcv_zvl256b_zba_zbb_zbc_zbs -mabi=lp64d -ffast-math -static` 可编译，dgemm 驱动 46 s、941 KB、含 56 处 `vsetvl`。
- **第 1 天 30 分钟确认**：板卡型号（期望 SpacemiT K1 / BPI-F3）、`nproc`=8（2 簇×4）、VLEN（**必须跑内联 vsetli 探针**，`/proc/cpuinfo` 看不到）、`scaling_available_frequencies` 最高 1.6 GHz、温度与 governor。脚本见 `08b` §1.2；也可用 `科研产出/tools/riscv_env_check.sh`。
- **计时协议**：`CLOCK_MONOTONIC_RAW`、taskset 绑核、5 warmup + 20 次中位数、RSD>3–5% 重测、记录频率防降频；现有 `bench.h` 用 `CLOCK_REALTIME`、`benchmark_common.h` 用 `clock()`，都不能直接用于论文数字。
- **K1 的缓存现实**：L1d 32 KB/核 → L2 512 KB/簇 → 无 L3 → DRAM；所以"L3 档"不存在，用 DRAM 档代替（向量类 n=1024/16384/1M，gemv n=256/1024/4096，dgemm n=64/128/512）。
- **能说/不能说**：真机可以报同 ISA 内的相对提升（S_C1、EGC）；**不能**报"RVV 比 x86 快/慢 N 倍"（跨 ISA 绝对值不可比），也不能把 QEMU 数字写进性能表。
- **风险**：BPI-F3 无风扇，满载易降频——买 20 元 5V 风扇并锁 1.2/1.6 GHz 重测；板子不在手则性能全留 x86，RISC-V 只做正确性回归。
- **机时**：R0–R5 六项合计约 3.5–4.5 h（编译 1 h + 板上跑 1 h + 调试），一个晚上加一个半天可完成；详见 `08b` §6。
- **板子不在手怎么办（当前情况）**：① 交叉编译与 QEMU 已在本机 WSL2 打通，**E4 的开发与正确性验证可以先做**；② x86 主实验（E1/E2/E3/E6/E7）完全不依赖板子，照常推进；③ 板子到位后只补 E4 的真机性能（约 1 天）；④ 若 W6 前仍拿不到板，E4 降级为"QEMU 正确性 + 结构泛化"，论文明确写"RISC-V 性能待补"或改用租用/购买方案；⑤ **租/买方案已调研**：首选 Bianbu Cloud 免费 K1 实例（gdriscv.com），备选 Cloud-V 物理板，兜底买 Orange Pi RV2 / BPI-F3（¥300–800），详见 [`11_RISC-V板卡方案.md`](11_RISC-V板卡方案.md)。
