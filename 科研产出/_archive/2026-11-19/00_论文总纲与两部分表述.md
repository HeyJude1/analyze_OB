## 1. 一句话把两部分说清楚

**第一部分：把 OpenBLAS 里"高性能算子怎么写"的经验，建成一个带条件、参数、模板、证据和来源的知识图谱；再用它做条件检索和代码生成，验证"结构化知识"相对"扁平文本"到底有没有增量。**

**第二部分：让 Agent 从第一部分的成功/失败轨迹里总结，经过门控和版本化，反过来维护这个知识图谱；用冻结的留出算子验证"知识库是不是越用越准"，以及会不会越改越差。**

两部分是**递进关系**，不是两个并列系统：

```text
OpenBLAS 多架构实现
        ↓ 第一部分：抽取、对齐、建图、检索、生成
   知识图谱 v1  +  每次生成的成功/失败/修复轨迹
        ↓ 第二部分：总结轨迹、提更新、门控、版本化
   知识图谱 v2 → v3 → …  +  冻结留出集上的学习曲线
```

> 一句话主线：**知识从哪来 → 怎么用 → 用完怎么修**。

## 2. 第一部分：知识图谱构建与知识增强生成

### 2.1 做什么

1. 从 OpenBLAS 取 12 个常用算子（向量类、矩阵-向量类、矩阵-矩阵类）的通用 C 实现与多架构优化实现；
2. 对"通用版 → 优化版"做差分，抽出优化策略：向量化、循环展开、寄存器分块、缓存分块、预取、打包、尾部处理、布局调整；
3. 把每条策略写成**策略卡**：适用条件、硬件条件、参数、代码模板、性能证据、文件行号、跨架构范围；
4. 把策略卡组织成图谱：算子 → 计算流程 → 策略 → 模板/参数/硬件/证据/来源；
5. 用七步检索（识别流程 → 召回 → 条件过滤 → 硬件过滤 → 冲突消解 → 打分 → 组装策略包）把知识注入生成模型；
6. 在 x86 与 RISC-V 上验证生成代码的正确性与性能，并与编译器、OpenBLAS、零样本、硬件提示、扁平文本对照。

### 2.2 回答的三个问题

- **问题一**：能不能把"高性能算子编写经验"建成可执行、可追溯的知识图谱？建得准不准？
- **问题二**：结构化知识相对扁平文本检索，能不能提升生成代码的正确性/性能？增量来自哪一部分？
- **问题三**：同一套知识能不能跨算子、跨架构迁移？边界在哪？

### 2.3 实验（都在第一部分）

| 实验 | 回答什么 |
|---|---|
| 知识质量 | 抽出来的策略准不准、能不能溯源 |
| 策略推荐 | 给代码+硬件，能不能推对策略（不执行代码） |
| x86 生成 | 生成代码对不对、比 -O3 快吗 |
| RISC-V 生成 | 换到真机还成立吗 |
| 跨架构迁移 | 哪些策略能迁、哪些不能 |
| 消融 | 提升来自知识、条件、硬件、参数还是模板 |
| 案例与失败 | 为什么成功、为什么失败 |
| 第二个大模型 | 换个模型结论还成立吗 |
| 多视角分析 | 先逐条分析再综合，有没有额外提升 |

### 2.4 第一部分的贡献

1. **多架构可执行的知识表示**：策略卡 = 条件 + 参数 + 模板 + 证据 + 来源 + 跨架构范围；
2. **差分驱动的知识获取**：以"通用版 vs 优化版"的配对差异为监督，规则抽事实、模型只命名，降低幻觉；
3. **硬件条件约束的检索与生成**：七步过滤 + 冲突消解，把"知识选择"变成可审计的决策链；
4. **可执行基准**：OpOptBench-12（12 算子 × 3 尺寸 × 双平台 + 隐藏测试 + 可复现包），作为验证载体，不抢主创新。

## 3. 第二部分：反馈驱动的知识图谱自维护

### 3.1 做什么

1. 每次生成后记录三类轨迹：一次成功、修复后成功、最终失败；
2. Agent 总结"哪条策略有用/哪条条件写错/缺什么知识/参数怎么不对"；
3. 提出知识更新：加失败案例、改条件、改参数、加模板、合并同义策略；
4. 门控：schema 校验 + 证据要求 + 人工抽检，只接受可验证的更新；
5. 每次更新生成一个版本（KG_1、KG_2…），可回滚；
6. 在**冻结的留出算子**上评估每一版：正确率/加速比有没有持续提升，回归率有多高。

### 3.2 回答的两个问题

- **问题四**：反馈能不能带来留出任务上的持续提升？提升来自"知识变准"还是"知识变多"？
- **问题五**：会不会越改越差（负迁移/遗忘）？门控和版本化是否必要？

### 3.3 实验（第二部分）

五轮循环：初始知识库 → 冻结测试集评估 → 更新集跑任务、收集轨迹 → Agent 提更新 → 门控写回 → 新版本 → 再评估。
对照：不更新、只用失败、只用成功、成功+失败、随机更新、无门控。
指标：冻结测试集上的正确率/加速比学习曲线、回归率、新知识人工精度、更新采纳率、成本。

### 3.4 第二部分的贡献

5. **反馈驱动的知识自维护机制**：轨迹总结 → 门控更新 → 版本化 → 冻结集验证，并给出"正向维护"的可证伪判定标准。

## 4. 两部分怎么衔接（不要写成两张皮）

| 第一部分产出 | 第二部分怎么用 |
|---|---|
| 知识图谱 v1 | 作为初始知识库 |
| 每条策略的条件/参数/模板/来源 | 作为"可修改的对象" |
| 每次生成的初始代码、修复代码、失败原因 | 作为"更新提议"的素材 |
| 冻结留出算子 | 作为两部分的共同测试集，第二部分绝不拿它更新 |
| 检索/生成/验证流水线 | 第二部分只改知识库，不改模型和流水线 |

**关键**：第二部分不改大模型参数，只改知识库；所有更新可追溯、可回滚；测试集冻结。

## 7. 边界（先写死，避免被问）

- 硬件只做 x86 + RISC-V 真机；ARM 只做知识，不做性能实验；
- 不覆盖 GPU/CUDA；
- 不做模型微调；第二部分不更新 LLM 参数，只更新知识库；
- 不声称全面超过 OpenBLAS/所有 AI 优化方法；
- 语料只 OpenBLAS，外部效度靠 S2 留出 + 第二模型 + 可复现包补；
- 所有性能结论只来自真机；QEMU 只验正确性。

## 10. 答辩三句话

1. **第一部分**："我不是把方法跑在 OpenBLAS 上，而是从 OpenBLAS 构造了可执行基准；知识图谱把'专家怎么写'拆成带条件、参数、模板、证据和来源的策略卡，再用七步检索注入生成。"
2. **第二部分**："自维护不是让模型自我进化，而是让 Agent 在冻结测试集之外积累经验，经门控写回版本化知识库；用五轮学习曲线、回归率和知识精度判断它是不是正向。"
3. **边界**："如果某条机制不成立，我报告边界（例如某些算子编译器已饱和、某些更新只增加成本），不硬吹。"
