## 0. 先更正我上次说错的地方

上次我说：`stg:axpy:specialize_s` 的 ID 后缀 `_s` 是"单精度"，和条件 `dtype in ["d"]` 矛盾，并报了 **28/66 条"ID 与条件不一致"**。

**这是错的。** 我去看了 `normalize.py:257-266`：

```python
if source == "analysis":
    base_id = "stg:%s:%s_%s_a" % (op, action, level)
elif source == "static":
    base_id = "stg:%s:%s_s" % (op, action)      # ← _s = static（静态特征通道）
```

`_s` / `_d` 是**来源通道**，不是 dtype。你的图在这条上没错，是我按 dtype 读法审计，读错了。抱歉。

**但这次更正之后，我重新做了一次"跨字段一致性审计"，反而找到了真问题**——而且正是你说的那类"没校验"：

| 检查 | 结果 | 性质 |
|---|---|---|
| C1 策略要求某 ISA，绑定的 profile 不支持 | 0 | ✅ 干净 |
| C2 证据平台不在绑定 profile 里 | 0（`scope=operator` 的继承属设计内） | ✅ 干净 |
| **C3 参数实例值不在声明取值域内** | **34 条** | ❌ 真问题 |
| C4 同一对策略既冲突又可组合 | 0 | ✅ 干净 |
| **C5 同算子同族同层的疑似重复** | **6 组** | ⚠️ 待人工判定 |
| **C6 命名歧义（`_s/_d` 与 dtype 码冲突）** | **28 条** | ⚠️ 规范问题 |
| C7 硬条件少于 2 条 | 0 | ✅ 干净 |
| C8 证据方向矛盾（support 但 speedup≤1） | 0 | ✅ 干净 |

C3 的例子（都是真数据）：

```text
stg:asum:tile_arm_neon      par:reg_block_n       值 30，声明域 [2,4,8,16,32]
stg:dot:tile_arm_neon       par:reg_block_n       值 24，声明域 [2,4,8,16,32]
stg:copy:prefetch_x86_avx2  par:prefetch_distance 值 6， 声明域 [1,2,4,8]
stg:dot:prefetch_arm_neon   par:prefetch_distance 值 9， 声明域 [1,2,4,8]
```

根因在 `multiarch.py::_param_list`：

- `unroll_factor` 用 `dims[0]*dims[1]`（**块面积**）当展开因子 → 5×6 得 30；
- `prefetch_distance` 用 `prefetch_count`（**指令条数**）当预取距离（单位是 cacheline）；
- `reg_block_n` 用 `reg_block_estimate`（**寄存器估计值**）直接写入，不吸附到合法集合。

所以你的判断成立，只是机理不是"AI 编了假知识"，而是"**规范化环节写了估计值，没有任何检查器验证它落在声明域内**"。这个区别很重要：前者要训 judge，后者写 30 行检查就行。

## 1. 论文地图：AI 在建图的哪一步

先给结论：**"用 LLM 建 KG"已经是一个成熟子领域**，2024–2026 有综述、有系统、有专门的校验方法。按"AI 参与哪一步"分，是五步：

| 步骤 | AI 可以干什么 | 代表工作 | 这一步的质量保障 |
|---|---|---|---|
| ① schema / 本体 | 归纳 schema、扩展类型、写抽取指南 | AutoSchemaKG（[arXiv:2505.23628](https://arxiv.org/abs/2505.23628)）；OneKE 的 schema 配置 | 人工审 + schema 校验 |
| ② 抽取 | 实体/关系/事件抽取，三元组生成 | GraphRAG（[arXiv:2404.16130](https://arxiv.org/abs/2404.16130)）、LightRAG（[arXiv:2410.05779](https://arxiv.org/abs/2410.05779)）、Triplex、CodeKGC（[arXiv:2304.09048](https://arxiv.org/abs/2304.09048)） | schema 注入 + few-shot + 输出格式约束 |
| ③ 归一 / 融合 | 实体消解、同义合并、跨源对齐 | KGGen（[NeurIPS 2025](https://neurips.cc/virtual/2025/loc/san-diego/poster/117386)）、iText2KG（[arXiv:2409.03284](https://arxiv.org/abs/2409.03284)） | 相似度阈值 + 聚类 + 抽检 |
| ④ 校验 | 判断一条知识对不对、错在哪 | **GraphJudge**（EMNLP 2025，[arXiv:2411.17388](https://arxiv.org/abs/2411.17388)）；OneKE 的反射 agent | 独立校验器（见 §2.4） |
| ⑤ 维护 | 增量更新、补全、纠错 | LightRAG（增量）、iText2KG（增量）、Paulheim 的 KG refinement 综述 | 版本化 + 回滚 |

综述两篇够用：

- *LLM-empowered knowledge graph construction: A survey*（[arXiv:2510.20345](https://arxiv.org/abs/2510.20345)）——2025 年最全，重点讲 schema 从"固定"变成"抽取中演化"。
- 领域综述（如交通领域的 [ScienceDirect 2025](https://www.sciencedirect.com/science/article/pii/S0968090X25004322)）——把方法分成 **prompt / fine-tuning / agent-based** 三类，这个三分法很好用。

**这三类范式的取舍**（选型时看这张表）：

| 范式 | 代表 | 成本 | 质量 | 适合 |
|---|---|---|---|---|
| Prompt-only（大模型 + schema + few-shot） | GraphRAG、LightRAG、OneKE | 高（token） | 中，幻觉多 | 语料杂、schema 常变 |
| Fine-tuned 小模型 | Triplex（Phi-3.8B 微调的 4B 模型，宣称比 GPT-4 便宜约 60×）、GraphJudge | 低（推理） | 稳定但覆盖窄 | 固定 schema、大批量 |
| Agentic（多 agent + 反思 + 工具） | OneKE、KAG | 最高 | 最高 | 专业领域、要可审计 |

## 2. 他们具体怎么"用 AI"（机制细节）

这一节是你真正想知道的：不是"用 GPT 抽三元组"这种废话，而是每一步的工程手法。

### 2.1 提示层：把 schema 塞进 prompt，把输出约束成代码

- **schema 注入**：把实体类型、关系类型、每个类型的字段写进 prompt，让模型只能从这个闭集里选。KAG 更进一步，用**逻辑形式**（logical form）把问题/知识约束成 SPARQL 式的结构。
- **code-format 输出**：CodeKGC 的做法是把三元组写成**代码**（`Relation(Entity, Entity)` 或 JSON-like 结构），而不是自然语言。好处是格式错误率大幅下降、重叠关系更好处理——论文报告的提升主要来自这一点。
- **few-shot 例池**：OneKE 把"历史错误案例"沉淀成一个可配置知识库，下次抽取时作为反例注入 prompt。

> 对你的启发：你的 `prompts/generate_b3.md` 已经在做 schema 注入；但**"错误案例库"这一层没有**——第二部分的自维护正好可以长在这上面。

### 2.2 解码层：self-consistency 投票 + 反射修正

OneKE 的流程（[arXiv 正文 §2](https://ar5iv.labs.arxiv.org/html/2412.20005)）：

```text
同一段文本 → 多次采样抽取 → 投票/一致性筛选
    ├─ 高一致 → 直接接受
    └─ 低一致/不确定 → 交给 Reflection Agent 调试修正 → 再判定
```

- **self-consistency** 抓的是"模型自己都不确定"的样本（随机幻觉）；
- **reflection agent** 抓的是"有系统性错误"的样本（比如总把 A 的关系抽成 B）；
- 两者都**不能**抓"模型很自信但错了"的样本——那要靠外部证据（§2.4）。

### 2.3 结构层：实体消解与增量合并

- **KGGen**：抽完之后对所有 mention 做**聚类**，把"同一个人/同一个概念"的多种写法合并成一个节点。它把"实体消解"当成一等公民，而不是后处理。
- **iText2KG**：增量构建，每来一篇新文档，先做实体/关系匹配（相似度阈值，README 里是 `ent_threshold=0.8, rel_threshold=0.7`），再决定"并入已有节点"还是"新建"。
- 共同点：**它们都承认"抽出来的东西一定重复/不一致"，所以把归一当成主流程的一步。**

> 对你的启发：你有 262 条策略 / 30 条跨架构策略，合并逻辑存在，但**没有可测的合并精度**（我上次提的 6 组疑似重复就是证据）。KGGen 的做法可以直接借：把"同族判定"换成"嵌入相似 + 结构相似"的双通道，再人工抽检 precision/recall。

### 2.4 判定层：训一个"图法官"

GraphJudge（EMNLP 2025）是目前最贴你问题的一篇。它先把 LLM 建图的三个毛病写清楚：

1. 文档里有噪声 → 抽出来的信息很乱；
2. 朴素 LLM 在**专业文档**上会抽错（它举的例子：原文只说"Protein X 与更好疗效相关"，模型抽成"cured"）；
3. **幻觉**：直接让 LLM 建图，会往图里塞不存在的事实。

它的解法两步：

```text
① entity-centric 去噪：先定实体，再围绕实体抽关系（减少无关三元组）
② 微调一个 LLM 当 graph judge：输入候选三元组 + 原文证据，输出"接受/拒绝/为什么"
```

**关键设计**：judge 是**独立于生成器的第二个模型**，而且**带原文证据**。这两点决定了它能抓到生成器抓不到的错误。

> 对你的启发：你完全可以用同样的结构做"策略卡 judge"——输入是策略卡 + 源码行号 + 性能证据，输出是"条件是否成立/参数是否在域内/模板是否可编译"。区别只是**被审对象从三元组变成了策略卡**。

### 2.5 人机层：门控 + 抽检 + 版本

学术论文很少写这一层（不好发），但工程系统都有：更新提议 → 规则门控 → 人工抽检 → 版本快照 → 可回滚。

你的第二部分（`02b`）已经有这套设计（门控、版本化、冻结集），**不用改，只要把 §4 的检查器接进去**。

## 3. "AI 不校验"到底是不是问题？

分三层回答：

**第一层：早期 pipeline 确实不校验。**
GraphRAG / LightRAG 的主流程都是"抽完就用"，没有独立的验证步骤；它们的评测指标是下游问答效果，不是图本身的质量。这也是 2025 年之后一批工作专门去补校验层的原因。

**第二层：2025 年开始，校验被单独做成模块。**
GraphJudge（微调 judge）、OneKE（self-consistency + reflection）、iText2KG（schema consistency 评分）、KGGen（实体聚类）——它们共同的假设是：**生成器不可信，必须有独立的第二道关**。

**第三层：但"校验"目前主要校"三元组对不对"，很少校"字段之间一不一致"。**
这就是你这次撞上的空白：

| 校验对象 | 谁在做 | 典型检查 |
|---|---|---|
| 三元组是否忠实于原文 | GraphJudge、RAGAS 类 | 蕴含/矛盾/无依据 |
| 实体是否重复 | KGGen、iText2KG | 聚类/相似度 |
| schema 是否合规 | 所有工程系统 | 类型、必填、端点 |
| **卡内字段是否自洽**（条件/参数/模板/证据） | **几乎没人做** | 参数域、单位、命名、冲突+组合 |

所以你的判断可以更精确地表述为：

> **不是"AI 不校验"，而是"校验的粒度停在三元组，没有下沉到字段"。** 对三元组图来说，字段就是三个位置，没什么可查的；但对你这种"策略卡"图，字段之间有大量可机器验证的约束（参数域、单位、条件与硬件是否兼容、证据平台是否绑定），这些约束**目前没有现成的检查器**。

这句话本身就是你论文第 3 章一个可以立住的点：**面向程序性知识的字段级质量门（field-level quality gate）**。

## 5. 这对论文意味着什么

### 5.1 你的"建图方法"其实已经是"生成-校验分离"的一种

你一直是"**规则差分抽事实，LLM 只命名**"。这在文献里对应的是"**弱监督抽取 + 模板化规范化**"，优点是幻觉空间小；缺点是**错误会以"规范化错误"的形式出现**（单位、域、命名），而不是以"编造事实"的形式出现。

这个区别值得写进论文：

> 与依赖 LLM 端到端抽取的建图方法（GraphRAG、LightRAG）不同，本文的事实由配对差分与静态分析确定，LLM 仅参与命名与解释；因此本文的错误模式不是"幻觉"，而是"规范化与字段一致性"，需要一类不同的质量门来约束。

### 5.2 可以立一个新点：字段级质量门

- 与 GraphJudge 的区别：它审三元组，你审**策略卡字段**；
- 与 schema 校验的区别：schema 只管类型，你管**字段间约束**；
- 与人工金标准的区别：检查器是**自动、可回归**的，金标准是抽样、一次性的。

这三条差异，正好是一节"构建质量保障"的骨架（放在第 3 章末尾）。

### 5.3 和第二部分的衔接

第二部分的自维护是"Agent 提更新 → 门控 → 版本化"。你现在可以把门控写成**同一套检查器**：

```text
构建期：生成 → 门 1-4 → 写库
更新期：Agent 提议 → 门 1-4（同一套）→ 若通过则写库，否则拒绝并记录原因
```

好处：**门控不是拍脑袋的规则，而是可复用的质量函数**；而且"更新被拒的原因分布"本身就是一张好图（哪类更新最容易出错）。

## 7. 答辩三问（新增）

**Q1："你的图是 AI 建的吗？"**
> "事实不是。事实来自 OpenBLAS 通用版与优化版的差分、静态特征提取和日志，LLM 只负责命名和解释。所以我的错误模式不是幻觉，而是规范化和字段一致性——这也是我为什么单独做了一层字段级检查。"

**Q2："AI 建图不是有幻觉吗？你怎么保证质量？"**
> "四道门：schema 校验、跨字段一致性、证据门、语义门（人工金标准 + 编译验证）。跨字段这一层是文献里最缺的——GraphJudge 审的是三元组是否忠实原文，我审的是策略卡的条件/参数/模板/证据是否互相自洽。检查器是自动的，每次构建都跑，可回归。"

**Q3："这和 GraphJudge / OneKE 有什么区别？"**
> "对象不同。它们处理的是从文档抽三元组，错误是'抽错/抽漏/编造'；我处理的是从代码差分抽策略卡，错误是'参数越界/单位错/命名歧义/同族重复'。前者需要训 judge 判语义，后者用规则就能抓住大部分——但前提是你得想到去查。"
