## 0. 先看这页：三个困惑，三句话

| 你的困惑 | 一句话答案 | 在本课题里具体是什么 |
|---|---|---|
| 知识图谱怎么检索？ | 图检索不是"找相似文本"，而是**在带类型和约束的图上执行一次查询，返回一个子图**。查询可以是 Cypher、可以是"种子+几跳扩展"、可以是条件过滤，也可以是 LLM 规划的路径。 | 七步检索：算子 → 计算流程 → 召回策略 → 条件求值 → 硬件过滤 → 冲突消解 → 打分 → 打包成策略包 |
| 和向量 RAG 差在哪？ | 四个东西换了：**检索单位**（chunk → 子图）、**匹配方式**（余弦相似 → 约束满足/连通性/路径）、**上下文形态**（原文摘录 → 字段化知识+溯源）、**失败模式**（召回不全 → 种子错/扩展爆炸/图缺边）。 | 向量检索给"5 段像 daxpy 优化的文字"；你的图给"3 条在 AVX2 上确实成立、带参数和行号的策略" |
| 图的质量怎么评？ | **三层，缺一不可**：图本身（正确/完整/一致/可追溯）、检索层（SAR/Recall@k/nDCG/上下文成本）、下游任务（FCR/加速比/消融）。只报下游 = 不可归因；只报图指标 = 不知道有没有用。 | 你的 `04` 协议已有 FCR/SAR/nDCG/SIF；缺的是**图本身的质量表**和**等 token 对照** |

**本课题的一句话定位**（下面第 3.7 节展开）：

> 你建的不是 GraphRAG 那种"从文档里自动抽出来的实体图"，而是**schema 固定、事实有差分监督、每条知识可执行的程序性知识库**。所以该抄的是"约束检索 / 知识选择"，**不该抄的是"社区摘要"**——那是给百万 token 文档语料做全局总结用的，和你的问题不是一个问题。

## 1. 文献地图：KG+AI 的五条线

这个领域 2023 年后基本分成五条线。每条线给代表工作，并标出**能借用什么、不能照搬什么**——后者比前者重要。

### 1.1 地基：KG 到底是什么

Hogan 等人的综述（*Knowledge Graphs*, ACM CSUR 54(4), 2021，[DOI](https://doi.org/10.1145/3447772) / [arXiv:2003.02320](https://arxiv.org/abs/2003.02320)）把 KG 拆成四件套：**数据模型（三元组/属性图）+ schema/本体 + 查询语言（SPARQL/Cypher/GQL）+ 推理与嵌入**。

它对你最有用的一句话是：**"图"不是一个文件格式，是"数据模型 + 约束 + 查询能力"的组合**。所以判断你建的是不是 KG，不看有没有可视化，看三件事：

1. 有没有**类型系统**（节点/边类型是闭集，不是自由文本）；
2. 有没有**可执行的约束**（能对一条知识判断"此刻适不适用"）；
3. 有没有**可查询的接口**（能按类型/路径/条件取子图，而不是只能看）。

你的 12 实体 / 14 关系 / 10 谓词，正好对上前两条；`retrieve.py` 对上第三条。

### 1.2 用 LLM 建图

| 工作 | 干了什么 | 关键机制 |
|---|---|---|
| Pan et al., *Unifying LLMs and KGs: A Roadmap*, IEEE TKDE 2024（[DOI](https://doi.org/10.1109/TKDE.2024.3352100)） | 把这个领域分成三块：KG 增强 LLM、LLM 增强 KG、双向协同 | 给你"相关工作"章节的骨架 |
| *LLM-empowered knowledge graph construction: A survey*（[arXiv:2510.20345](https://arxiv.org/abs/2510.20345)） | 2025 年最全的"LLM 建图"综述 | 指出 schema 从"固定"变成"抽取中动态演化" |
| Edge et al., *From Local to Global: A Graph RAG Approach to QFS*（[arXiv:2404.16130](https://arxiv.org/abs/2404.16130)） | 微软 GraphRAG：LLM 抽实体图 → 社区检测 → 预生成社区摘要 → 全局问答 | 图是**索引**，不是知识库；检索的核心是"社区摘要" |
| AutoSchemaKG（[arXiv:2505.23628](https://arxiv.org/abs/2505.23628)） | 从网页级语料自动归纳 schema，再抽三元组 | schema 归纳（schema induction） |
| KGGen（NeurIPS 2025，[页面](https://neurips.cc/virtual/2025/loc/san-diego/poster/117386)） | 纯文本 → KG，重点解决**实体消解**（同义实体聚类） | 没有实体消解，图就会"同一件事存十份" |
| LightRAG（[arXiv:2410.05779](https://arxiv.org/abs/2410.05779)） | 建图 + **双层检索**（实体级 + 主题级）+ 增量更新 | 增量更新对第二部分有参考价值 |
| KAG（[arXiv:2409.13731](https://arxiv.org/abs/2409.13731)） | 专业领域：文本块与 KG **互索引**，用逻辑形式引导推理 | 最接近你的场景（专业、要严谨），值得精读 |

**能借用**：实体消解的必要性（KGGen）、schema 与抽取的耦合（AutoSchemaKG）、互索引（KAG）、增量更新（LightRAG）。
**不能照搬**：GraphRAG 的"社区摘要"路线——它的前提是"语料是海量文档、问题是全局总结"。你的语料是 70 个实现文件，问题是"这个算子在这个硬件上该用哪几条策略"，两者不在一个问题上。

### 1.3 图上的检索与推理

这是你最缺的一块。文献里的做法可以归并成六种**检索算子**（我的归纳，第 3.2 节展开）：

| 工作 | 检索算子 | 一句话机制 |
|---|---|---|
| StructGPT（EMNLP 2023，[ACL](https://aclanthology.org/2023.emnlp-main.574/)） | 迭代式接口检索 | 给 LLM 一组"访问结构化数据的接口"，迭代"读取→推理"（IRR） |
| ToG（ICLR 2024，[OpenReview](https://openreview.net/forum?id=nnVO1PvBvTv)） | LLM 在图上做束搜索 | LLM 逐步选关系、扩展、剪枝，直到能回答 |
| RoG（ICLR 2024，[PDF](https://shiruipan.github.io/publication/iclr-24-luo/iclr-24-luo.pdf)） | 规划-检索-推理 | 先让 LLM 生成"关系路径"作为计划，再按计划去图上取路径 |
| SR（ACL 2022，[ACL](https://aclanthology.org/2022.acl-long.396/)） | 子图检索器 | 把"取子图"和"推理"解耦，检索器可单独弱监督训练 |
| G-Retriever（NeurIPS 2024，[ACM](https://dl.acm.org/doi/10.5555/3737916.3742140)） | 连通子图选择 | 把子图选择形式化成 prize-collecting Steiner tree，选"又小又连通"的子图 |
| KAPING（AAAI 2024，[AAAI](https://ojs.aaai.org/index.php/AAAI/article/view/29889)） | 事实级相似检索 | 用问题-事实的语义相似度取三元组，直接前置进 prompt |
| HippoRAG（NeurIPS 2024，[slides](https://neurips.cc/media/neurips-2024/Slides/94043.pdf)） | 图上的传播 | 用 Personalized PageRank 在 KG 上传播，一次检索覆盖多跳；比 IRCoT 便宜约 10× |

**能借用**：SR 的"检索器与推理器解耦"（你的七步检索本来就是解耦的，这是优点，要写出来）；G-Retriever 的"子图要连通且小"（你的策略包应该显式约束条数和 token）；HippoRAG 的"传播式检索"（如果将来要处理"改了 A 会影响哪些 B"）。
**不能照搬**：ToG/RoG 那一套是给开放域多跳问答设计的，查询是自然语言、图是 Wikidata 规模。你的查询是结构化的（算子+硬件+代码特征），不需要 LLM 在图上瞎逛——你已经知道该从哪个节点出发。

### 1.5 评测（第 4 节展开）

| 工作 | 给了什么 |
|---|---|

## 2. 构建：通用流水线 vs 你的七步

### 2.1 文献里的通用五段

```text
① 本体/schema 设计  →  ② 抽取（实体/关系/事件）  →  ③ 对齐与融合（同义、跨源）
        →  ④ 校验（schema/约束/冲突）  →  ⑤ 版本化与发布
```

你的 `22` 文档七步，是这条流水线的一个**特化版本**：把 ① 固化成闭集 schema，把 ② 换成"差分驱动"，把 ③ 换成"跨架构对齐"，④⑤ 原样保留。

### 2.2 你的做法 vs 文献主流：三处关键差异（这是你的创新点，要写清楚）

| 环节 | 文献主流 | 你的做法 | 为什么这在本课题成立 |
|---|---|---|---|
| 知识来源 | LLM 读文档直接抽三元组 | **通用版 vs 优化版做差分**，规则抽事实，LLM 只命名和解释 | 差分是"弱监督信号"：改了什么、哪一行改的，是客观的；LLM 只负责起名字，幻觉空间小 |
| schema | 越来越流行"动态归纳"（AutoSchemaKG） | **固定闭集**：12 实体 / 14 关系 / 10 谓词 | 专业小图要的是**可复现、可校验**；动态 schema 会让两次构建不一致，反而毁了"版本化"这个卖点 |
| 知识形态 | 三元组 `(头, 关系, 尾)` | **策略卡**：条件 + 参数 + 模板 + 证据 + 来源 + 跨架构范围 | 算子优化知识是"程序性知识"，一条三元组装不下"当 dtype=double 且 stride=1 时展开 4 次" |

**这段可以直接进论文第 3 章**：你的构建方法不是"又一个 LLM 建图 pipeline"，而是"**以配对差分作为监督信号的、schema 固定的程序性知识获取**"。这个说法比"知识图谱构建"精确得多，也躲开了"你和 GraphRAG 有啥区别"的追问。

### 2.3 文献给的三个警告（每个都有反例，你必须回应）

**警告一：LLM 抽取的覆盖率是不可信的。**
你自己的 `02` 文档里记了一条 2026-01 的工作（Reliable Graph-RAG for Codebases）：LLM 抽取的 KG 在 Shopizer 上**漏掉 377 个文件**，索引慢、成本高；确定性 AST 图在正确性和多跳 grounding 上更好。
→ **你的回应**：你用规则差分，天然不漏文件；但你必须报**语料覆盖率**（12 算子 × 5 架构 × 文件数，哪些格子是空的）。这不是可选项，是审稿人一定会问的。

**警告二：没有实体消解，图会"同一件事存十份"。**
KGGen 专门用聚类做实体消解；AutoSchemaKG 用概念化做 schema 归并。
→ **你的回应**：你有 262 条策略 / 262 个模板、30 条跨架构共有策略，说明合并逻辑存在。要报的是**合并精度**：抽 50 组"被判为同族"的策略，人工判断该不该合并（precision），以及抽 50 组"被判为不同"的，判断是否漏合并（recall）。

**警告三：图能跑通 ≠ 知识正确；而且"跑通"的检查通常只覆盖结构，不覆盖字段之间的一致性。**

先更正我上一版的说法：`stg:axpy:specialize_s` 里的 `_s` **不是"单精度"**，而是 `normalize.py:257-266` 的来源标记（`static` → `_s`，`diff` → `_d`）。我按 dtype 读法审计，把 28 条读成了"ID 与条件矛盾"——**这个结论是错的，特此更正**。

但它暴露了两类真问题（用 `tools/kg_consistency_audit.py` 做的跨字段审计）：

```text
参数域越界（34 条）：reg_block_n=30，而声明 range=[2,4,8,16,32]
                    prefetch_distance=12，而声明 range=[1,2,4,8]
                    根因：multiarch.py::_param_list 把块面积(dims[0]*dims[1])当展开因子、
                          把 prefetch 指令条数当预取距离、把寄存器估计值直接写入不吸附到合法集合
命名歧义（28 条）：_s/_d 既是来源标记，又长得像 dtype 码（s/d/c/z）
疑似重复（6 组）： 同算子同族同层，来自 _a 通道与 _s 通道的两条策略
```

**为什么重要**：参数越界会让 PIV（参数有效性）虚高、让"参数推导"这条贡献失去证据；命名歧义会让任何自动检查（包括我这次的）读错。**修这两类比多做一组实验值钱。**

## 3. 使用（核心一）：图到底怎么检索

### 3.1 先把"接口"说清楚

你熟悉的是这个：

```python
# 向量库：一个函数，返回排序列表
hits = vector_db.search(query, top_k=5)
# hits[i] = (chunk_id, text, cosine_score)
```

图检索的接口不是这个，是**"查询 → 子图"**：

```python
# 图：一个查询程序，返回一个子图（节点集合 + 边集合 + 每步的理由）
subgraph = graph.query(
    seed      = operator_node("axpy"),          # 种子：从哪进
    expand    = ["OPERATOR_HAS_PATTERN", "PATTERN_OPTIMIZED_BY"],  # 沿哪些边扩
    where     = conditions_match(features),      # 过滤：什么条件下成立
    rank_by   = ["match", "fit", "hw", "evidence"],  # 排序：为什么它排前面
    stop      = top_k_and_budget(5, registers=13)    # 停：什么时候够
)
```

**图检索必须回答四个问题**（向量检索只需要回答一个）：

1. **种子从哪来？**（实体链接：把查询里的"daxpy / AVX2 / 双精度"映射到图里的节点）
2. **沿哪些边扩？**（关系选择：只沿 `PATTERN_OPTIMIZED_BY`，还是也走 `GENERALIZES`）
3. **什么时候停？**（跳数、条数、token、资源预算）
4. **怎么序列化？**（子图变成 prompt 的哪几段：策略名、条件、参数、模板、证据、来源）

你现在的七步检索，四个问题都答了；但**答案散在代码里，没写进论文**。第 3 章要把它写成形式化的东西。

### 3.2 六种检索算子（文献归纳，对照你的图）

| # | 算子 | 一句话机制 | 代表工作 | 在你的图上是什么形态 | 成本 |

### 3.4 与向量 RAG 的逐项对照

以同一个问题为例：*"daxpy 在 x86 AVX2 上怎么写快？"*

| 维度 | 向量 RAG | 知识图谱检索（你的七步） |
|---|---|---|
| 查询解析 | 整句编码成向量 | 解析成**结构**：算子节点 + 代码特征 + 硬件 profile |
| 候选生成 | 全库 ANN 近邻 | 从种子节点沿**指定关系**扩展（可控） |
| 匹配依据 | 余弦相似度（连续、不可解释） | 谓词真假 + 硬件能力 + 冲突约束（布尔、可解释） |
| 能否判断"不适用" | 不能（只能靠 LLM 自己读出来） | 能，而且是显式淘汰（带理由） |
| 能否算参数 | 不能 | 能（LMUL/SEW/展开因子由硬件推导） |
| 上下文 | 原文片段（可能有噪声） | 字段化知识 + 模板 + 证据 + 行号 |
| 可解释性 | "相似度 0.83" | "因为 stride=1 且 AVX2 支持 FMA，且证据来自 haswell 微基准" |
| 失败模式 | 召回不全 / 语义漂移 | 种子错 / 扩展爆炸 / **图缺边**（缺边比缺文档更致命） |
| 成本 | 低（编码+ANN） | 低（本地图查询）+ **高上下文**（把模板都带上） |
| 更新 | 重嵌入/重建索引 | 加节点加边 + 版本化（第二部分的核心） |

**一句话**：向量检索回答"**哪段文字和这个问题像**"；图检索回答"**在这个约束下，哪些知识成立**"。前者是相似性问题，后者是**可满足性问题**。

**怎么读这张表（这段要原样写进论文的"检索实验"小节）**：

1. **图检索的 100% 是构造保证，不是实验发现**。它先过滤再排序，当然全可用。真正要证明的是"**过滤规则本身对不对**"——所以 SAR 必须配一个**人工判定的金标准**（4.3），否则是自证。
2. **文本检索的失败不是"排序不好"，是"它没有算子维度和硬件维度"**。dgemm 那一格最典型：5 张卡全是 "AVX2 tile"，只有 1 张是 gemm。daxpy/RVV 那格的 60% 是同一回事（3 张 axpy + 2 张 copy）。只要算子名恰好出现在卡名里（dot 全是 `stg:dot:*`），BM25 就能到 100%——**它靠的是命名巧合，不是知识**。
3. 这条观察有一个直接的反驳预案：审稿人会说"那你给每张卡前面拼上'算子/硬件'字段，BM25 不就行了？"——**可以，但那等于让文本检索器自己重建图**。你正好可以把这个当消融：*扁平文本 + 字段前缀（有结构信息、无过滤）* vs *图检索（有结构信息、有约束过滤）*，两者之差才是"约束求值"的净贡献。
4. **图检索的上下文贵 3–10 倍**（6k–15.5k 字符 vs 1k–2.5k）。这不是缺点，是"把模板/参数/证据一起带上"的代价。但你必须做**等上下文对照**（4.4），否则"图的增益"可能只是"多给了 token"。
5. 这个 pilot 只有 4 组查询、单种子、BM25 替身（不是真 embedding）。**它只能当诊断，不能当结论**。正式实验要换成 bge-m3 + 30 组以上查询 + 3 seeds。

### 3.6 什么时候不该用图

按 *When to use Graphs in RAG*（ICLR 2026）和 *RAG vs GraphRAG* 的结论，加上你自己的场景：

| 场景 | 该用什么 | 理由 |
|---|---|---|
| 单跳、细节、事实型（"daxpy 的签名是什么"） | **向量/关键词** | 图的过滤是负担，没有结构收益 |
| 全局总结（"OpenBLAS 的优化手法有几类"） | 图 + 社区摘要 | 这正是 GraphRAG 的强项 |
| **带硬约束的选择**（"AVX2 + double + stride=1 用哪几条"） | **图**（你的主场景） | 约束是布尔可判定的，文本相似度表达不了 |
| **多跳推理**（"这条策略依赖哪个 ISA，那个 ISA 在 K1 上支持吗"） | **图** | 路径就是证据 |
| **可审计**（"凭什么推荐这条"） | **图** | 有行号、有证据、有淘汰理由 |
| 需要覆盖未知知识（图里没有的算子） | 向量 + 图（混合） | 图缺边时，文本还能兜底 |

**这句话可以直接用在开题**：*"本课题不主张图普遍优于文本，而是主张：当知识的选择依赖**可判定的硬约束**和**可追溯的证据**时，结构化的收益是可测的；我给出这个边界的实验证据。"*

### 3.7 一个定位建议：把"检索"改叫"约束引导的知识选择"

审稿人看到"RAG"三个字，第一反应是"你和 GraphRAG/LightRAG 比了吗、你的检索器有什么新意"。你比不过，也不该比——你的检索器的新意不在"检索算法"，在"**知识表示让检索变成约束求解**"。

建议在论文里这样表述：

> 本文不把该过程称为"检索"（retrieval），而称为**约束引导的知识选择**（constraint-guided knowledge selection）：给定算子、代码特征与目标硬件，从知识图谱中选出一个**可执行、无冲突、带参数与证据**的策略集合。选择的正确性由谓词求值、硬件能力匹配与资源预算判定，而非由相似度排序决定。

这么改带来三个好处：

1. **可辩护**：不和 GraphRAG 比检索精度，比"选择的有效性"（SAR、参数正确率、冲突率）；
2. **可证伪**：三个命题都能做实验——(a) 约束过滤提升 SAR；(b) 硬件绑定减少无效生成；(c) 模板+参数提升实现保真度（SIF/PIV）；
3. **可归因**：消融能一项一项拆（条件/硬件/参数/模板/证据），这正是你 `04` 协议里 A1–A6 想做的事。

### 3.8 图还能怎么用（超出"检索→生成"的六种用法）

你现在只用了第 1 种。后面几种不一定要做，但答辩时能说出来，说明你理解"图是一种基础设施，不是一次检索"。

| # | 用法 | 怎么做 | 在本课题的位置 | 建议 |
|---|---|---|---|---|
| 1 | 条件检索 | 七步检索 → 策略包 | 第一部分主线 | 已有 |
| 2 | 参数推导 | 由硬件画像 + 参数推导式算 LMUL/块大小/展开因子 | 检索第 5、6 步 | 已有（参数绑定 + 寄存器预算） |
| 3 | 冲突与预算检查 | 冲突边 + 资源预算 | 检索第 5 步 | 已有（14 条冲突边） |
| 4 | **失败归因** | 编译/运行错误 → 反查涉及哪条策略、哪个条件没满足 → 给修复方向 | **第二部分轨迹总结的现成入口** | 建议做：比"让 LLM 自由总结"可控得多 |

## 4. 使用（核心二）：质量怎么评

### 4.1 三层框架

```text
第 1 层：图本身          →  知识对不对、全不全、一致不一致、能不能追溯
第 2 层：选择/检索        →  该选的选出来了吗、选出来的能用吗、代价多大
第 3 层：下游任务         →  生成的代码对不对、快不快、增量从哪来
```

**三层的关系**：第 1 层是**前提**（图错，后面全错）；第 2 层是**机制**（解释"为什么下游会变"）；第 3 层是**价值**（论文的主结果）。只报第 3 层，审稿人会问"是不是 prompt 写得好"；只报第 1 层，审稿人会问"所以呢"。

GraphRAG-Bench 的三段式（构建/检索/生成）就是这个框架的公开版本，可以直接引用作为方法论依据。

### 4.2 第 1 层：图本身怎么评

**七个维度 + 公式 + 你的现状**：

| 维度 | 定义 | 怎么算 | 你的现状 |
|---|---|---|---|
| 正确性 | 抽出来的知识对不对 | 人工金标准上的 precision / recall / F1（按"策略卡字段"逐项判） | 待标注（`22` 计划 120 条） |
| 完整性 | 该有的有没有 | 覆盖率 = 有知识覆盖的 (算子×架构×策略族) 格 / 计划格；以及**语料覆盖率**（文件级） | 能算（arch×op 矩阵已有空格，如 rvv 缺 symv） |
| 一致性 | 内部有没有矛盾 | 冲突边数、疑似重复数、命名歧义数 | 冲突 14 条（7 对）；命名歧义 28 条；疑似重复 6 组 |
| 可追溯 | 每条能不能回到源头 | 有文件+行号+sha256 的策略占比 | 262/262 = 100% |
| 可执行 | 条件能不能被程序求值 | 可执行条件占比 | 262/262 = 100% |
| 参数合法 | 实例值在声明域内、单位一致 | 越界条数 / 参数实例总数 | **34 / 236 条参数边越界** |
| 简洁性 | 有没有冗余 | 重复策略数 / 总策略数；同族策略的合并率 | 262 策略 / 262 模板（1:1，说明模板没冗余；**策略级冗余要等合并抽检**） |
| 时效性 | 证据新不新 | 证据的采集时间分布、是否需重跑 | 88 条证据，QEMU 置信度 0.35 |

**人工金标准怎么标（这是最容易被问倒的地方）**：

- 抽样：6 个建图算子 × 20 条 = 120 条策略卡（分层抽：每个策略族至少 2 条）；
- 标注字段：**条件对不对 / 参数合不合理 / 模板能不能落地 / 来源对不对**（四个字段分开算，不要合成一个总分）；
- 两人独立标 + 第三人仲裁；报 Cohen's κ（你 `04` 里的目标是 ≥0.75）；
- **关键**：金标准要包含**负例**（"这条不该被抽出来"），否则只能算 precision，算不了 recall。

**自动化校验（不用人，跑一次就能出）**：

```text
schema 合规    节点/边类型在闭集、边两端存在、必填字段非空
谓词合法       谓词在 10 个闭集里、值域类型对
冲突对称       A 冲突 B ⇒ B 冲突 A
槽位完整       模板的 slots 与参数表对得上
命名无歧义     ID 后缀不与 dtype 码冲突、来源字段显式      ← 新增，28 条待改
参数在域内     实例值 ∈ 参数声明的 range，单位/口径一致     ← 新增，34 条待修
```

> 后两条就是第 2.3 节那两个问题。脚本已经写好：`tools/kg_consistency_audit.py`（8 类检查，退出码非 0 表示有 ERROR）。**接进 `validate` 的 CI，比人工看一百条都管用。**

### 4.3 第 2 层：选择/检索怎么评

你 `04` 协议里已经有 SAR / R@k / nDCG@k / PIV / PNR，不用重造。缺的是三件事：

**(1) gold selection set（最关键，没有它 SAR 就是自证）**

要评"选得对不对"，得先有"标准答案"。三种造法，按成本排序：

| 造法 | 怎么做 | 成本 | 可信度 |
|---|---|---|---|
| A. 专家清单 | 对每个 (算子, 硬件) 组合，让 2 位熟悉 BLAS 的人列出"应选的 3–5 条策略" | 高（约 2 人日/20 组） | 最高 |
| B. 实现反推 | 从专家实现（OpenBLAS kernel）里检测出实际用了哪些策略，作为 gold | 中（需要策略检测器，你已有 `SIF` 的思路） | 中高（受限于检测器） |
| C. 交叉验证 | 用 A 的 20 组做种子，其余用 B 扩展，人工抽检 20% | 低 | 中 |

**建议 A+B 混合**：20 组人工清单（覆盖 x86/RVV × 向量/矩阵）做主 gold，其余用实现反推扩展。这 20 组同时能当"策略推荐实验"的测试集。

**(2) 报"转换链"，不要只报终点**

NeurIPS 2026 那篇 audit 的核心发现是：检索侧指标涨了，答案正确率不一定涨（conversion gap）。所以你的检索实验要报一条链：

```text
候选可用率（34 条里几条真可用）
  → 选中可用率（SAR@k）
  → 注入完整率（选中的策略，模板/参数是否都进了 prompt）
  → 实现保真度（SIF：生成代码里真用了几条）
  → 答案正确率（FCR）
```

这条链上每一段掉多少，就是你论文里"机制解释"的素材。比如：SAR 100% 但 SIF 只有 40%，说明"选对了但模型没用上"——这是 prompt/呈现问题，不是知识问题。

**(3) 上下文效率**

```
上下文效率 = SAR@k × k / 上下文字符数（千字符）
```

你现在的图检索是"高 SAR、高成本"；BM25 是"低成本、低 SAR"。这个 trade-off 本身就是一张好图（横轴 token，纵轴 SAR）。

### 4.4 第 3 层：下游任务怎么评（在现有协议上补三个对照）

你的 FCR/EGC/GM/SIF/PIV/PNR 已经够用。要补的是**归因对照**，否则"图有用"这个结论站不住：

| 对照 | 怎么做 | 排除什么 |
|---|---|---|
| **等 token** | 给扁平文本基线 3 倍的检索量，使两边上下文字符数相当 | 排除"只是多给了字数" |
| **等规模随机** | 从图里随机抽同样条数的策略（保证条数、token 相当） | 排除"多给几条就好" |
| **同 reranker** | 两种检索都过同一个重排器 | 排除"增益来自重排"（audit 论文的 matched attribution control） |

**消融矩阵**（你 `04` 的 A1–A6 已经列了，这里给判定口径）：

| 去掉什么 | 预期掉什么 | 如果没掉，说明什么 |
|---|---|---|
| 条件过滤 | SAR↓、FCR↓ | 条件没起作用（可能条件写太宽） |
| 硬件过滤 | 编译率↓ | 模型自己能判断硬件（不太可能） |
| 参数 | PIV↓、PNR↓ | 参数是废话 |
| 模板 | SIF↓ | 模板只是装饰 |
| 证据/来源 | 正确率不变但可解释性↓ | 证据不影响生成，只影响信任 |
| 图结构（换随机子图） | 全面↓ | 图结构无价值 → 你的核心假设不成立 |

最后一行是**生死线**：如果"随机子图"和"图检索"效果一样，你的论文就得改写成"知识内容有价值，但结构没价值"——这也是一个诚实的结论，但要提前想好退路。

### 4.5 统计与五个坑

1. **重复**：每个 (算子, 硬件) 至少 3 次生成（温度>0 时），报均值+方差；确定性解码要说明。
2. **配对检验**：同一任务上比两种方法，用配对 Wilcoxon 或 bootstrap CI，不要用独立 t 检验。
3. **多重比较**：12 算子 × 2 平台 × 5 指标 = 120 个比较，至少做 Holm 校正或预先指定主指标。
4. **LLM-as-judge**：如果用模型评"代码对不对"，必须和人工评 20% 样本对齐（报 agreement），否则不可信。
5. **小样本**：4 组查询的 pilot 只能当方向，不能当结论——今天这张 SAR 表就是 pilot。

### 4.6 第二部分（自维护）复用同一套

你 `02b` 里已经有：学习曲线、回归率、知识精度、更新采纳率、成本。这里只补一句**衔接**：

> 第一部分的"图质量"指标，在第二部分变成**版本间的差分**：每轮更新后，一致性/覆盖率/ID-条件一致率是升还是降？如果知识精度升了但一致性降了，说明门控只挡住了"错的知识"，没挡住"重复的知识"。

## 7. 答辩三问（针对本文档新增的）

**Q1："你这个知识图谱到底怎么检索的？"**
> "不是相似度检索，是约束引导的选择。给定算子、代码特征和硬件，我从算子节点出发沿'有流程→被优化'两条边走，召回候选策略；然后逐条对条件谓词求值、查硬件绑定和 ISA 能力、做冲突和寄存器预算检查；最后按匹配度/适用度/证据强度打分，打包成带模板和参数的策略包。每一步都有 trace，能被淘汰的会记下理由。今天 daxpy/AVX2 的例子是 34 条候选 → 条件淘汰 23 条 → 硬件淘汰 8 条 → 3 条进 prompt。"

**Q2："这不就是 RAG 吗？你和 GraphRAG 有什么区别？"**
> "共享'检索增强'的框架，但检索单位、匹配方式和要解决的问题都不同。GraphRAG 是从文档抽实体图、用社区摘要回答语料级问题；我的图是 schema 固定的程序性知识库，问题带硬约束（dtype/stride/ISA），检索是约束满足而不是相似度。我不主张图普遍更好——单跳细节查询用文本检索更划算；我的主张是：当选择依赖可判定的硬约束和可追溯证据时，结构化有可测收益，我给出这个边界的证据。"

**Q3："你怎么证明图的质量？"**
> "三层。图本身：120 条人工金标准算条件/参数/模板/来源四项 P/R/F1 和 κ，加上覆盖率矩阵、一致性（命名歧义/疑似重复）、参数域合法率、溯源率、可执行率，并把这些做进构建期的自动检查。选择层：20 组人工 gold 上的 SAR@5/R@5/nDCG，以及从候选到答案的转换链。下游：FCR/EGC/SIF/PIV，配等 token、等规模随机、同 reranker 三个对照，把'结构'的贡献和'多给上下文/多给条数/重排'分开。如果拆不开，我就报边界，不硬说图有用。"

| 向量 RAG 里的词 | 图里的对应物 | 差别 |
|---|---|---|
| chunk | 子图 / 策略卡 | 子图有类型、有边、有约束 |
