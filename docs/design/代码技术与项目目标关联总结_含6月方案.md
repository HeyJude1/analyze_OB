# OpenBLAS/KG 代码技术、6 月方案与项目目标关联总结

## 1. 材料范围

本总结基于以下文件整理：

- `KG/`：知识图谱构建、实体对齐、优化策略检索与 Neo4j 导出代码。
- `agent24.py`：OpenBLAS 优化策略三层分析 Agent 定义。
- `agent_work24.py`：算法层、代码层、指令层顺序分析工作流。
- `6月设计方案.docx`：重点阅读“基于大模型的多层级代码转换”。
- `项目.docx`：重点关注“动态知识提炼、阶段化提示、测试驱动约束、验证反馈”的研究目标。

总体判断：当前代码已经形成了一个“面向高性能算子代码的阶段化语义分析 + 知识图谱 + RAG 策略推荐”原型。它与 `6月设计方案.docx` 中的多层级代码转换思路高度相关，也能为 `项目.docx` 中“过程化提示方法、动态知识提炼与验证反馈”的目标提供工程基础。不过，当前代码更偏“分析、提炼、检索、推荐”，距离完整的“自动生成代码 + TDD 验证 + 错误反馈修复”仍需补齐生成与测试闭环。

## 2. 代码完成的主要工作

### 2.1 三层优化策略分析

`agent24.py` 将 OpenBLAS 优化策略分析拆成三类专家：

| 层级 | 函数 | 关注内容 |
|---|---|---|
| 算法层 | `create_algorithm_optimizer` | 循环结构、分块、数据重用、计算重排 |
| 代码层 | `create_code_optimizer` | 缓存优化、内存访问模式、对齐、预取 |
| 指令层 | `create_instruction_optimizer` | SIMD、FMA、指令级并行、寄存器使用 |

每个专家都要求输出统一结构，包括优化名称、层级、原理、实现模式、性能影响、代价、适用条件、可调参数和关联计算流程。这种设计已经体现了“分层语义约束”：模型不是一次性自由总结，而是在明确的语义层级和字段约束下工作。

`agent_work24.py` 进一步用 `LangGraph` 编排顺序流程：

```text
algorithm_analysis -> code_analysis -> instruction_analysis -> finalize
```

该流程包含源文件拼接、结构化提示、JSON 解析、格式验证、错误记录和重试机制。它可以视为 `项目.docx` 中“过程化生成/分析流程”的早期原型。

### 2.2 KG 中的知识图谱抽取

`KG/extractor21.py` 将历史分析结果转换为知识图谱实体，并写入 Milvus。主要实体如下：

| 实体 | 作用 |
|---|---|
| `computational_pattern` | 计算流程/计算模式，如参数校验、packing、microkernel |
| `optimization_strategy` | 优化策略，如循环展开、分块、SIMD 化 |
| `hardware_feature` | 硬件特征，如 Cache、SIMD、寄存器 |
| `tunable_parameter` | 可调参数，如块大小、展开因子 |
| `code_example` | 代码样例 |
| `relation` | 实体关系 |

主要关系包括：

- `OPTIMIZES_PATTERN`：优化策略作用于某类计算流程。
- `TARGETS`：优化策略面向某硬件特征。
- `HAS_PARAMETER`：优化策略包含可调参数。
- `IS_ILLUSTRATED_BY`：优化策略由代码样例说明。

这部分对应“动态知识提炼”：从已有算子分析结果中提取可复用的知识单元，并建立可检索、可追溯的结构化知识库。

### 2.3 实体聚类、对齐与关系精炼

`KG/entity_alignment.py` 调度三轮实体对齐流程：

```text
retrieve_clusters21.py
  -> refine_clusters21.py
  -> relation_merger21.py
```

各模块职责如下：

| 模块 | 工作 |
|---|---|
| `retrieve_clusters21.py` | 从 Milvus 取出实体，按 embedding 相似度聚类 |
| `refine_clusters21.py` | 调用 LLM 判断簇内实体是否应合并，并给出规范名称 |
| `relation_merger21.py` | 合并实体内容、重定向关系、生成策略上下文 |

最终会生成 `optimization_strategy_context_*.json` 和策略频率 CSV。这里的关键价值是把重复、近似、表述不一的策略整理为更稳定的知识上下文，为后续检索和生成提供更可靠的约束。

### 2.4 新代码的策略检索与评分

`KG/Operator_op2.py` 是 KG 文件夹中最关键的面向新任务模块。它的流程是：

```text
输入源码
  -> 四阶段计算流程识别
  -> embedding 向量化
  -> Milvus 相似计算模式检索
  -> 通过 OPTIMIZES_PATTERN 关系找到关联策略
  -> 结合 core_patterns/contextual_patterns 评分
  -> 输出 final_strategies
```

四阶段计算流程包括：

| 阶段 | 典型模式 |
|---|---|
| 计算准备 | 参数合法性校验、索引与指针初始化、循环不变量计算 |
| 数据转换与预处理 | packing、特殊结构展开、transpose |
| 核心计算 | vector reduction、elementwise update、GEMV-like、rank-1 update、microkernel、tiled loop、triangular solve |
| 后处理与写回 | 结果缩放与累加 |

该模块还支持批量处理 `Morph/openblas_output/` 下的多个 `.c` 文件，并输出到 `op_results/`。因此，它已经具备“自动化知识召回与交付物生成”的雏形。

### 2.5 Neo4j 导出与数据库备份

`KG/export_to_neo4j.py` 将 Milvus 中的实体与关系导出为 Neo4j 图数据库节点和边，方便可视化与关系查询。

`KG/backup_database.py` 支持 Milvus 数据库复制、集合结构保留、索引恢复和加载，保证知识库可迁移、可备份。

## 3. 使用的核心技术

| 技术 | 在代码中的作用 |
|---|---|
| 大语言模型 | 代码优化策略分析、计算流程识别、实体语义精炼、实体内容融合 |
| Prompt Engineering | 用强约束模板控制输出字段、分析层级和可识别模式 |
| LangChain | 封装 LLM、Prompt、结构化解析器和工具调用 |
| LangGraph | 编排多阶段分析工作流 |
| DashScope/Qwen | 作为主要大模型与 embedding 服务 |
| Milvus | 存储实体向量，支持相似计算模式检索和实体聚类 |
| Neo4j | 图谱化展示实体关系 |
| Embedding/RAG | 将当前源码模式与历史优化知识连接起来 |
| 高性能计算知识 | BLAS 算子、SIMD、FMA、packing、blocking、cache locality、microkernel |

## 4. 与 6 月设计方案“多层级代码转换”的关系

`6月设计方案.docx` 中将 X86 到 RISC-V 的代码转换拆成四个层级：

| 6 月方案层级 | 方案关注点 | 当前代码中的对应基础 |
|---|---|---|
| 跨函数级代码转换 | 识别并重构平台耦合的高层计算策略 | `algorithm_level_optimizations`、优化策略实体、策略上下文 |
| 函数级代码转换 | 并行模式重构，如线程、任务划分、同步 | `code_level_optimizations` 中的循环、内存访问、并行友好结构分析，可扩展到 OpenMP/RISC-V 并行策略 |
| 片段级代码转换 | 循环结构、数据局部性、Cache 适配 | `computational_pattern` 中的 `core.tiled_loop`、`transform.packing`、`core.mm_microkernel`，以及 Cache 相关策略 |
| 语句级代码转换 | X86 SIMD 到 RISC-V V 扩展的语义等价转换 | `instruction_level_optimizations`、SIMD/FMA/hardware_feature 实体 |

6 月方案还强调结构化提示词由四类要素组成：

| 提示词要素 | 当前代码支撑 |
|---|---|
| 源代码描述 | `Operator_op2.py` 读取源码并抽取计算流程、代码片段、数据对象特征 |
| 目标平台描述 | 当前配置中尚不充分，需要补充 RISC-V 编译器、库、并行框架信息 |
| 硬件约束信息 | KG 已有 `hardware_feature` 实体，可扩展为 RISC-V Cache、RVV、流水线、内存对齐等知识 |
| 结果反馈信息 | 当前主要有格式验证和重试，需扩展为编译/测试/性能反馈 |

因此，当前 KG 系统可以作为 6 月方案中 RAG 模块和多层级转换智能体的“知识支撑层”。它能识别源码中的计算流程，并召回相关优化知识；后续只需把召回结果进一步转化为跨函数级、函数级、片段级、语句级转换 Prompt，即可接入多层级代码生成。

## 5. 与 `项目.docx` 目标的关系

`项目.docx` 的核心目标是：

> 构建融合动态知识提炼与测试驱动开发的过程化提示方法，将分阶段语义约束思想引入大语言模型代码生成流程，提升生成代码的稳定性与可验证性。

当前代码与该目标的对应关系如下：

| 项目目标 | 当前代码基础 | 关联程度 | 还需补齐 |
|---|---|---|---|
| 动态知识提炼 | KG 抽取策略、计算流程、硬件特征、参数和代码样例 | 强 | 扩展到需求文档、接口定义、测试规范 |
| 阶段化语义约束 | 三层优化分析、四阶段计算流程识别、LangGraph 流程 | 强 | 泛化为需求抽象、测试生成、代码生成、验证修复 |
| 外部知识引导 | Milvus/RAG 根据当前源码召回历史优化策略 | 强 | 将策略注入代码生成 Prompt |
| 测试驱动约束 | 当前只有格式验证、JSON 校验、重试 | 中 | 增加单元测试生成、测试执行、失败反馈 |
| 验证反馈优化 | LLM 调用重试、实体对齐迭代、策略评分 | 中 | 增加编译日志、运行错误、性能回退分析 |
| 自动化交付物 | 输出 JSON、关系文件、策略上下文、CSV | 强 | 增加测试报告、实现说明、变更摘要 |

换句话说，当前代码非常适合作为项目中的“动态知识提炼与阶段化约束构建”模块，但还不是完整的“测试驱动代码生成系统”。

## 6. 可以形成的统一技术路线

建议将当前代码与两个文档目标统一为如下路线：

```text
阶段 1：任务/源码语义抽象
  输入：项目文档、接口定义、已有源码、算子代码
  输出：结构化任务描述、计算流程、数据对象特征
  可复用：Operator_op2.py 的四阶段模式识别

阶段 2：动态知识提炼与 RAG
  输入：历史分析结果、优化策略、硬件文档、API 文档
  输出：相关策略、硬件约束、代码样例、可调参数
  可复用：extractor21.py、retrieve/refine/merge、Milvus、Neo4j

阶段 3：多层级代码转换/生成
  输入：源代码描述、目标平台描述、硬件约束、召回知识
  输出：跨函数级、函数级、片段级、语句级候选代码
  可复用：agent24.py 的分层专家设计
  需新增：真正面向 RISC-V 的代码生成 Agent

阶段 4：TDD 验证与反馈修复
  输入：候选代码、测试用例、编译/运行/性能结果
  输出：结构化失败原因、修复提示、下一版代码
  需新增：测试生成器、测试执行器、错误日志解析器、修复 Agent

阶段 5：自动化交付
  输入：最终代码、测试结果、知识引用、策略使用情况
  输出：测试报告、功能说明、变更摘要、实验数据
  可复用：op_results 和 relation_refine 的结构化归档方式
```

## 7. 当前技术亮点

1. 代码已经具备面向复杂算子代码的多层语义拆解能力，可以从算法层、代码层、指令层分别提取优化策略。
2. KG 模块建立了“计算流程 - 优化策略 - 硬件特征 - 参数 - 代码样例”的图谱结构，支撑知识可追溯和可复用。
3. 使用 Milvus + embedding 实现相似模式检索，使系统能够根据当前源码动态召回历史经验。
4. 使用 LLM 进行实体聚类精炼和内容融合，降低知识冗余，提高知识库稳定性。
5. `Operator_op2.py` 已经能面向新代码给出 `final_strategies`，可作为代码生成前的约束推荐器。
6. 批量处理和结构化输出机制可支撑实验评估与自动化交付。

## 8. 当前不足与风险

1. `agent_work24.py` 当前存在语法缩进问题，`try/except` 结构不完整，直接运行会失败。若作为原型展示，需要优先修复。
2. 当前验证更多是“输出格式验证”，还不是 `项目.docx` 所需的“行为正确性验证”。
3. 当前知识库主要围绕 OpenBLAS 优化策略，若要支撑 X86 到 RISC-V 代码迁移，还需要补充 RISC-V API、RVV intrinsics、编译器、运行时和硬件文档。
4. 当前 `Operator_op2.py` 能推荐策略，但还没有把策略自动转成目标平台代码。
5. 当前缺少自动测试生成、编译执行、错误日志解析和反馈修复模块。

## 10. 可用于项目材料的表述

可以将当前代码包装为如下已有基础：

> 已构建面向高性能算子代码的知识增强分析原型。该原型通过大模型将源码行为拆解为计算准备、数据转换、核心计算和结果写回四类计算流程，并从算法层、代码层、指令层抽取优化策略；进一步将计算流程、优化策略、硬件特征、可调参数和代码样例组织为知识图谱，利用向量数据库实现面向当前代码上下文的动态知识召回。该原型为后续多层级代码转换中的源代码语义抽象、RAG 知识注入、结构化提示约束和自动化交付提供了工程基础。

也可以与 `项目.docx` 目标这样衔接：

> 在项目所提出的过程化提示代码生成框架中，现有 KG 系统可承担“动态知识提炼”和“约束构建”角色：它从历史代码与分析结果中提炼可复用知识，并在新任务到来时召回相关策略，形成可注入 Prompt 的结构化上下文。后续结合测试生成、编译运行和错误反馈模块后，可进一步形成“知识提炼 - 测试约束 - 代码生成 - 验证修复 - 交付归档”的闭环。

## 11. 总体结论

当前代码、6 月设计方案和 `项目.docx` 可以形成清晰关联：

- `KG/` 代码提供“知识提炼、知识图谱、RAG 检索、策略推荐”的工程基础。
- `agent24.py` 和 `agent_work24.py` 提供“分层专家、阶段化语义约束、结构化输出”的 Prompt/Agent 基础。
- `6月设计方案.docx` 提供“跨函数级、函数级、片段级、语句级”的代码转换框架。
- `项目.docx` 提供更通用的研究目标，即“动态知识提炼 + TDD + 过程化提示 + 验证反馈”。

最准确的定位是：

> 现有代码是面向 OpenBLAS/高性能算子的阶段化语义分析与知识增强原型；它可以作为项目中动态知识提炼、RAG 知识注入和多层级代码转换提示构建的基础模块。后续补齐代码生成、测试驱动约束、编译运行验证与错误反馈修复后，即可扩展为 `项目.docx` 所描述的过程化、高可验证代码生成系统。
